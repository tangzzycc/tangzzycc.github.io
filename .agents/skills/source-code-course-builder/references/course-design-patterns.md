# 课程划分与单课组织

## 内容

1. 从目标到课程主线
2. 课与课之间的依赖和边界
3. 按主题选择单课组织方式
4. 贯穿例子与重复内容
5. 讲义表达与改版检查

## 从目标到课程主线

先确定受众已具备的知识、希望获得的能力、课程深度，以及交付是大纲还是可讲述正文。已有课程能回答这些问题时直接沿用，不重复询问，也不把备课表机械贴进讲义。

为模块确定一个可以回答的主要问题。例如“请求如何从输入到模型输出”“有限显存如何容纳多个请求”“如何减少 Attention 的数据搬运”。技术和类名围绕问题组织，而不是逐项开课。

选择能解释实际变化的主线：

| 主线 | 起点 | 需要解释到的结果 |
|---|---|---|
| 请求执行 | 一个请求到达 | 获得输出或进入明确的等待、失败状态 |
| 资源管理 | 有限容量与请求需求 | 分配、查找、复用和释放的效果 |
| 调度决策 | 多个竞争任务 | 谁被执行、谁被等待及其依据 |
| 数据表示 | 用户输入或逻辑对象 | 下游实际使用的布局或索引 |
| 性能优化 | 特定负载下的成本 | 成本如何降低、还剩什么瓶颈 |

不要求所有课程走同一条“架构—数据结构—调度—执行”路线。以算法为主的课程可以从直接计算进入推导；以架构为主的课程需要先交代必要边界。

## 课与课之间的依赖和边界

为候选课程做一张简短的作者用表：

| 本课问题 | 必须已知 | 新增理解 | 贯穿例子或证据 | 与相邻课的边界 |
|---|---|---|---|---|
| 一句话写出读者的问题 | 真正被用到的概念 | 学完能解释什么 | 用哪个状态变化证明讲清了 | 哪部分已讲、哪部分由本课承担 |

检查每个前置概念是否已经出现。若当前课只需一个直观定义，局部补足即可；若核心机制依赖尚未解释的复杂过程，应调整顺序、缩小范围或增加必要铺垫，不能靠一句“后面会讲”跨过去。

### 拆分与合并

- **拆分：** 一课包含两个独立问题，各自都需要新模型、独立例子和较长推导；或者后半部分引入的前置知识掩盖了前半部分的主线。
- **合并：** 两课一直使用同一问题和同一状态变化，第二课大半内容用于重建第一课；或者某课只是另一课的一段准备步骤。
- **保留同课：** 即使跨多个文件、角色或执行阶段，只要这些环节共同解释一个结果，而且负担可控，就沿同一个例子讲完。
- **保留分课：** 共用术语或数据结构不意味着冗余；若回答的问题、决策或可观察结果不同，可以保留并明确新增部分。

不要只按字数、图数、函数数量或文件边界判断。若用户提供授课时长，按实际讲解步骤与概念密度估算节奏；不要凭字数给出精确时长。

### 优化课的先后关系

把每项技术放回它解决的问题：原有机制已经消除了哪些成本，留下了什么，新技术针对其中哪一项。不能因版本号递增就默认后者解决前者所有瓶颈，也不能把工作负载不同的优化强行串成单线演进。

诊断工具围绕可观察的现象引入。例如先说明需要区分 CPU 空闲、传输等待和 GPU 计算，再选择对应证据；只有目标本身是系统性能诊断训练时，才考虑独立组织 profiling 模块。

## 按主题选择单课组织方式

以下是因果组织方式，不是固定章节标题。选择主线后按实际内容增减；没有必要的环节可以省略，不强制补齐所有节点。

### 优化类：从具体成本推到新机制

原始做法 → 成本和瓶颈 → 关键观察 → 方案带来的新约束 → 推导与机制 → 同例对照 → 实现与适用边界。

读者应该能回答：为什么要优化这一项？方案为什么能降低它？方案又引出了什么困难？如何保持原有语义？

例如 Attention 的课程主线可以是：

1. 固定例子，给出直接计算的关键中间结果，并追踪哪些中间量被写入、读回 HBM。
2. 从已说明的读写成本提出分块生成、就地使用，而不是直接宣布一个算法名称。
3. 说明每块只有部分分数，独立 softmax 的分母无法代表完整一行，由此产生跨块维护状态的需求。
4. 推导可以合并的统计量及其更新关系，解释它们为什么足以得到完整结果。
5. 用原例已有的中间结果，展示新状态如何跨块更新并得到相同目标输出；只计算变化的步骤。
6. 在选定实现中核对状态与执行映射，并说明优化适用的负载条件。

这只是组织示例，实际矩阵数量、执行顺序、复杂度和硬件行为必须由所选实现或论文支持。不能把数学分块直接当成线程块划分，也不能把读写下降等同于所有负载必然加速。

### 架构类：沿一个任务追踪职责

具体请求或任务 → 必要角色和边界 → 数据与控制如何流转 → 关键决策及状态变化 → 可见结果 → 设计取舍。

先让读者知道“谁要完成什么”，再解释角色为何存在。在同一调用链中区分控制信息与实际数据、调度决定与执行动作。源码用于回答当前环节是谁发起、谁持有、谁更新，不能变成类名清单。

总览图可以放在角色介绍附近，局部图放到复杂转换处；若读者尚不认识图中的对象，应先补必要介绍。

### 机制类：跟踪规则怎样改变状态

待解决问题 → 最小输入与初始状态 → 规则或不变量 → 状态逐步变化 → 结果为何成立 → 对应实现与必要边界。

用对象 ID、索引、形状或具体数值连接步骤。数学机制展开必要推导，资源机制展开分配与查找，不强迫每种机制都出现“生产者、消费者、回收”三节。

反例、边界或替代方案放在能消除具体误解的位置，不默认各自独立成章。源码可以穿插于各步骤，不一定集中在最后。

## 贯穿例子与重复内容

选择一个足够小、但能触发关键状态变化的例子。计算类固定输入、形状和计量口径，资源类固定请求、页号与分配状态；示意数值与严格计算结果明确区分。

同一课内给每段内容分配不同作用：引入问题、推导规则、应用规则、说明边界。如果两段使用同一组步骤得出同一结论，保留解释更清楚的一处。

推导与应用不一定重复：推导说明更新规则为何成立，应用说明规则如何进入完整算法。应用部分引用已算过的结果，只展开状态保存、循环或映射等新增内容。

跨课复用已经建立的概念时，用当前步骤需要的一两句提醒或准确链接恢复上下文；不要复制整段推导，也不要为了去重让单课无法阅读。记录概念首次出现位置和后续用途，防止定义、记号和例子悄悄变动。

正文与图片各自承担解释任务：正文说明理由和条件，图展示难以用文字跟踪的变化；图注解释阅读方法或必要假设，不再复述整段正文。

## 讲义表达与改版检查

- 前言若需要，写问题与核心内容的摘要；不堆放版本免责声明、写作安排或后续章节指路。必要版本条件靠近相关实现说明。
- 标题使用具体概念和关系，例如“分块计算中的归一化依赖”，而不是“先建立直觉”或一整句备课口号。
- 新术语首次使用时给足以继续阅读的解释。非必要缩写、符号和旁支不进入主线。
- 把重要公式放到推导步骤里，写清从前一步到下一步改变了什么。使用常见符号，但不为展示“通用性”引入本课不需要的变量。
- 图片出现在相应内容处；只讲一行算式或一个简单事实时不强行配图。
- 结尾若需要，回答本课问题，保留影响结论的适用条件；不固定增加回顾或下一课预告。

改版时检查目录、编号、前置概念、文内跳转和图片引用是否仍然一致。目录里明确每课贡献，正文不必反复说明作者怎样安排课程。实践、练习、选读和独立实验应由课程目标或用户要求决定，不能作为凑齐模板的章节。
