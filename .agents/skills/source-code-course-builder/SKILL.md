# Source Code Course Builder

把技术知识组织成学习者能跟随、讲师能讲清的课程。以学习目标、概念依赖和具体问题决定结构；不照搬源码目录，也不让每节课套同一种模板。

## 确定本次交付范围

先读取用户要求、已有课程和仓库规则，明确受众基础、课程目标、现有章节及输出位置。从上下文能确定的信息直接沿用。

- **规划课程或调整划分：** 阅读 [course-design-patterns.md](references/course-design-patterns.md)，先确定主线、依赖和每课边界，再写正文。
- **编写或修改单课：** 阅读该课及必要的相邻课程，确定核心问题、已有知识和新增理解；按需查阅同一参考文件的单课组织方式。
- **审阅或准备定稿：** 阅读 [quality-rubric.md](references/quality-rubric.md)，区分事实错误、逻辑断层、重复内容与排版问题。
- **解释或核查实现：** 阅读 [source-evidence.md](references/source-evidence.md)，沿定义、调用方、状态变化与结果确认行为。

简单解释或局部修改不需要重新规划整门课；用户只要聊天回答时，不额外创建文档。规划阶段可以先确定结构，写实现结论时再核实对应源码。

## 先建立教学主线

回答：学习者目前能解释什么，学完应能解释或完成什么，哪些理解必须先建立？用可观察的能力描述目标，例如“能沿调用链解释一个请求如何获得 KV 空间”，而不是“掌握 KV Cache”。

按任务需要梳理系统边界、控制决策、数据流或资源生命周期，不要求每次画齐所有地图。选出能连接多个知识点的主线，例如一个请求的执行、一份资源的分配与释放，或一个性能瓶颈的逐步消除。

每课围绕一个主要问题，明确必要前置知识、这次新增的理解，以及用什么例子或证据说明它。依赖顺序优先于文件顺序、论文年代和技术名称列表。不要为了目录整齐强行凑课数。

## 按理解边界划分课程

同一课内的各节应共同回答开头的问题。生产者、消费者和状态变化属于同一条可理解的链路时，放在一起讲；不能仅因位于不同类、文件或进程就拆课。

出现两条独立主线，或者后一部分需要大量尚未建立的前置知识时，考虑拆分。某一课离开相邻课后没有独立问题、反复重复前置推导时，考虑合并。必要的简短提醒不等于冗余，完整重讲已建立的机制才需要处理。

课程规划中的“本课负责什么、后课依赖什么”用于作者检查边界，不自动变成讲义中的范围声明或下节预告。重排后同步目录、课号、交叉引用和图片引用；未经需要不扩大到无关模块。

## 用问题推动每节课

先确定本课属于优化、架构、机制，还是其他任务，再选择合适的展开方式，详见课程组织参考。混合主题以一个主要问题为中心，让其他内容服务于它。

每增加一节，检查它回答了前文产生的哪个疑问，又提供了什么新增理解。若只是另列一个术语、函数或工具，没有因果关系，就需要重新安排或删除。标题写具体内容，不直接使用“建立直觉”“为什么讲这个”“如何消费”等备课提示。

需要前言时，用简短摘要说明本课的问题与核心内容。只有当前解释确实依赖旧知识时才简短提醒，不固定设置“课程回顾”。结尾回答本课问题及必要边界，不机械复述目录。

## 让例子和推导承担解释

选择足够小、但保留关键机制的例子，尽量贯穿前后。优化前后保持相同输入、输出目标和计量口径。已经算过的中间结果可以引用，后续只展开新的变化；不要换一组数字重新证明同一件事。

公式先交代对象、形状、符号和所解问题，再展示关键推导。只引入推导需要的记号；能直接写清的常数不另起别名。采用简化假设时说明条件，不能为了少一个符号而把一般情况下可能不同的量说成恒等。

按内容需要区分逻辑与物理、元数据与实际数值、视图与副本、完整向量与序列分块、算法分块与线程执行映射。小例子应算得闭合，不能用“结果一致”替代关键步骤。正确性说明可以是手算、不变量或推导，不必新增可运行实验。

## 用证据支撑实现和优化结论

实现结论绑定已核实的源码版本。优先使用 `git show <rev>:<path>`、`git grep <pattern> <rev> -- <path>` 等方式，避免把当前工作树行号用于另一个版本。

沿概念所需的调用链解释定义、输入、输出、状态变化和可见效果；遇到不改变理解的封装即可停止。源码片段和链接放在它支撑的说明旁，解释代码为什么这样组织，而非逐行翻译。

区分论文算法、生产实现中的改造与仅仅相似的思路。性能结论注明工作负载、指标及必要硬件条件；理论成本不冒充实测收益。版本或证据尚未核实的结论保留为待确认项，不用自信措辞补齐。

交付带 GitHub 源码链接的 Markdown 时运行 `scripts/audit_course.py` 做机械检查；多仓库或多版本材料按对应范围分别检查。脚本通过不能证明链接语义、数学或教学逻辑正确。

## 在需要解释的位置配图

先确定读者需要通过图看懂哪个关系，再决定是否画图、放在哪里。图跟随相应介绍；只有理解整课确实需要全局地图时才在开头放总览图。不设置必备图数。

让图形展示对象如何产生、变化、共享、移动和得到结果；避免把正文搬进几个文字框。保持对象身份、轴、颜色和计量口径一致。公式贴近对应操作，配图不替正文完整重讲一遍。

示意图与实际执行调度要明确区分。在最终文档显示宽度检查标签、箭头、数学和信息密度。需要最终插图时使用合适的绘图技能；用户指定 SVG 或已有可编辑工作流时保留它。

`audit_course.py --require-visual` 仅在交付要求确实需要配图时启用，只检查存在性，不要求图片出现在开头；放置位置仍需人工判断。

## 本课程仓库的写作约定

以下来自本用户的课程要求，适用于此课程系列；新的明确要求优先，不推广为所有课程的通用规则。

- 默认中文正文、英文图内标注；使用自然、具体的章节标题。
- 不添加“下一课讨论……”等预告，也不在正文插入备课安排和无助于理解的元说明。
- 不主动添加实验、练习、选读或训练扩展章节；手算例子和必要推导照常保留。用户要求实践课程时按新目标安排实践。
- 性能分析在具体瓶颈出现时引入，先给排查依据再给工具；不单独堆放没有问题场景的 profiling 清单。
- 讲 vLLM 时聚焦 vLLM，不引入无关个人项目。
- 在目标 Markdown/PDF 渲染环境检查公式、矩阵换行、粗体边界及图文排版。按该系列约定在粗体结束标记后留空格，不把这一习惯说成所有 Markdown 引擎的统一规则。

## 检查并交付

按正确性、逻辑依赖、重复内容、讲解可理解性和展示效果检查，先修影响理解的错误，再处理美观。区分必要前提提醒与重复推导；不要为“去重”删掉因果链中的关键一步。

只交付任务需要的规划、讲义、插图或修改结果。验证过程中的脚本和检查记录不自动进入发布课程。明确哪些经过源码、算例或渲染检查，哪些尚未核实；静态检查通过不等于已经适合录课。
