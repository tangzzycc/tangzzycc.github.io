## 1. 最终结果

最终 benchmark 使用单卡 AMD Radeon 8060S（`gfx1151`）、32 条独立 COCO holdout、
`max-num-seqs=1`、greedy、最多 64 token、`torch.compile` 与 HIP Graph
`FULL_DECODE_ONLY`。

| 指标（P50） | BF16 | Tuned AWQ W4A16 | 变化 |
|---|---:|---:|---:|
| TTFT | 1165.09 ms | 1164.42 ms | **-0.06%，基本持平** |
| TPOT | 66.49 ms/token | 27.42 ms/token | **-58.76%** |
| Decode TPS | 15.04 token/s | 36.47 token/s | **2.42×** |
| End-to-End Latency | 5237.98 ms | 2883.99 ms | **-44.94%** |

显存结果：

| 指标 | BF16 | AWQ W4A16 | 变化 |
|---|---:|---:|---:|
| 模型加载显存 | 34.48 GiB | 16.94 GiB | -50.87% |
| KV Cache 显存 | 60.96 GiB | 77.27 GiB | +26.75% |
| KV Cache token 容量 | 70,090 | 88,836 | +26.75% |

最重要的归因边界是：

> **2.42× Decode 加速来自 W4A16 权重压缩及已有 HIP skinny decode 路径；本次 CogAgent
> Prefill tile 调优只负责消除最初的 TTFT 回退，不能把 Decode 加速归因于 Prefill 调优。**

## 2. 心智模型：同一个 Linear，两种 M 区间

对 Linear GEMM：

$$
Y_{M\times N}=X_{M\times K}W^T_{K\times N}
$$

`M` 是本次送入 Linear 的 token 行数。Decode 通常只有很小的 `M`，Prefill 和视觉 encoder
输出则可能有数百到数千行。两种场景的瓶颈不同：

默认 `--w4a16-prefill-dequant=off` 时：

```text
M <= 5   -> HIP skinny GEMM, wvSplitK_int4_g
M > 5    -> Triton fused-dequant W4A16 GEMM
```

若把 `--w4a16-prefill-dequant` 设为 `soft` 或 `hard`，并成功缓存 dense dequant 权重，`M > 5`
还可能复用普通 unquantized GEMM dispatch。当前最终对比使用 `off`，因此后文 Prefill 调优针对
Triton 路径。

- Decode 更偏权重带宽受限，直接读取 INT4 packed weight 收益大。
- Prefill 计算密度更高，tile 大小、workgroup 数和 K-group 边界更重要。
- 两条路径共享一份 `[N, K//8]` skinny packed 权重，避免为 HIP 与 Triton 保存两套量化权重。

因此“W4A16 更快”不能只用一个 kernel 解释；必须分别观察 TTFT 和 TPOT/Decode TPS。

## 3. CogAgent 的量化接入保持在模型层边界内

CogAgent W4A16 支持提交为
[`1d57dc25b1`](https://github.com/tangzzycc/vllm/commit/1d57dc25b1e7de85ac804fd06773017b5b922d68)，
主要修改下列文件：

- [cogagent.py](https://github.com/tangzzycc/vllm/blob/gfx11/cogagent-18b-support/vllm/model_executor/models/cogagent.py)
- [rdna_hybrid_w4a16.py](https://github.com/tangzzycc/vllm/blob/gfx11/cogagent-18b-support/vllm/model_executor/kernels/linear/mixed_precision/rdna_hybrid_w4a16.py)
- [test_rdna_hybrid_w4a16.py](https://github.com/tangzzycc/vllm/blob/gfx11/cogagent-18b-support/tests/kernels/quantization/test_rdna_hybrid_w4a16.py)

模型侧只做标准 vLLM quantization plumbing：

```python
class CogAgentForCausalLM(nn.Module, SupportsMultiModal, SupportsQuant):
    ...

quant_config = vllm_config.quant_config

self.layers = nn.ModuleList(
    CogAgentDecoderLayer(
        self.hf_config,
        cache_config=cache_config,
        quant_config=quant_config,
        prefix=f"{prefix}.layers.{i}",
    )
    for i in range(self.hf_config.num_hidden_layers)
)
```

`quant_config` 再传给 `QKVParallelLinear`、`ColumnParallelLinear`、
`MergedColumnParallelLinear` 和 `RowParallelLinear`。AWQ 的合并 MLP 权重 loader 同时映射：

```text
weight / qweight / qzeros / scales
```

这让量化 checkpoint 复用 vLLM 现有 Linear quantization 接口，没有把 AWQ 分支扩散到 scheduler。

## 4. Hybrid kernel 的真实 dispatch

生产实现把 kernel 注册为 opaque custom op，使 `torch.compile` 不把 Python 分支捕获进图：

```python
if M <= MAX_SKINNY_BATCH_SIZE:
    return ops.wvSplitK_int4_g(
        w_q, x_2d, w_s, cu_count, group_size, w_zp, bias
    )

if w_dequant is not None:
    return rocm_unquantized_gemm_impl(x_2d, w_dequant, bias)

return triton_w4a16_skinny_fmt_gemm(
    x_2d,
    w_q_i32,
    w_s,
    group_size,
    packed_scale_zp=packed_scale_zp,
)
```

当前 kernel 的合法性约束包括：

- ROCm `gfx11/gfx12`；
- activation 为 FP16 或 BF16；
- UINT4/UINT4B8 权重；
- group size 为 32、64 或 128；
- 不支持 `g_idx` reorder；
- `K` 必须同时满足 16 和 group size 的整除要求。

本次 CogAgent checkpoint 实际使用 BF16 activation、非对称 UINT4 与 group size 128。

## 5. 为什么 Prefill 需要单独调优

初始 W4A16 已显著改善 Decode，但 AWQ TTFT 相对 BF16 曾回退约 4.95%。原因不是 INT4 一定让
Prefill 变慢，而是通用 gfx11 BF16 tile 对 CogAgent 的若干真实 shape 不够合适。

调优覆盖的主要形状：

```text
language-expert token rows: M=22
vision-expert token rows:   M=257
完整 decoder / cross-attention query 与 output: M≈279
Decoder cross-attention K/V projection: M=6400

N,K:
12288,4096   QKV-like
4096,4096    output-like
22016,4096   gate/up-like
4096,11008   down-like
1024,4096    cross-attention query-like
4096,1024    cross-attention output-like
2048,1024    cross-attention K/V projection-like
```

调参变量为：

```text
BLOCK_M, BLOCK_N, BLOCK_K, num_warps
```

`BLOCK_K` 不能跨越 quant group，否则同一 tile 会错误复用 scale/zero point。

## 6. 调优方法与配置表边界

脚本为每个 shape 做 coarse search，再对前 5 个候选和 baseline 交错重复测量。packed weight 的
rotating buffer 以 512 MiB 为目标，并限制为 2～32 份；实际容量随 shape 变化。这样可以降低权重
常驻 cache 造成的虚假收益；最终还比较 tuned 与 baseline 输出：

```python
torch.testing.assert_close(
    tuned_output,
    baseline_output,
    rtol=0.03,
    atol=0.03,
)
```

配置没有按“CogAgent 模型名”硬编码，而是按 `(N, K, group_size)` 和工程设定的 `M` 区间匹配：

```python
_GFX1151_BF16_PREFILL_CONFIGS = {
    (12288, 4096, 128): (
        _W4A16PrefillConfig(192, 512, _W4A16TileConfig(64, 128, 64, 4)),
    ),
    (2048, 1024, 128): (
        _W4A16PrefillConfig(1024, 8192, _W4A16TileConfig(64, 256, 64, 8)),
    ),
}
```

未命中精确 `(N,K,group_size)` 或配置的 `M` 区间时，继续走原通用 fallback。当前归档 search
覆盖 11 个中心 shape；区间边界属于基于这些结果的工程外推，合入长期版本前仍应补邻近 `M` 回归。
相同 shape 的其他模型可以复用配置，同时避免按模型名 dispatch。

## 8. Prefill 调优的增量 E2E 证据

同一 AWQ 模型在调优前后执行 32 条请求：

| 指标（P50） | 调优前 AWQ | 调优后 AWQ | 变化 |
|---|---:|---:|---:|
| TTFT | 1239.21 ms | 1159.55 ms | **-6.43%** |
| TPOT | 27.51 ms/token | 27.53 ms/token | +0.09% |
| End-to-End | 2965.57 ms | 2883.19 ms | -2.78% |

32 条 greedy 输出与调优前 AWQ byte-for-byte 一致。TPOT 基本不变，直接说明这次配置表优化作用于
Prefill/TTFT，而不是 Decode。

还可以用另一个角度验证：

```text
未调优 AWQ vs BF16: TTFT +4.95%
最终 tuned AWQ vs BF16: TTFT -0.06%
```

所以合理结论是“Prefill 调优消除了 AWQ 的 TTFT 回退”。

## 9. 最终 BF16 对比如何归因

最终数据来自独立的 32-request rerun，因此与上一节增量验证的绝对毫秒值略有差异。

| 结果 | 主要来源 | 不能错误归因给 |
|---|---|---|
| TTFT 基本持平 | gfx1151 BF16 W4A16 Prefill tile 调优 | HIP skinny decode |
| Decode TPS 2.42× | INT4 权重流量下降 + 已有 HIP skinny decode kernel | 本次 Prefill 配置表 |
| E2E -44.94% | Decode 占请求主体时的综合收益 | 任意一个单独 microbenchmark |
| 模型显存 -50.87% | Decoder 权重从 BF16 压到 INT4，部分模块仍 BF16 | KV Cache 优化 |
| KV token 容量 +26.75% | 权重释放显存后，vLLM 可分配更多 KV Cache | KV dtype 改变 |

TPOT 的计算口径为：

$$
TPOT = \frac{E2E-TTFT}{output\_tokens-1}, \quad output\_tokens>1
$$

$$
Decode\ TPS = \frac{1000}{TPOT_{ms}}
$$

`completion_tokens <= 1` 的请求会被 TPOT/Decode 汇总排除。这里包含少量 HTTP streaming 与客户端
计时开销，不是纯 GPU kernel latency。

## 11. 证据边界

当前可以说：

- 在单卡 `gfx1151`、32 条 holdout、并发 1 的当前 workload 中，W4A16 Decode TPS 是 BF16 的
  2.42×，E2E P50 降低 44.94%；
- shape-aware Prefill 配置将同一 AWQ workload 的 TTFT P50 降低 6.43%，并消除了相对 BF16 的
  TTFT 回退；
- 调优前后 32 条 AWQ greedy 输出完全一致；源码已补齐 93-case kernel 测试矩阵，但本次复查因
  platform probe 未识别为 ROCm 而整模块显示 `1 skipped`，这次执行不能记为测试通过。
- 显存与 KV 容量数字来自已保存的结果 README；若要作为可独立复现的强证据，还应归档对应的
  BF16/W4A16 服务启动日志。

当前不能说：

- 所有 prompt 长度、batch size 和并发下都能获得 2.42×；
- Prefill tile 调优带来了 2.42× Decode 加速；
- microbenchmark 的 1.56× 可直接换算成请求 E2E 1.56×；
- P50 结果代表 P95/P99、吞吐饱和点或多用户稳定性；
- 32 条输出一致能替代更大规模任务质量评估；
- 32 条自然 EOS 的 BF16/W4A16 TPOT 与 E2E 是完全相同 decode 轨迹的纯性能对照。

## 12. 自测题

<details>
<summary>1. 为什么 Decode 适合 HIP skinny，而 Prefill 适合 Triton GEMM？</summary>

Decode 的 `M` 很小，更受权重读取和小矩阵利用率限制；HIP skinny kernel 针对这种形状。Prefill
的 `M` 更大，需要通过 `BLOCK_M/N/K` 和 workgroup 数提高计算与访存利用率。

</details>

<details>
<summary>2. 如何证明 Prefill 调优没有制造 Decode 加速？</summary>

同一 AWQ 模型调优前后 TPOT 为 27.51 与 27.53 ms/token，基本不变；变化集中在 TTFT
1239.21 -> 1159.55 ms。2.42× 是最终 W4A16 相对 BF16 的 Decode 对比，不是调优前后对比。

</details>

<details>
<summary>3. 为什么配置表要按 shape，而不是按模型名？</summary>

kernel 性能由 `M/N/K`、dtype、group size 和硬件决定。其他模型只要产生相同 shape 就可以复用；
按模型名判断既不通用，也会掩盖未测 shape 应回退通用配置的边界。

</details>
