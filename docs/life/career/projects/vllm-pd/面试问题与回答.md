## 一、完整介绍：从长 Prefill 干扰到同设备解耦 {#project-introduction}

长 Prefill 改变了混合批次的执行时间。项目把 P/D 的主机推进与设备提交拆开，同时共享权重和 KV；Chunked Prefill 控制工作量，同设备解耦改变执行组织，两者可以结合。

### 1. 请完整介绍一下你的 vLLM P/D 解耦与调度优化项目。 {#q1}

**背景与目标：长输入到来时保持生成稳定**

这个项目关注的是 **长输入请求到来时，怎样让已经在生成的请求继续稳定 Decode** 。在常规 vLLM 混合批次中，Scheduler 把 Prefill 和 Decode token 交给同一次模型执行。新请求的 Prompt 很长时，这轮计算会变重，已有请求下一次输出也要等这轮完成。

Chunked Prefill 能控制每轮加入的输入量，但两类工作仍在同一个执行节奏中；我的目标是进一步拆开这个节奏，同时保留同一设备上的权重和缓存容量优势。

**整体方案：独立 P/D，共享权重与 KV**

我采用 RAPID-Serve 的同设备解耦思路，在 **vLLM V1/MRV2 中实现独立的 P、D 进程** 。两侧分别准备输入、组批和提交模型执行，底层通过 GPU IPC 映射同一份模型权重与 KV。

上层仍由 D 侧统一维护请求和逻辑 KV 分配：新请求先获得 block 授权，再交给 P 处理；P 写完 Prompt KV、采样首 token 并发回完成消息后，D 才接手后续生成。

这样长请求 B 的 Prefill 尚未结束时，已有请求 A 的 Decode 可以沿自己的执行链推进，交接也不需要跨 GPU 池复制整份 Prompt KV。

**个人贡献：引擎接入、共享存储与执行协调**

**我个人主要完成了引擎接入、共享存储与请求生命周期、执行资源协调三部分工作** 。

引擎侧把协调器接到 EngineCore step，扩展 Scheduler 的可调度性与 P 授权，并通过 Executor 管理 P 进程和消息；运行侧适配 MRV2，让导入共享权重的 D 建立自己的私有状态，P 使用独立 token 预算，D 保留 Graph 和异步提交。

模型 forward 和主要 Attention kernel 沿用现有能力，我改的是这些组件如何被组织和协调。

**核心难点：最后一次 GPU 使用决定回收时机**

最难的部分是 **请求逻辑结束，不代表 GPU 已停止使用它的 KV** 。P 可能还在写，D 也可能有在途读取，取消消息还可能晚于 kernel 提交。

因此我用 P lease 和 D in-flight 引用保护 blocks，直到最后一次使用结束才回收；完成消息带 session/sequence，防止同名请求复用后接到旧结果。IPC 还要保留 storage 的别名、stride 和 offset，导出存储的进程必须活得足够久。

这些条件共同保证解耦后读到的仍是正确上下文。

**资源策略与当前范围**

执行分开后，两侧依然争用同一 GPU。我在 ROCm 上加入 **CU-masked stream 和在线资源策略** ，根据 P 的待处理工作、D 的生成负载及完成事件选择全 CU 共享或分区，并在切换时维持执行顺序。因此这个项目既有调度组织，也有共享内存生命周期和平台资源管理。

当前分支是单设备配对实现；传统多 P、多 D 资源池和 TP 多卡扩展是后续部署问题，需要另行处理映射与通信。

这套方案的第一个追问是[与传统分离的关系](#q2)，随后是[为什么 Chunked Prefill 还不够](#q3)；真正的工程难点落在[共享 KV 的交接与生命周期](#q12)。

### 2. 你的项目与传统 P/D 分离、RAPID-Serve 的关系是什么？ {#q2}

我采用的是 RAPID-Serve 的 **同设备 P/D 独立执行、共享权重与 KV** 的核心思路，并把它接入 vLLM V1/MRV2。

- 传统异设备分离侧重独立扩容和资源隔离，我的项目侧重同设备上的批次解耦与共享容量，交接时主要传控制信息，避免跨 GPU 池复制 Prompt KV。

- 具体适配包括 V1 的统一请求管理、MRV2 异步输出、分块或整段 P，以及在线 CU 策略。**当前代码实现的是单设备配对执行** ，多P/多D 的资源池部署属于传统分离的架构知识，扩展到多卡仍需要另外处理映射和通信。

### 3. vLLM 已经有 Chunked Prefill，为什么还要做 P/D 解耦？ {#q3}

Chunked Prefill 控制的是 **一轮混合批次中加入多少 Prefill token** ，可以限制长输入的阻塞时间，但 P/D 仍由同一次模型执行一起推进。

- 我的方案把两侧提交拆开，让请求 A 的 Decode 能在请求 B 的 Prefill 尚未结束时继续执行，P 也能使用独立预算。

- 两者可以结合：P 仍可以分块，只是不再和 D 拼成同一个执行批次。**解耦改变执行组织，chunking 改变单次工作量** ；同设备上的算力和带宽争用仍需要资源策略处理。

### 4. 为什么用两个进程，而不是两个线程或两个 stream？ {#q4}

**进程独立的是主机调度与运行状态，stream 独立的是设备提交队列** 。

- 只增加 stream，P/D 的 Python 调度、输入准备和 runner 状态仍可能串在同一主机路径中；两个线程还要处理 GIL 和共享状态。

- 独立进程让两侧各自推进这些工作，再用 IPC 协调。不过 PyTorch 底层运算可以释放 GIL，不能说线程完全不能并发。两个进程同样不自动保证 GPU 重叠，还需要合适的 stream、无多余同步，以及足够资源承载并发 kernel。

主机推进分开后，GPU 是否能同时承载两类 kernel，还要回到[两阶段的资源特点](#q5)和[CU 分区策略](#q23)。

### 5. 为什么 Prefill 通常偏计算受限，小 batch Decode 通常偏带宽受限？ {#q5}

看一个 Linear，Prefill 一次处理多行 token，**同一份权重能被多行输入复用** ，算术强度更高，也更容易使用高吞吐矩阵指令。

- 小 batch Decode 每轮只有少量 token，却仍要读各层权重，权重复用少；上下文增长后，历史 KV 读取也会成为明显成本。

- 因此两阶段可能需要不同的资源配置。不过这是常见倾向，**batch、矩阵 shape、上下文和模型结构都会改变瓶颈** ；大 batch Decode 可能更偏计算，短 Prefill 也可能受访存或提交开销限制。

## 二、个人贡献：让一个请求沿新的执行链推进 {#implementation}

请求仍由同一个 EngineCore 管理。新的协调器将上下文工作交给 P，生成工作交给 D；Scheduler 的授权、Executor 的进程消息和 MRV2 的本地输入状态，把这两个角色连接起来。

### 6. 你个人主要完成了哪些工程工作？ {#q6}

我的工作集中在调度、共享存储和执行协调三部分：

1. **引擎接入** ：将配对执行接入 EngineCore、Scheduler 和 Executor，让同一套上层请求状态驱动独立的 P/D。
2. **共享与生命周期** ：实现权重、KV 的 IPC 共享，用 P 租约、D 在途引用和迟到消息身份校验管理交接与回收。
3. **执行资源协调** ：适配 MRV2 的独立运行状态、P token 预算和 D Graph/异步输出，在 ROCm 上加入 CU-masked stream、资源控制器及事件切换。

模型 forward 和主要 Attention kernel 沿用现有路径。

### 7. V1、MRV2、Scheduler、Executor、Worker、ModelRunner 是什么关系？普通调用链怎么讲？ {#q7}

**V1 是引擎架构，MRV2 是第二版 GPU ModelRunner** ，二者处于不同层级。

| 组件 | 在请求执行中的职责 |
| --- | --- |
| EngineCore | 接收经 API 预处理和引擎客户端传入的请求，驱动执行与状态更新 |
| Scheduler | 决定哪些请求执行多少 token，管理逻辑 KV |
| Executor | 将执行任务交给 Worker |
| Worker | 管理设备上下文，调用 ModelRunner |
| ModelRunner / MRV2 | 将调度元数据转成 GPU 输入与 Attention metadata，运行模型、采样并返回结果 |

同步链路是 **接收请求 → 调度 → 执行/采样 → 更新输出** ，异步模式允许主机准备与设备执行交错。

```text
API / engine client → EngineCore → Scheduler.schedule()
  → Executor → Worker → GPUModelRunner → model / attention backend
  → execute / sample output → Scheduler.update_from_output()
```

普通同步 step 见 [EngineCore.step](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/engine/core.py#L678-L707)；数据形态可回看[请求变成 GPU 输入](../../../../vllm/基础篇/请求变成GPU输入.md)。

### 7.1. P/D 解耦中，P 和 D 分别持有 Scheduler 吗？ {#q7-scheduler-ownership}

**先区分部署方式，再回答自己的实现**

如果 P、D 是两个独立的 vLLM 引擎实例，通常各有 EngineCore、Scheduler 和 KVCacheManager；路由与 KV 传输连接两侧。我的同设备共享 KV 方案只有 **一份完整的 vLLM Scheduler，位于 D 侧 EngineCore** 。P 侧运行轻量的 `PrefillEngine`，负责已授权工作的组批与分块执行。

因此，**两侧独立组批和提交，不等于两侧各有完整 Scheduler** 。两侧 runner 的可变执行状态独立，共享 KV 池的逻辑所有权则统一管理。

**面试口述**

> 我的方案采用统一请求管理、两侧独立执行。完整的 Scheduler 在 D 侧，负责请求入场、共享 KV 的逻辑分配和生命周期，并向 P 授权 Prefill 工作。P 侧是 PrefillEngine，负责已授权任务的本地组批和分块，不持有独立的 KVCacheManager。这样 P、D 可以各自推进，同时避免两个分配器在同一个共享 KV 池里产生冲突。P 完成后，D 侧 Scheduler 校验完成消息并更新统一请求状态，再允许这个请求进入 Decode。

**组件位置与权限**

```text
D 侧 EngineCore
  ├─ DecodeScheduler / AsyncDecodeScheduler
  │    ├─ 全部请求状态、KVCacheManager、P lease、D in-flight
  │    └─ 授权 P 工作与调度 D 批次
  └─ PairedCoordinator / PairedExecutor
       ├─ 向 P 发送 PrefillWork，接收完成通知
       └─ 向 D Worker / MRV2 提交 Decode

P 独立进程
  └─ PrefillEngine → P Worker / MRV2
       ├─ waiting / pending、局部进度、取消与完成处理
       └─ 在已授权工作内，按 P 预算选择批次与 chunk
```

| 决策或状态 | D 侧 Scheduler | P 侧 PrefillEngine |
| --- | --- | --- |
| 新请求入场 | 决定是否接纳并获得执行资源 | 接收已授权任务 |
| KV blocks 分配与回收 | 统一管理 | 使用任务携带的 block IDs |
| Prefill 执行量 | 授权完整待处理上下文并保留空间 | 按本地 token budget、请求槽位与 chunk 配置选择本轮工作 |
| Decode 开始条件 | 收到并校验 P 完成消息，更新请求状态 | 确认全部工作完成后通知 D |
| 取消与生命周期 | 管理逻辑结束和安全回收 | 停止后续工作，等待在途执行收尾并清理本地状态 |

源码中 [`DecodeScheduler`](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/scheduler.py#L34-L45) 继承 `Scheduler`；开启异步时选择 `AsyncDecodeScheduler`，见[配置选择](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/engine.py#L22-L31)。P 进程由 [`run_prefill()`](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/process.py#L16-L51) 创建 Worker 和 `PrefillEngine`，后者明确不拥有 KV block manager，见[本地队列与配置](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/prefill.py#L34-L47)。
{.interview-source}

**用 40 Token 的 Prompt 说明授权与执行的区别**

D 先为请求 B 的完整待处理上下文保留 KV blocks，记录 lease，发送 40 Token 的 PrefillWork。若 P 本地预算为 16，它可按 `16 + 16 + 8` 推进；这不是每个 chunk 都向 D 重新申请 KV。

这期间 D 可以继续调度已在生成的请求 A。请求 B 因为仍有 P lease，被排除在 D 的可调度集合外。P 确认最后一个 chunk 完成后通知 D，D 校验 session/sequence、解除 lease 并更新首 Token 与请求状态；若仍需生成，B 才进入后续 Decode。

授权见[`grant_prefills()`](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/scheduler.py#L115-L159)，局部组批见[`PrefillEngine.step()`](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/prefill.py#L109-L156)，调度排除与交接见[eligibility](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/scheduler.py#L74-L86)、[`complete_prefill()`](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/scheduler.py#L176-L189)。
{.interview-source}

P 持有的 `scheduler_config` 用于配置 token budget 和 runner 容量，**有 SchedulerConfig 不等于创建了 Scheduler 实例** 。P 创建共享权重与 KV 的物理存储，也不代表它有请求块的分配权，继续见[物理创建与逻辑管理](#q10)。

### 9. 开启你的项目后，一个请求从到达到 P/D 执行的调用链是什么？ {#q9}

上层请求仍进入同一个 EngineCore，开启配置后，由 **`PairedCoordinator.step()`** 驱动：

1. **授权** ：`DecodeScheduler.grant_prefills()` 保留完整上下文的 KV blocks，`PairedExecutor.send_prefills()` 将任务发给 P。
2. **Prefill** ：P 的 `PrefillEngine` 组批，本地 Worker/MRV2 写入共享 KV，完成后返回首 token 和身份信息。
3. **交接** ：D 的 `complete_prefill()` 核对并更新统一请求状态，协调器为它安排 Decode。
4. **生成** ：D Worker 执行与采样，`complete_decode()` 更新输出。

**P/D 批次独立，逻辑请求与 KV 所有权统一** 。

```text
EngineCore.step_fn → PairedCoordinator.step
  ├─ grant_prefills → send_prefills → P process / PrefillEngine
  │    → P Worker / MRV2 → shared KV → prefill_done
  │    → poll_prefills → complete_prefill
  └─ schedule → D Worker.execute_model / sample_tokens
       → pending output → complete_decode
```

核心调用见[协调器](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/engine.py#L70-L248)、[P 授权](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/scheduler.py#L115-L159)、[P 执行](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/prefill.py#L69-L156)。

### 10. 启动时谁加载模型、谁创建 KV？为什么 D 仍能统一管理缓存？ {#q10}

**物理存储创建与逻辑 block 分配是两种职责** 。

| 对象 | P 侧 | D 侧 |
| --- | --- | --- |

### 11. P 和 D 为什么要使用不同的 token budget？预算和 runner 有什么关系？ {#q11}

解耦后，P 需要一次处理更多输入行以提高矩阵效率，D 则围绕活跃生成请求组织小步执行，因此 **P 的执行预算可以独立配置** 。

- Token budget 是一批 aggregate token 数，不是请求数量；它还影响 MRV2 输入 buffer 的容量，不能只扩大 Scheduler 预算而不改变 runner 尺寸。

- 另外，D 授权时预留的是完整待重建上下文的 KV 空间，P 真正执行时再按自己的预算分块或整段处理。**缓存保留范围和一次执行量是两种约束** 。

### 11.1 开启 Chunked Prefill 好，还是不开启好？你的项目如何选择？ {#q11-chunk-choice}

**面试口述** ：我会区分普通混合调度和同设备 P/D 解耦。普通混合调度下，长 Prefill 会拖长整轮执行，分块通常有助于控制已有 Decode 请求的等待；在我的双进程方案里，D 已能独立提交，分块仍能控制 P 单次工作量和 activation 峰值，但不是 D 继续执行的必要条件。整段 P 减少重复提交与输入准备，可能提高 P 效率，却需要更大的执行预算，也可能增加同设备争用。因此我支持两种模式，结合 TTFT、P95 ITL、吞吐和显存选择；已有同预算实验没有证明某一种稳定更好。

| 取舍 | 开启分块 P | 关闭分块，整段 P |
| --- | --- | --- |
| 本次输入范围 | 请求剩余上下文可以按本批剩余预算推进 | 一个请求的剩余 Prefill 必须完整放入本批 |
| P 的执行成本 | 更多输入准备、kernel 提交和历史 KV 读取，较小矩阵的效率可能下降 | 减少分块轮次，较大 GEMM 可能更高效；短输入不一定有明显差别 |
| 单次资源占用 | 控制输入规模，通常有利于压低 activation / workspace 峰值 | 需容纳较长输入，峰值与单次资源占用可能更大 |
| 对 D 的影响 | 普通混合调度可限制每轮阻塞；本项目中主要改变资源竞争粒度 | 本项目 D 仍独立推进，但 P/D 继续争用算力、缓存和带宽 |
| 入场与公平性 | 可利用剩余 token 预算，但是否优先短请求取决于调度实现 | 队首长请求放不下时可能留下空预算、延后短请求 |

**当前分支的具体行为** ：`rapidserve_chunked_prefill` 默认开启，`rapidserve_prefill_max_num_batched_tokens` 决定 P 的 aggregate token budget。关闭分块时，默认预算至少覆盖 `max_model_len`，显式预算必须通过长度校验。整段不等于每批只有一个请求；多个请求只要都能完整放下，仍可合批。

例如 P budget=6144，先装入 3072 tokens 后只剩 3072；队首下一个请求需要 4096 tokens。开启分块可先推进它的 3072，余下 1024 留到后续批次；关闭分块则把整个请求放回队首，结束本批。当前代码不会绕过它搜索后面的短请求。分块模式也会将未完成请求放回队首，不能据此宣称已实现短请求优先或完全公平。

**同预算的已有证据** ：本地 Radeon 8060S、Qwen3-30B-A3B BF16、单设备、Triton MoE、B16、KV8 GiB、两侧全 CU，8 个短请求开始生成后再加入 8 个长请求，输入为 1024/4096 tokens、输出固定 64 tokens。分块/整段各测两轮；下面仅比较 paired 内相同 P budget 的两个模式。

| P budget | 分块输出 tok/s | 整段输出 tok/s | 整段相对分块 |
| ---:| ---:| ---:| ---:|
| 6144 | 32.32 | 31.97 | 约 -1.1% |
| 12288 | 33.73 | 34.28 | 约 +1.6% |

两组方向不同、轮数有限，不能说整段总是更好。P12288 下，分块/整段的新请求平均 TTFT 为 15.30/15.82 s，初始请求 P95 ITL 为 201.5/202.2 ms，也应一起判断。Qwen3-0.6B 的分块 P2048 与整段 P8192 同时改变了预算，不能拿那组结果单独归因于 chunking 开关。

实际选择时，长短输入混合、显存峰值或生成尾延迟敏感，可以先保留分块并调 P budget；低并发、输入较整齐、资源足够且更关注 P 效率，可比较整段。两种模式都按同一套[请求完成协议](#q14-chunk-ready)交接；chunk 越小不保证 TTFT 越低，也不会免去请求最终需要的 causal attention 计算。

## 三、共享 KV：交接、取消与回收是一条生命周期 {#kv-lifecycle}

以前同一个 runner 内隐含的执行顺序，拆进程后必须显式表达。首 token 的回传、Prompt KV 的完成、block 的最后一次使用分别发生在不同时间点，取消和迟到消息也不能改变这条生命周期。

### 12. 一个请求怎样在共享 KV 中完成交接？首个输出 token 由谁产生？ {#q12}

以 **40 个 Prompt token、block size 16** 的请求 B 为例：

1. **D 分配** ：保留 3 个逻辑 block 对应的物理块，将 token history、已计算长度和 block IDs 发给 P。
2. **P 建立上下文** ：可以分三次处理输入，在最后一次执行后采样首个输出 token。
3. **P/D 交接** ：P 等 KV 写入和输出回拷完成后通知；D 核对身份，更新请求状态并交付首 token。
4. **D 继续生成** ：首次执行消费这个首 token，写入它的 KV，再采样第二个输出。

**首 token 已采样，不代表它自己的 KV 已写入** 。只要求一个输出 token 的请求，可以在 P 完成后结束。

分步例子见[请求交接](02-V1-MRV2实现与设计取舍.md#request-handoff)。
{.interview-source}

这段交接成立的前提是[写入先于读取、最后一次使用先于回收](#q15)；取消请求会进一步检验这些条件。

### 13. block_table、slot_mapping 和 KVCacheBlock 分别是什么？为什么不能直接跨进程传对象？ {#q13}

| 对象 | 描述什么 | 谁使用 |
| --- | --- | --- |
| `block_table` | 逻辑历史页到物理 KV block 的映射 | Attention 读取历史 KV |
| `slot_mapping` | 本次新 K/V 的写入槽位 | KV 写入路径 |
| `KVCacheBlock` | block ID、引用等逻辑管理信息 | 缓存管理器 |

真实 K/V 存在 GPU tensor 中。以 block size 16、逻辑第三块映射物理 block 19 为例，逻辑位置 34 在简化布局下对应 slot `19×16+2`。

跨进程要共享 tensor 存储、传 block IDs，再由各自 runner 构造本地输入。复制 Python 对象无法建立 GPU 内存共享；两侧 request slot 也可能不同，**本地行号不能充当跨进程请求身份** 。

### 14. GPU IPC 为什么能避免交接时传输整份 KV？还需要注意哪些布局信息？ {#q14}

GPU IPC 让 D 导入 P 持有的 **同一份物理存储** ，交接时主要传 handle、视图描述和完成信息。

- P 写完后，D 就能读这份 KV，无需把它复制到另一个 GPU 池。我的 manifest 按 storage 去重，并保留 **dtype、shape、stride、offset 和设备身份** ，这样才能还原切片与共享权重别名。

- 两进程虚拟地址可以不同；共享也没有省掉 Attention 读取 KV 的访存。权重之外的可变 buffer、activation 和 Graph 状态仍要按执行上下文分别管理。

视图导出导入见 [TensorViews](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/ipc.py#L20-L87)。

### 14.1 GPU IPC 如何管理权重内存地址？P、D 的地址要一样吗？ {#q14-weight-address}

**面试口述** ：P 加载并持有模型权重，按底层 storage 去重，导出 IPC handle 和 tensor 的 dtype、shape、stride、offset。D 通过 handle 建立本进程的显存映射，再重建 tensor view，挂到 meta model 上，避免加载第二份权重。P/D 的虚拟地址不要求一样，它们访问同一份物理存储；映射和 owner 引用还要在 GPU 使用期间保持有效。

项目导出调用 `storage._share_cuda_()`，导入调用 `torch.UntypedStorage._new_shared_cuda(*args)`。这是 PyTorch 的 GPU IPC 封装，ROCm 也沿用 `torch.cuda` 接口名。以传统 CUDA IPC API 解释底层原理，就是 P 通过 `cudaIpcGetMemHandle` 导出显存分配，D 通过 `cudaIpcOpenMemHandle` 获得本地映射基址；实际调用与 allocator 路径由 PyTorch/运行时处理。

**裸指针和 handle 的用途不同** ：P 的 `data_ptr()` 是 P 地址空间中的指针，不能直接作为 D 的可用指针。项目用 `storage._cdata` 在 P 内识别 storage，跨进程传的是共享元数据；UVA 不会自动建立另一个进程的映射。D 导入时还校验 GPU UUID，不能只根据本地 `cuda:0` 判断是同一张物理卡。

需要区分三个对象：

| 对象 | 与寻址有关的信息 |
| --- | --- |
| 底层 GPU allocation | handle 标识共享分配；D 导入后取得自己的映射基址 |
| Storage | 可能是 allocator 大分配中的一段，需要 allocation 内的字节偏移和 storage 大小 |
| Tensor view | storage index、dtype、shape、stride，以及按元素计的 `storage_offset()` |

PyTorch caching allocator 可能让多个 storage 位于同一块大 allocation。传统 CUDA IPC 映射该底层 allocation，并在接收端恢复所需 storage 范围；映射范围较大不代表复制整块数据。首元素地址可理解为：

```text
D tensor 首地址 = D allocation 映射基址
                 + storage 在 allocation 内的字节偏移
                 + tensor.storage_offset() × element_size

示例：BF16，每元素 2 byte
P allocation 基址 = 0xA000，D allocation 基址 = 0xB000
storage 字节偏移 = 0x100，tensor 元素偏移 = 16
P tensor 首地址 = 0xA000 + 0x100 + 16×2 = 0xA120
D tensor 首地址 = 0xB000 + 0x100 + 16×2 = 0xB120
```

这是地址映射示意，两边数值不同但对应同一存储位置。非连续 tensor 的后续元素还要按 stride 寻址。项目通过 `tensor.set_(imported_storage, offset, shape, stride)` 还原 view；相同 storage 的不同 view 保留别名，完全相同的参数 view 在 D 中复用 Parameter 对象。

**存储生命周期** ：P 的 `_owners` 保留导出 storage 的引用，序列化时不传这些 owner 对象；PyTorch IPC 层负责相关共享引用与映射管理。D 在 meta device 建模型并替换参数，可变 buffers 则按项目设计 clone。当前不支持 reload/update weights 或重新分配共享权重，正常退出先清理 D 的导入引用，再关闭 P。双方按只读方式使用权重，这是执行约定，IPC handle 本身不提供“禁止写入”的保证。

**Graph 追问** ：D 在导入后建立本地执行状态、预热并捕获 Graph；Graph 引用的是 D 的本地地址，replay 期间映射与 buffer 地址要稳定，不要求 P 的地址与 D 相等。共享参数也不会自动共享两进程的 Graph 或 workspace。

源码依据：[storage 去重与元数据导出](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/ipc.py#L40-L69)、[UUID 校验与 view 重建](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/ipc.py#L71-L87)、[meta model 挂接](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/ipc.py#L161-L205)、[退出顺序](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/executor.py#L253-L281)。

### 14.2 D 如何知道 P 已完成计算，什么时候可以读取共享 KV？ {#q14-prefill-ready}

**面试口述** ：P 提交模型执行和采样后，在执行 stream 上记录 GPU event，把本批任务、异步输出和 event 放进 pending 队列。P 主循环查询执行 event 和输出 copy event，确认 KV 写入完成、CPU 可读取结果，再通过 Pipe 发送 `prefill_done`。D 收到后匹配 req_id、session、sequence，解除 P lease 并更新请求状态，再允许这个请求进入 Decode。其他已经就绪的请求可以继续生成。

**CPU 提交返回不等于 GPU 执行结束** 。`execute_model()` / `sample_tokens()` 返回后，GPU 仍可能执行；成功建立共享映射也不能证明 KV 已写好。这里用事件确认，而不是从“函数返回”或“能访问内存”推断完成。

```python
# PrefillEngine.step：提交后记录当前执行 stream 的事件
self.worker.execute_model(batch)
output = self.worker.sample_tokens(None)
event = torch.cuda.Event()
event.record()
self.pending.append((selected, output, event))
```

随后查询 pending 队首的 `event.query()` 和 `output.copy_event.query()`。`query()` 不等待 GPU 完成；尚未 ready 就保留任务，继续主循环。两者分别保证：

| 条件 | 保证的边界 |
| --- | --- |
| 执行 event 完成 | 该 stream 中事件之前的 GPU 工作及其依赖已完成，相关 KV 写入结束 |
| 输出 copy event 完成 | 采样结果回拷完成，CPU 可安全取回并发送结果 |
| 正常请求全部 P 工作完成 | 可以交接这个请求；单个 chunk ready 的处理见下一问 |

事件必须记录在相关计算之后。当前 Worker 将角色 stream 设为 current stream / runner main stream；若另用计算 stream，也必须建立相应依赖。一个 event 不会自动覆盖所有 stream，copy event 也不应单独当作所有 KV 写入完成的证明。

P 的 `finish()` 发送 `("prefill_done", (work.identity, result))`，D 协调器通过 `poll_prefills()` 收取，再调用 `complete_prefill()`。D 查当前 lease 并匹配 session/sequence，匹配才解除 lease、更新 computed tokens 与首 token；请求仍有效且需要继续生成时，才成为 D 可调度请求。通知若对应取消工作，只用于清理确认；只需一个输出 token 的请求可直接结束。

```text
P 写共享 KV → P 执行 event / 输出 copy event ready
  → 正常请求全部 P 工作完成 → Pipe 发送 prefill_done
  → D 接收并匹配当前 lease → 更新请求状态
  → D 提交后续 Decode → 读取共享 KV
```

**跨进程 event 追问** ：当前由 P 本地查询 event，D 接收经过完成确认的 CPU 消息，普通交接没有全设备同步。另一种设计可以导出 IPC event，让 D 导入并执行 stream wait；那需要事件生命周期和每次工作的关联协议，不是当前实现。启动时 storage IPC 内部的同步信息也不能替代每个请求后续 KV 写入的完成协议。

源码依据：[提交与记录 event](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/prefill.py#L150-L156)、[查询完成与发送通知](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/prefill.py#L69-L108)、[D 收取通知](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/engine.py#L70-L93)、[D 匹配 lease](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/scheduler.py#L176-L189)。
{.interview-source}

### 14.3 开启 Chunked Prefill 后，D 如何知道所有 chunk 都完成了？ {#q14-chunk-ready}

**面试口述** ：GPU event 标记本次 batch 的执行完成，整个请求完成则由 P 的累计 token 进度判断。P 每次记录该请求处理到的位置，event 和 copy event ready 后，如果仍小于本次授权的 `work.num_tokens`，就放回 waiting 继续处理；达到全部工作量才发送正常 `prefill_done`。D 不逐个统计 chunk，而是持有该请求的 P lease，等最终通知并验证身份后才允许 Decode。

组批时，P 保存的是 `(work, computed + count)`。`computed` 是这次授权中已经完成的相对进度，`count` 是本批推进量；实际模型的输入位置从 `work.request.num_computed_tokens + computed` 继续，不能每个 chunk 都从位置 0 开始。

```python
# event 和 copy_event 均 ready 后，按请求检查累计完成量
for work, count in selected:
    if work.sequence in self.cancelled:
        self.finish(work, EMPTY_MODEL_RUNNER_OUTPUT)
        continue
    if count < work.num_tokens:
        self.waiting.appendleft((work, count))
        continue
    # 提取该请求的最终采样结果，再 finish() 发 prefill_done
```

沿用 40-token Prompt、P budget=16 的例子，忽略真实最小配置限制：

| P 批次 | 本次 Prompt 位置 | 累计完成量 | event / copy event ready 后 |
| --- | --- | ---:| --- |
| 第 1 次 | 0–15 | 16/40 | 放回 P waiting，D 保留 lease，尚不交接 |
| 第 2 次 | 16–31 | 32/40 | 放回 P waiting，D 保留 lease，尚不交接 |
| 第 3 次 | 32–39 | 40/40 | 返回最终首 token，发送 prefill_done，D 验证并更新 |

**中间 chunk 不发正常完成通知，也不把中间采样结果交给用户** 。D 此时可以执行其他请求的 Decode，但不能提前生成这条未完成 Prompt 的请求。完整 Prompt 的首个输出依赖全部上下文；本项目也没有让同一请求的 P chunk 与其 D 自回归生成同时执行。

事件按实际 batch 记录，进度按请求记录。如果同一 batch 中短请求 A 已全部完成、长请求 B 只完成一部分，在该 batch ready 后，P 可分别通知 A 并把 B 放回 waiting。D 不必等整个 P 队列清空，A 就能进入 Decode。

**lease 贯穿全部 chunks** ：D 的 `_is_request_eligible()` 排除正在持有 P lease 的请求，不能在第一个 chunk 完成时就释放其 blocks。取消未提交工作可以直接确认；取消在途 chunk 要先等事件完成，再丢弃结果并通知，D 最后检查 P lease 与 D in-flight 后回收。迟到通知仍由 session/sequence 过滤。

源码依据：[累计进度与输入位置](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/prefill.py#L133-L156)、[逐请求完成 / 重新排队](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/prefill.py#L80-L108)、[有 lease 时排除 D 调度](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/scheduler.py#L74-L86)。是否采用分块见[开关与性能取舍](#q11-chunk-choice)。

### 15. 两个进程共享 KV，怎样避免读写冲突和提前回收？ {#q15}

保护分为分配、执行依赖和最后一次使用三个层次：

1. **唯一分配** ：D 给不同请求分配各自 blocks，同一请求在 P 完成后才允许 D 读取。
2. **在途保护** ：P 使用 blocks 时记录 lease，D 提交 GPU 工作时记录 in-flight 引用；任一引用存在都不能回收。
3. **延迟回收** ：请求逻辑结束但仍有引用时，进入 retired 状态，继续占用容量，直到最后一次使用结束。

这样 A 的 D 与 B 的 P 可以并行，而 B 尚未写完的块不会被分给 C。**共享 handle、执行依赖和引用保护分别解决不同问题** 。

### 16. 请求取消时为什么不能马上释放 KV？P 进程退出又有什么影响？ {#q16}

删除请求或发取消消息，**不会立即停止已经提交的 GPU kernel** 。

- 若 P 还在写旧 block，D 立即复用就可能破坏新请求；D 的在途读取也需要保护。因此先停止后续工作与输出交付，P 未提交的工作可以清理，在途工作等完成再确认，D 等 P lease 和自身引用都结束才回收。

- 物理存储还依赖 producer 存活，正常退出要 **先销毁 D 的导入引用，再关闭 P** ，避免持有真实分配的进程提前退出。

### 17. 完成消息中为什么除了 req_id，还要有 session 和 sequence？ {#q17}

| 身份字段 | 用途 |
| --- | --- |
| `req_id` | 业务请求名，旧请求退出后可能被复用 |
| session | 区分一次调度会话 |
| sequence | 区分具体工作的代次 |

D 只接受与当前 lease 匹配的完成。若只按 req_id 匹配，旧工作的迟到结果可能被应用到同名新请求。

P/D 的本地 request slot 也会复用，无法代替稳定身份。这组字段用于区分重复通知、取消后的迟到消息和新请求，防止错误更新 token、解除租约或释放 KV。

### 18. KV 不足发生抢占后，为什么不能只重新计算最初的 Prompt？ {#q18}

抢占释放的是已有上下文的 KV，而上下文可能包含 **原始 Prompt 和已经生成的历史 token** 。

- 恢复时，模型需要重新构建当前输入之前的完整历史；只重算 Prompt 就会让 D 读取缺失的生成历史 KV。我的 `needs_prefill()` 根据已计算长度与当前 token history 判断是否还需 P，授权时传完整历史和 computed offset，再交给 P 重建。

- 最后一个已采样 token 通常留给下一次执行作为输入，所以 **token 历史长度和已建立 KV 的长度需要分别理解** 。

### 19. 为什么进程消息也要做背压？直接用 Pipe 发送会有什么问题？ {#q19}

若 P 来不及接收，**同步 Pipe 写入可能阻塞协调器，让 D 也停止提交** ，重新引入主机侧耦合。

- 我用有界发送队列和 sender thread，把实际 Pipe 写移出 D 正常推进路径；协调器通过 `can_send()` 控制新 P 授权。

- 同时 P 的 pending 深度和 resident 请求数限制批次与 runner 槽位使用。消息条数上限不能代替 token、KV 或请求容量限制，因此 **通信背压与计算、存储 admission 要共同工作** 。

消息队列见 [prefill_rpc / can_send](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/executor.py#L122-L147)。

## 四、持续 Decode：异步提交、输出 ready 与资源切换 {#execution}

共享 KV 解决数据交接，异步调度减少主机等待，Graph 减少反复提交，CU 策略处理同设备资源争用。这几种机制各有依赖条件，需要共同保持 Decode 连续推进。

### 20. 异步调度怎样提前准备下一轮？它违反自回归依赖吗？ {#q20}

自回归依赖仍然成立，下一轮必须使用上一轮真实采样结果。

- 异步调度提前准备的是 **请求位置、批次元数据和执行空间** ，CPU 可以用 output placeholder 表示尚待返回的位置；MRV2 在 GPU 上更新 `last_sampled_tokens`，后续输入准备按 stream 顺序读取真实设备结果。

- 这样 CPU 不必等 token 回拷后才做所有准备。Placeholder 不是猜测的 token ID，也不是有效 KV；请求结束时，已在途的额外工作仍要收尾，并避免把多余输出交给用户。

CPU 可以提前准备不代表 CPU 输出已经 ready：[执行 event 与 copy event](#q21)决定何时能更新请求状态。

### 21. GPU 执行完成 event 和输出 copy event 为什么要分别检查？ {#q21}

**执行完成和 CPU 输出 ready 是两个条件** 。

| 完成事件 | 能说明什么 | 不能据此推断什么 |
| --- | --- | --- |
| 主 stream 的执行 event | 相关模型/GPU 工作完成 | copy stream 已把 token 回拷到 CPU |
| 输出 copy event | CPU 输出数组已可读 | 可以忽略 KV 写入与主执行依赖 |

MRV2 可以在独立 copy stream 上异步回拷采样结果。P 交接既要 KV 写完，也要取得首 token；D 更新状态同样要等相关执行和输出 ready。

协调器先用 `query()` 检查两个 event，ready 后再取输出，减少主动阻塞。Event 表达具体依赖，比每次交接做全设备同步更精细。

### 22. CUDA/HIP Graph、torch.compile 和异步调度分别解决什么？你的项目怎么使用它们？ {#q22}

| 机制 | 主要解决的成本 |
| --- | --- |
| `torch.compile` | 算子或计算图的执行与融合 |
| CUDA/HIP Graph | 重复提交 kernel 的主机开销 |
| 异步调度 | 主机准备等待设备工作的时间 |

三者可以组合。当前 **P 使用 eager 与 pending 队列，D 保留 MRV2 Decode Graph 和异步输出** 。

Graph 要求稳定的执行结构、地址和支持的 shape，输入内容可以在固定 buffer 更新。拆 P/D 时仍需保留各自 runner 状态；若全局强制 eager，D 原有的提交优化也会丢失。

### 23. CU Mask 是什么？P/D 各分一半 CU 就能完全隔离吗？ {#q23}

CU Mask 限定一个 HIP stream/queue 的 workgroup **可以调度到哪些计算单元** ，可以让 P/D 使用互补 CU 集合，不必修改每个 kernel。

- 它主要控制计算资源上的竞争，但两侧仍共享内存带宽、缓存等资源，已提交 kernel 也不会被强制抢占。P/D 都允许全 CU 时，是两侧都具备使用权限，实际资源由硬件调度；固定分区则可能在一侧空闲时浪费资源。

- 因此 **全 CU 共享与分区是按负载选择的策略** ，不是越固定越好。

### 24. 你的自动资源调度观察什么，怎样避免频繁切换？ {#q24}

控制器的决策顺序是：

1. **建立基线** ：从全 CU 开始，按 D batch 大小分桶，用 EWMA 平滑 GPU 步时间。
2. **试探分区** ：P/D 持续重叠、D 负载达到条件且已有基线样本时，试一个配置好的分区。
3. **避免抖动** ：结合进入持续时间、保持时间和失败记录限制频繁切换。
4. **回退** ：分区后 D 明显变慢就回退；只有一侧活跃时恢复全 CU。

观察量是 **GPU 步时间** ，作为生成延迟的内部代理。它并非直接测客户端 ITL，也没有遍历所有分区比例求最优。

策略见 [ResourceController](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/resources.py#L60-L138)。
{.interview-source}

策略选择之后还要回答[切换 stream 与 Graph 怎样保持原有执行顺序](#q25)，否则新的 mask 本身不能保证正确性。

### 25. 切换 CU Mask 时怎样保持执行顺序？Graph 要重新捕获吗？ {#q25}

自动模式在启动时 **预热各策略对应的 stream 和 D Graph** ，运行时选择现成资源。

- 切换时在旧 stream 记录 event，让新 stream 等待该 event，再切换 runner 的 main stream 和 Graph manager；这样后续批次保持本角色顺序，主机不用等整个设备排空，也不用现场捕获新 Graph。

- P/D 各在自己的顺序点生效，并非瞬间原子切换。还要确保 HIP Graph 的执行队列遵循 CU 配置，**创建了 masked stream 不代表 Graph 内部执行一定继承 mask** 。

事件切换见 [advance_resource_policy](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/worker.py#L96-L132)。

## 五、延伸到传统部署：容量、实例比例与多卡边界 {#deployment}

同设备配对主要处理执行干扰与容量共享，异设备分离还要处理独立扩容和 KV 搬运。两侧输入输出压力与 KV 驻留成本决定部署比例，多卡并行又增加了分片、拓扑和通信约束。

### 26. 传统 P/D 分离是什么，主要解决什么场景下的问题？ {#q26}

传统 P/D 分离把 Prefill 和 Decode 放到 **独立服务实例与不同 GPU 资源池** 中执行。

- P 负责处理 Prompt 并产生 KV，D 接收对应上下文后持续生成。它主要面向 **长短 Prompt 混合、并发生成和两阶段容量需求不均** 的在线服务：长 Prefill 会干扰已有请求的生成间隔，分离后可以分别调整 P 的首 token 延迟和 D 的生成延迟，还能独立扩容、选择硬件与并行配置。

**业务例子：企业知识助手同时服务文档问答和流式对话**

- 请求 A 已经在逐字生成回答，请求 B 此时提交一份长技术文档。混合执行时，B 的长 Prefill 可能让 A 的下一次输出变慢，用户看到的就是生成中途停顿。
- 分离后，B 的上下文处理在 P 池排队，A 在 D 池继续生成；两池还可以分别按首 token 等待和生成阶段压力扩容。

这里要解决的是 **新输入的重计算干扰已有请求的持续生成** 。如果业务流量很低、单实例已能满足延迟要求，分离增加的成本未必值得。

- 代价是两侧模型副本、KV 传输和跨实例路由，因此部署比例要结合输入输出长度分布与资源需求选择。

### 27. KV Cache 大小怎样估算？为什么它会影响传统 P/D 的部署比例？ {#q27}

普通 Attention 的单请求 KV 载荷可估为：

`KV 字节数 ≈ 2 × 层数 × 缓存 token 数 × KV heads × head dim × 每元素字节数`

- **2** ：分别对应 K 和 V。
- **GQA** ：使用 KV heads，不能替换成 Query heads。
- **TP** ：按当前设备的实际 KV 分片计算。

D 长期保留多个活跃请求，长输出还会增加上下文，所以可能先受显存容量约束，而 P 已处理完当前输入。

例如合同审查只生成一小段结论，但输入合同很长，D 在回答期间仍要保留整份合同的 KV。**短输出不等于 D 显存压力小** ；如果许多长文档同时完成 Prefill，D 也可能因接不下这些上下文而成为瓶颈。

估算并发需扣除权重、workspace、Graph 和 block 尾部浪费。MLA、滑窗或混合模型则按 **实际 cache spec** 计算。

### 28. 1P/1D 中的 P、D 是 GPU 数量吗？这种部署适合什么情况？ {#q28}

这里的 P、D 通常指 **Prefill 和 Decode 服务实例或副本的数量** ，一个实例内部还可以使用 TP/PP 占用多张 GPU。

1P/1D 是一组 P 对接一组 D，每个请求先在 P 处理输入，再把 KV 交给 D。

**业务例子：规模有限、负载较稳定的内部知识问答服务**

- **请求特点** ：每次检索固定数量的知识片段，生成几段解释；仍有长短请求混合和流式交互，但并发在可控范围内。
- **为什么可以 1P/1D** ：经过容量评估，一个 P 能及时处理输入，一个 D 能承载活跃回答；先用明确的配对关系隔离输入处理与持续生成，路由和运维也较简单。
- **扩容信号** ：如果 P 排队持续增加而 D 仍有余量，考虑增加 P；如果活跃生成不断积压、D 的 KV 或执行容量先满，考虑增加 D。

它适合作为分离部署的起点，但 **实例数量相同不代表容量匹配** 。这个例子成立的前提是两侧都能覆盖目标负载，不能仅凭业务叫“问答”就决定 1P/1D。

### 29. 多P/1D 主要适合什么负载，会遇到什么瓶颈？ {#q29}

多P/1D 适合 **输入较长、Prefill 压力较大，而输出较短或单个 D 尚有容量** 的情况。

**业务例子：长合同的信息抽取与分类接口**

- **请求特点** ：用户集中上传不同合同，输入包含整份正文，输出只是少量字段组成的 JSON 或一个分类标签。新文档较多、共享前缀命中有限，Prefill 工作难以大量复用。
- **为什么增加 P** ：长输入处理容易排队，多个 P 同时处理不同合同；输出较短，D 为每个请求持续执行的轮数较少，单个 D 在容量足够时可以汇聚这些结果。
- **需要检查什么** ：短输出仍可能对应很大的 Prompt KV，要同时核对 D 的驻留容量、接收带宽和生成负载。若 D 接不下，就需要增加 D 或限制 P 授权，不能继续只加 P。

这里扩大的是 **不同请求的 Prefill 服务容量** ，不会自动把一份合同拆给多个 P。主要风险是 P 完成速度超过 D 接纳能力，形成大量已算好却无法进入生成的上下文。

### 30. 1P/多D 主要适合什么负载，一个请求会同时交给多个 D 吗？ {#q30}

1P/多D 更适合 **输出较长、活跃生成请求多，Decode 容量或 KV 显存成为主要约束** 的情况。

**业务例子：根据简短提纲生成长文章的写作服务**

- **请求特点** ：输入是短指令或提纲，输出是一篇长文章；新请求还在不断到来，前面的文章尚未生成完，活跃请求逐渐累积。
- **为什么增加 D** ：P 每个请求只处理较少输入，有机会及时完成；D 则要连续执行很多轮并长期持有上下文。多个 D 分摊不同文章的生成负载和 KV 驻留。
- **请求怎样分配** ：P 完成后，路由器选一个有余量的 D，后续保持归属。D 的选择考虑 KV 容量、生成负载和传输拓扑。

**增加 D 副本让更多文章同时生成，不会让同一篇文章的自回归 token 自动并行生成** 。若输入变成长材料或到达率高到 P 也排队，单纯增加 D 无法解决首 token 等待。

### 31. 多P/多D 怎样组织，为什么比简单轮询更复杂？ {#q31}

多P/多D 把两侧都做成可独立扩容的资源池，适合 **大规模服务和输入输出长度分布变化明显** 的负载。

**业务例子：同时提供文档抽取、RAG 问答和代码生成的企业模型平台**

- **请求特点** ：文档抽取可能长输入、短输出；代码生成可能带大量仓库上下文，又要输出长代码；普通问答还混在其中，各时段的流量比例也不同。
- **为什么两侧都扩容** ：长输入业务增多时 P 压力上升，长输出和活跃会话增多时 D 压力上升，两池需要独立调整容量。业务之间输入输出形态差异大，固定配对容易一侧排队、另一侧闲置。
- **为什么不能轮询就够了** ：两个请求的计算与驻留成本可能相差很大；只数请求条数，可能把多个长文档压到同一个 P，或把多个长输出压到 KV 已紧张的 D。

路由应结合 **P 排队工作量、D 活跃生成与 KV 容量、缓存命中和传输距离** ，建立配对交接并做背压。通常一个请求由选定 P 处理输入，再交给选定 D 持续生成；故障迁移另需协议。

四种部署的业务判断可以这样对应：

| 部署方式 | 业务例子 | 选择依据 |
| --- | --- | --- |
| [1P/1D](#q28) | 负载可控的内部知识问答 | 一个 P 与一个 D 都能覆盖目标容量 |
| [多P/1D](#q29) | 不同长合同 → 少量 JSON 字段 | P 处理输入先排队，D 仍有执行和 KV 余量 |
| [1P/多D](#q30) | 简短提纲 → 长文章 | P 能及时处理，长时间生成让 D 活跃请求积压 |
| [多P/多D](#q31) | 文档抽取、RAG、代码生成混合平台 | 两阶段都有规模压力，负载比例随业务变化 |

这些是 **解释容量选择的业务例子** 。实际比例仍要结合模型、硬件、到达率、输入输出长度、缓存命中和延迟目标确定。

### 32. P/D 实例数量和 TP、PP、DP 是什么关系？多卡扩展只需多启动几个进程吗？ {#q32}

**P/D 数量描述服务角色的副本数，TP/PP 描述一个实例内部怎样并行模型** ；DP 通常描述请求在多个副本间分配。

- 一个 P 实例可以使用多卡 TP，一个 D 实例也可以采用自己的并行配置，因此 1P/1D 可以占用多张 GPU。传统分离若两侧分片不同，还要在 KV 传输时匹配布局。

- 我的配对实现当前是 TP1/DP1，扩展时必须建立各 rank 的共享映射，协调 **collective 顺序、所有 rank 的完成与故障** ，不能只复制当前单设备进程。

### 33. 传统 vLLM P/D 分离的 KV Connector 与你项目的 IPC 路径有什么区别？ {#q33}

传统分离中，P/D 各有自己的 KV 池，**Scheduler 侧 Connector 规划恢复、分配和生命周期，Worker 侧 Connector 负责实际数据传输** ；外部路由器传控制参数，GPU KV 字节走数据通路。

- 例如 NIXL pull 由 D 发起读取，把 P 的 KV 搬到 D 本地 blocks。我的路径则在启动时映射同设备共享存储，运行时由 D 授予 blocks、P 写入后通知，交接不搬整份 KV。

- 当前禁止叠加外部 KV Connector，二者的 **缓存所有权与交接机制不同** 。

传统分离的版本化实现可回看[PD 分离与 KV 传输](../../../../vllm/基础篇/PD分离与KV传输.md)。

### 34. PagedAttention、FlashAttention 和 prefix caching 分别优化什么？和共享 KV 有什么关系？ {#q34}

| 机制 | 优化的对象 |
| --- | --- |
| PagedAttention | KV 的分页管理与寻址 |
| FlashAttention | Attention 中间结果的存储与访存 |
| prefix caching | 跨请求复用已计算前缀，减少重复 Prefill |
| P/D IPC 共享 | 同一请求的两个执行角色访问同一存储，减少交接复制 |

### 35. 为什么 MoE 不能只换模型名就接入共享权重？ {#q35}

MoE 除了模型参数，还有专家权重的 **运行时布局、kernel 状态和路由后的执行组织** 。

- P 导出的是已经处理为运行格式的权重，D 导入后要建立本进程私有执行状态，同时避免再次 repack 共享权重。我的适配使用 `weights_already_processed()` 包裹后处理，让既有布局保留，再初始化本地状态；当前接入 Qwen3 MoE 的 Triton 路径。

- 激活参数少也不代表只需加载少量权重，专家路由和每专家 token 数还会改变 P/D 的资源需求。

### 37. 为什么 MLA 的 P 和 D 可以采用不同计算路径，却共享同一份 cache？矩阵吸收是什么意思？ {#q37}

**简答** ：共享 cache 保存 latent 和 RoPE key。P 可以临时展开 K/V 做 Attention；D 将 K 的上投影移到 Q 一侧，并先在 latent 空间聚合 V，再做上投影，减少历史 cache 的展开与访存。

只看一个 head 的非 RoPE 部分，用行向量表示：历史 token 的 latent 为 `c_j`，K/V 上投影矩阵分别为 `W_UK`、`W_UV`。

```text
k_j = c_j W_UK
v_j = c_j W_UV

q_nope k_jᵀ = q_nope (c_j W_UK)ᵀ
            = (q_nope W_UKᵀ) c_jᵀ

Σ_j α_j v_j = Σ_j α_j (c_j W_UV)
            = (Σ_j α_j c_j) W_UV
```

D 先把 `q_nope` 投影到 latent 维度，直接与缓存的 `c_j` 计算分数；softmax 权重 `α_j` 聚合 latent 后，再乘 `W_UV` 恢复每个 head 的输出。RoPE 分数由当前 `q_pe` 和缓存 `k_pe` 另行计算，并与非 RoPE 分数共同进入 softmax；不能把两部分各做一次 softmax 后相加。

这种代数重排解释了为什么 D 不必把所有历史 K/V 完整展开。具体实现仍可能保留独立的 BMM，不能将“矩阵吸收”直接说成所有投影已离线融合成一个大矩阵。

源码推导见 [MLA 两种计算路径](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/layers/attention/mla_attention.py#L25-L117)；基础原理可回看[MLA：低秩压缩、矩阵吸收与解耦 RoPE](../../../../vllm/进阶篇/MLA：低秩压缩、矩阵吸收与解耦RoPE.md)。
{.interview-source}

### 38. DeepSeek 的 MLA cache 为什么是 576 维？Q、K、V 都是 576 维吗？ {#q38}

V3/R1 常见配置中，一份 token 的 cache 内容是 **512 维 KV latent 加 64 维 RoPE key** ，合计 576 维。这个数描述缓存内容，不能套到所有中间张量上。

| 对象 | 常见维度，不计 batch/token/head 轴 |
| --- | --- |
| cache 中的 KV latent | 512 |
| cache 中的 RoPE key | 64 |
| Prefill 展开后的每 head Q/K | 128 维 NoPE + 64 维 RoPE = 192 |
| Prefill 展开后的每 head V | 128 |
| Decode 吸收后的每 head Q | 512 维 latent query + 64 维 RoPE = 576 |
| Decode 在 latent 空间聚合的输出 | 512，上投影后恢复每 head 128 维 |

这些是模型的逻辑维度，kernel 还可能 padding 或打包。非量化 BF16/FP16 cache 的原始内容可估为 `层数 × token 数 × 576 × 2 字节`，再计入 block 对齐、尾部浪费和 backend 开销。量化 cache 按实际 spec 的字节数计算，不能继续直接乘 576。

### 39. MLA 的派生权重有哪些？只导出 named_parameters() 够吗？ {#q39}

**简答** ：要导出实际 forward 使用的运行时权重，是否能被 `named_parameters()` 找到取决于当前版本如何注册，不能只根据张量名字判断。

本版本 MLA 后处理从 `kv_b_proj` 拆分 K/V 上投影，普通路径注册 `W_UK_T`、`W_UV`；部分 AITER 路径注册 `W_K`、`W_V` 和对应 scales。这里使用 `replace_parameter()`，因此通常可以进入 parameter 导出路径。

ATOM PR 中对应派生权重有普通 tensor attribute 的形式，因此专门补充属性导出。我的 `export_model()` 已覆盖 parameters、buffers 和 module 的直接 tensor attributes，后续需核查非 `nn.Module` backend 对象中的状态及 Python 标志。

两个不同名字还可能指向同一 Parameter 或底层 storage，例如 router correction bias 的共享注册。要覆盖所有注册位置，并保留 view/别名，避免 D 某个位置仍为 meta，或把原来的共享关系拆成副本。

### 40. D 导入权重后，为什么不能正常重跑一次 process_weights_after_loading()？全部跳过可以吗？ {#q40}

**简答** ：共享的是已经转换好的权重，D 再处理会重复转换、增加显存，甚至写回共享参数；但完全跳过会遗漏本地 kernel 初始化。需要分开权重转换和执行状态初始化。

当前 `import_model()` 对 MoE 会在 `weights_already_processed()` 作用域调用全模型后处理。量化/MoE hook 可以识别该标记，但这个版本的 `MLAAttention.process_weights_after_loading()` 没有检查它，仍会重新生成派生权重。

更具体地说，MLA 部分路径使用 `replace_parameter(..., prefer_copy=True)`；当目标参数的 shape、dtype 和 device 匹配时，会向已有 tensor 执行 copy。若该 tensor 已由 IPC 导入，就可能写入 P/D 共享分配。

适配应让 P 正常完成转换，D 识别预处理权重、检查所需 tensor 已存在，只建立 backend 私有状态。**不能仅给 hook 加一个无条件 return** ，还要确认其本地初始化职责。

源码依据：[D 导入后的后处理调用](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/ipc.py#L160-L205)、[全模型后处理仍调用 Attention hook](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/model_loader/utils.py#L192-L204)、[prefer_copy 的写回行为](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/utils.py#L123-L134)。

### 41. 权重、量化 scales、workspace、RoPE cache，哪些共享，哪些私有？ {#q41}

判断依据是 **谁会修改它，以及修改时其他进程是否还在使用** ，不是它被注册成 Parameter 还是 buffer。

| 状态 | 管理方式及原因 |
| --- | --- |
| 固定 Linear/专家权重、MLA 派生权重 | 处理完成后由 P 持有，D IPC 共享，推理期间避免修改 |
| 固定的权重量化 scales | 随对应权重共享；动态激活量化产生的临时 scales 则本地管理 |
| 物理 KV cache | 共享，按 block 授权、完成依赖和 lease/in-flight 引用约束读写回收 |
| block table、slot mapping、Attention metadata、batch buffers | 各角色分别准备，P/D 的请求批次和位置不同 |
| 临时 workspace、kernel 对象、stream、event、Graph | 每个进程单独初始化，不能随权重 handle 跨进程搬过去 |
| RoPE cache 等 buffers | 固定只读时可评估共享；可能扩展或替换时 clone 或本地重建 |

当前 D 对 buffers 和普通 tensor attributes 一律 clone，是保守策略。扩展时可明确标记较大的只读 tensor 为共享，但不能把所有属性都改成共享。IPC 地址关系见[权重内存地址](#q14-weight-address)，请求级 KV 保护见[读写与回收](#q15)。

### 42. DeepSeek MoE 和当前 Qwen3 MoE 适配相比，多了哪些要核对的行为？ {#q42}

**简答** ：复用 DeepSeek 已有路由语义，核对 grouped top-k、correction bias、shared expert 和输出缩放，并让 kernel 的权重布局与状态正确恢复。

- **Grouped top-k** ：先选择专家组，再从候选专家中选 top-k；不能替换成所有专家上的普通 top-k。
- **Scoring 与 correction bias** ：V3 常见路由使用 sigmoid 分数和 correction bias。Bias 影响选择，最终混合权重的计算要遵循已有模型实现，不能直接把修正后的选取分数当作混合权重。
- **Shared expert 与 routed experts** ：共享专家每个 token 都执行；backend 可能单独计算，也可能融合进专家 kernel，导入后的组织必须与 P 一致。
- **Renormalization 与 routed scaling** ：保留配置中的归一化和缩放，避免模型层与 kernel 重复乘系数。
- **Dense/MoE 层选择** ：按配置保留前面的 dense 层和后续 MoE 层，不能把所有 FFN 都替换成专家层。

这些数学行为已有模型代码，个人适配重点在运行时权重布局、别名和本地 kernel 状态。尤其检查“权重可读”之后，backend 是否仍缺路由表、参数属性或执行对象。

源码依据：[DeepSeek MoE 的路由配置与 shared experts](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/models/deepseek_v2.py#L291-L410)、[dense/MoE 层选择](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/models/deepseek_v2.py#L1293-L1337)。

### 43. MLA 开启 Chunked Prefill 后怎样读历史上下文？多卡时谁确认 P 真正完成？ {#q43}

**简答** ：后续 chunk 按 block table 读取前面已写入的 latent/RoPE cache；只有最后一个 chunk 的相关 GPU 工作完成，才交接到 D。多卡还必须覆盖所有参与 rank。

例如 Prompt 分成三段：第二段的 query 要关注第一、第二段中的合法位置；第三段同样要读前两段。适配时检查 `num_computed_tokens`、序列位置、历史长度和写入 slot 一致，不能把每个 chunk 当成无历史的新 Prompt。

Scheduler 的 Chunked Prefill 拆分本轮 token 工作；MLA backend 还可能把历史 cache 的展开计算按 workspace 容量切块。这是两个层次，前者决定本次处理多少 token，后者组织一次 Attention 内部的计算。

单卡沿用[累计进度与完成事件](#q14-chunk-ready)。多卡下，本地 event 只覆盖相应 stream 上已建立依赖的工作，不能直接代表其他卡或独立通信 stream 完成。需要每个 rank 确认本地执行和必要通信完成，再聚合完成；或者使用已验证、具备同等保证的分布式执行返回语义。D 在此之后验证 lease 并接管，取消回收同样等待最后一次使用结束。

### 44. MoE 每个 token 只激活少量参数，为什么完整 R1 仍需要多卡？ {#q44}

**简答** ：激活参数量决定当前 token 的主要计算量，驻留参数量决定权重容量。不同 token 可能选择不同专家，常规全驻留服务仍需加载全部专家。

以约 671B 总参数估算，BF16/FP16 原始权重约 `671×10⁹×2` 字节，即 **1.34 TB，约 1.22 TiB** ；FP8 原始权重约 **671 GB，约 625 GiB** 。这些还没加 scales、非量化参数、KV、activation、通信和 Graph/workspace。

IPC 让同一 GPU 上的 P/D 共用一份本地权重，减少两份副本的容量需求，不能让完整模型凭空放进单卡。开发时可以用缩小配置验证 MLA+MoE 机制，完整 R1 的支持还要给出多卡配置和真实 checkpoint 的验证结果。

### 45. 多卡 P/D 怎样配对？TP 和 EP 是必须同时实现的吗？MLA cache 怎么分片？ {#q45}

**简答** ：先实现两侧一致的 TP 拓扑，每张卡上的 P rank 和对应 D rank 共享本卡分配。EP 可另行增加，不能把 MoE 支持和 EP/EPLB 支持混为一谈。

```text
GPU 0：P rank 0 ← 本卡权重/KV 共享 → D rank 0
GPU 1：P rank 1 ← 本卡权重/KV 共享 → D rank 1
……
P ranks：独立的 TP/EP 通信组
D ranks：独立的 TP/EP 通信组
```

Manifest 要携带并核对 rank、物理 GPU 和布局信息，D 不能让所有 rank 都导入 rank 0 的分配。增加 EP 时，还需保持两侧专家映射一致，分别初始化 dispatch/combine 通信状态；动态专家迁移和 EPLB 会进一步改变权重所有权，本阶段可以继续禁用。

MLA 的 latent 由各 query heads 共用，**不能直接用普通 MHA 的“KV 除以 TP 数”估算** 。本版本 `MLAAttentionSpec` 设置 `num_kv_heads=1`、`max_tp_shards=1`，普通 TP 场景不能假设 cache 会随 head 切分而缩小；DCP/CP 的分布另按实际配置和 backend 核查。

源码依据：[当前 cache spec](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/layers/attention/mla_attention.py#L1350-L1381)、[当前只处理一份 KV 配置](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/v1/rapidserve/executor.py#L152-L159)。

### 46. FP8 权重支持和 FP8 KV 支持是一回事吗？D 会不会再次量化？ {#q46}

**简答** ：它们分别压缩模型参数和历史上下文，格式与 scales 的管理也不同，要分别验证。

权重侧除了低精度值，还有 block/per-tensor scales、非量化层及 backend packing。P 导出处理后的运行格式，D 使用预处理权重路径，避免再次量化、转置或 shuffle。本版本 `Fp8LinearMethod` 已能跳过转换并恢复必要标志，`Fp8MoEMethod` 已能按导入权重重建 kernel；这提供适配基础，仍需核对目标 backend 的私有状态和参数属性。

KV 侧则按所选 cache spec 保留值、scales 或打包内容。有些格式把这些内容放在同一个 opaque blob 中，不一定存在独立的 `kv_scale` 张量。必须让 P/D 以一致格式读写，不能只导出低精度值、遗漏其解码信息，也不能把权重 scales 当成 KV scales。

源码依据：[FP8 Linear 的预处理权重路径](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/layers/quantization/fp8.py#L358-L371)、[FP8 MoE 重建本地 kernel](https://github.com/tangzzycc/vllm/blob/7a6515f3748a2a12f842fd67667e5a4cc4a7ee86/vllm/model_executor/layers/quantization/fp8.py#L695-L712)。

### 47. 导入后为什么还要重新预热和捕获 Graph？MLA 的辅助 stream 有什么风险？ {#q47}

**简答** ：权重和 KV 可以共享，Graph、metadata 与 stream 的执行关系属于本进程。D 要在导入和绑定完成后，用本地地址与状态预热、捕获。

P/D 虚拟地址无需相同，但每个进程捕获后的本地地址应保持稳定，后续不能随意替换派生权重或 workspace。当前项目的 P 使用 eager，D 保留 Graph；若保留这一设计，不需要为 P 强行增加 Graph。

Attention backend 可能在辅助 stream 上准备 metadata、搬运输入或生成索引。要确认主计算 stream 等待所需准备工作，也要避免多余等待将 P/D 执行串行化。CU Mask 只约束使用该 mask 的队列，不自动约束所有辅助 stream、通信或 Graph 内部队列。

ATOM PR 调整了 `atom/model_ops/attentions/aiter_mla.py` 中的 metadata 准备：rapidserve 模式改在当前 stream 执行相关准备，减少辅助 prep stream 等待带来的 Decode 延迟。vLLM 应沿实际 backend 的依赖链决定如何处理，不能直接把所有异步准备都关闭。

### 48. 怎样证明适配正确、没有第二份权重，也没有偷偷修改共享参数？ {#q48}

**简答** ：先比较相同模型和配置下普通执行与 P/D 执行的数值，再检查共享存储生命周期和启动显存，最后测试并发与性能。以下是待执行的验证方案。

| 验证目标 | 检查方法与判断范围 |
| --- | --- |
| 数值与生成正确 | 固定输入及采样配置，比较 Prefill logits、连续 Decode logits 和 greedy 输出；使用适合 dtype/backend 的误差容限，近似并列 logits 可能导致 token 分歧 |
| 历史 cache 读写 | 覆盖 block 边界、不同历史长度、整段/分块 Prefill；小配置中可比较可解析的 cache 内容和 positions |
| 完成与回收 | 覆盖最后一段尚在运行、取消、迟到完成、多卡某 rank 延迟/异常，确认 D 不提前读且 blocks 不提前复用 |
| 权重没有二次转换 | 导入后跟踪 storage 重绑定、tensor 内容和参数别名；在受控验证中比较执行前后权重，跨进程不以 `data_ptr()` 相等作为证明 |
| 显存容量 | 记录 P 加载、D 构造、导入、预热及 Graph 捕获的阶段峰值；结合分配记录和 manifest 的 storage 去重，排除第二份完整权重 |
| 性能收益 | 在相同模型、精度、硬件、输入输出长度和并发下比较 TTFT、ITL/TPOT、吞吐；单独解释 workspace/Graph 增量和资源争用 |

只检查权重地址稳定不能证明内容没被改，单看进程 allocated memory 也不能证明 IPC 没有额外映射或临时分配。缩小配置验证的是机制，完整 checkpoint 和多卡工作负载才支撑完整模型的支持结论。

### 49. 你参考 ATOM 的哪些部分？在 vLLM 中需要怎样调整？ {#q49}

**简答** ：参考的是处理后权重与 KV 的 IPC 共享、MLA 派生 tensor 导出、rank 配对和 stream 依赖；在 vLLM 中沿 V1/MRV2 的模型加载、cache spec 和调度状态适配。

对照 [ATOM PR #860](https://github.com/ROCm/ATOM/pull/860) 的 head `91e6dacd203deb07f619d4f3e83c26ba44931d84`：

- `atom/model_engine/ipc_utils.py` 补充 MLA 普通 tensor attributes 的权重导出和导入；vLLM 本版本已有直接属性导出，且主要 MLA 派生权重注册为 Parameter，要按实际表示调整。
- `RapidServeModelRunner` 增加按 rank 交换权重/KV handle、D 跳过加载和重新绑定 cache；当前 vLLM PairedExecutor 仍是单设备，需要扩展分布式 worker 与 manifest 分发。
- ATOM 的 MLA 绑定路径使用对应模型的 576 维 cache；vLLM 保留 `MLAAttentionSpec` 与 backend 布局机制，避免将模型常数写死在通用共享代码中。
- ATOM 调整辅助 metadata stream；vLLM 还要结合已有 Decode Graph、异步输出、lease/in-flight 和资源切换机制核查执行依赖。

**个人工作边界** ：当前已实现的是 V1/MRV2 中的单设备共享执行与生命周期管理；本节 DeepSeek 的设计工作是把 MLA/MoE 的运行时状态接到这条路径，完整多卡与量化实现仍待验证。
