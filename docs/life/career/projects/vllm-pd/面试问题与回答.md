## 一、请介绍这个项目，为什么要做 P/D 解耦？ {#q1}

### 1 分钟简答

我在 vLLM V1 和第二版 ModelRunner 上做了 **同一组 GPU 内的 Prefill/Decode 解耦与调度优化**，主要解决长输入计算对已有请求生成速度的干扰。

原来的混合批次中，Decode 也要等同批次的 Prefill 完成。我把两阶段拆成独立执行组，分别组批和提交，通过 GPU IPC 共享权重与 KV。D 统一管理请求和逻辑 blocks，P 按授权计算上下文，完成后交回 D 继续生成。

主要工作包括 **共享初始化、请求交接、异步完成和安全回收**，以及单机 TP、DeepSeek MLA/MoE/FP8 适配。ROCm 上再配合 CU 资源分配和 Decode Graph，控制两阶段的资源争用与提交开销。

### 5 分钟详细阐述

这个项目起点是一个具体的服务问题：**已有请求正在生成时，新到达的长 Prompt 会拉长它的 token 输出间隔。** 比如请求 A 已经进入 Decode，每轮只处理一个新 token；这时请求 B 带着很长的输入进来。如果把 A 的 Decode 和 B 的 Prefill 放进同一次模型执行，A 的下一次输出就要等整个批次完成。A 自己的工作量很小，等待却由整批的执行时间决定。

vLLM 的 Chunked Prefill 已经能缓解这个问题：把长输入拆成多轮，每轮给 Decode 留出推进机会。不过，两阶段仍然共用一次模型执行的节奏。chunk 小，单轮干扰会减轻，但调度、输入准备和 kernel 提交次数会增加；chunk 大，Prefill 更容易跑满，又可能让已有请求等得更久。

因此我的目标是 **让 P/D 分别决定组批和执行节奏，同时复用同一组 GPU 上的模型存储**。Prefill 一次处理很多 tokens，通常有较高计算强度；小 batch Decode 更受权重和历史 KV 读取影响。两者的最合适 batch 大小、执行时长和资源配额往往不同，拆开以后可以分别调优。

实现后，对外仍然是一个 vLLM 服务、一份请求集合，内部有 P、D 两条执行链。新请求 B 在 P 中处理上下文时，已有请求 A 可以继续由 D 调度和提交。两侧共享设备资源，仍会争用带宽和算力，但 **D 的推进不再要求先完成包含长 Prefill 的同一个混合批次**。

为了控制显存成本，P worker 加载模型并创建物理 KV，D worker 通过 IPC 映射这些存储。权重和 KV 的大块数据共用，各自的请求状态、输入 buffer、采样器、workspace 和 Graph 保持独立。这样避免额外复制一整套模型与 KV 池，也允许两侧采用不同的组批配置。

请求管理上，我保留 D 侧的 Scheduler 和 KVCacheManager 作为统一入口。D 决定请求何时入场、使用哪些 blocks、何时结束；P 只执行 D 授权的上下文工作。这个划分很重要：共享同一个 KV 池以后，必须只有一个逻辑块分配器，否则两侧可能把同一块显存分给不同请求。

开发先从单卡跑通完整生命周期，再扩展到单机 TP。例如 TP8 时，P、D 各有 8 个 workers，P rank i 和 D rank i 配在同一张 GPU 上，共享本卡的权重分片和 KV。**总共仍是 8 张物理 GPU**；两侧有各自的 TP 通信组和执行状态。DeepSeek 适配则进一步处理 MLA 吸收权重、MoE 路由引用和 FP8 后处理格式。

资源控制上，P 使用 eager，D 保留 Decode Graph；ROCm 支持全 CU 并发，也支持按负载切换互补 CU masks。前者让两侧充分使用设备，后者在重负载时限制相互干扰。具体选择要结合输入长度、生成并发和延迟要求。

本地最新实现已经完成复现测试，性能结果符合预期。项目的主要工程成果是把 **独立执行、共享存储、统一请求管理** 接成完整链路，并补齐多卡完成、取消和退出时的正确性。收益最需要关注的场景，就是长输入到达时，已有生成请求能否保持较好的推进速度。

## 二、你在框架层具体做了哪些工作，为什么这样拆分？ {#q2}

### 1 分钟简答

我主要改了 **执行组织、共享初始化和请求生命周期** 三个部分。

执行组织上，在 EngineCore 接入协调器，分别派发 P/D 工作并收取结果；执行器启动两组 workers，多卡复用 MultiprocExecutor。初始化上，D 导入 P 已处理好的权重与 KV，建立自己的 Runner 状态。

生命周期上，D Scheduler 统一分配 blocks，以授权记录（lease）保护 P 工作，完成后接回原来的结果更新逻辑；D 在途计数保护已提交计算，避免取消后提前复用 KV。

开发顺序是 **共享与交接 → 异步与回收 → 资源调度 → TP 与 DeepSeek**，模型运算继续复用 vLLM，改动集中在执行组织。

### 5 分钟详细阐述 {#framework-answer}

我先沿原来的请求链定位职责：EngineCore 推进引擎，Scheduler 选请求、决定 token 数并管理逻辑 KV，Executor 把工作发给 workers，ModelRunner 准备输入和 Attention metadata，执行模型与采样，最后结果回到 Scheduler。这条链里，需要调整的是 **谁组织 P/D 执行，以及执行完成后怎样更新同一份请求状态**。

**第一步，分离 ModelRunner 的共享存储与私有执行状态。** 两个进程可以读同一份权重，也可以按不同阶段写同一个请求的 KV，但不能共用正在修改的输入 buffer、请求槽位或采样状态。我在 MRV2 中整理了模型组件初始化入口，让 D 在导入权重之后建立自己的状态；KV 初始化支持绑定已有 tensors，避免再建一套物理缓存。

**第二步，接入两组执行器的初始化和调度循环。** EngineCore 根据配置选择 paired 路径，由 PairedExecutor 启动 P、D，再把引擎 step 交给 PairedCoordinator。协调器每轮处理取消和完成、派发新的 P 授权，并提交可运行的 D batch。P 的执行预算独立于 D，所以长输入可以集中在 P 处理，D 继续组自己的生成批次。

**第三步，解决两侧怎样管理同一条请求。** 我让 DecodeScheduler 保留唯一的 KVCacheManager。D 先为待处理上下文保留 blocks，再将 token history、开始位置、块表和授权身份交给 P。P 的 PrefillEngine 负责等待、组批和异步执行，不另外分配逻辑块。这样 P/D 可以独立执行，请求和显存空间的管理仍然集中。

P 完成后，不直接另建一套客户端输出流程。D 保存了授权时的 SchedulerOutput，用它接回 vLLM 的 `update_from_output()`，继续处理首 token、停止条件和流式返回。请求第一次进入 D Runner 时，再补建本地 NewRequestData；之后沿正常的 cached request 更新路径执行。这一步把业务请求连续性与两套 Runner 状态衔接起来。

**第四步，补齐异步下的完成和回收。** 任务提交后，GPU 可能还在计算，客户端也可能先取消。为此，P 授权由 lease 保护，D 已提交轮次由 in-flight 计数保护；业务结束与 blocks 真正释放分开处理。完成消息带 session 和 sequence，避免旧授权或重复消息误更新当前请求。进程退出则先关 D 消费者，再关 P 存储拥有者。

**第五步，把单卡完成语义扩展到 TP。** 多卡继续使用 MultiprocExecutor 的广播与响应队列，我增加适配层汇聚每个 rank 的完成。每个 worker 等本地 GPU 和输出拷贝完成后再返回，协调器只有收齐全部响应，才允许 P/D 交接或回收。共享 manifest 也按 rank 导出，每个 D rank 导入对应 P rank 的存储。

DeepSeek 在这一步增加了另一类问题：模型构造出来的参数与后处理后的实际运行格式不完全一致。因此共享导入还要恢复 MLA 吸收权重、FP8 标记和参数槽位，并修正 router 中的旧 meta 引用；同时为 D 重建本地 kernel 与 workspace。

**执行资源上，单卡阶段已经接入独立 stream、CU 分配和 Decode Graph，之后沿同样的依赖关系扩展到 TP。** 候选 CU 策略和 Graph 在启动时预热，运行切换通过 event 保持同一角色内的批次顺序。资源调度因此可以调整，而不需要切换时临时捕获 Graph 或破坏自回归依赖。

这些改动沿原来的职责分布：**协调器管推进，Scheduler 管请求和逻辑 KV，Executor 管进程与分发，Worker 管共享模型和执行资源，MRV2 管输入准备与模型执行**。开发中每接通一段，都能用一条请求核对它的状态、存储和完成时机，之后再逐步增加异步、多卡和模型格式的复杂度。

## 三、P/D 如何共享权重和 KV，初始化顺序为什么重要？ {#shared-storage}

### 1 分钟简答

共享初始化按 **P 加载权重 → D 导入权重 → P 分配 KV → D 绑定 KV → 两侧预热和 D Graph 捕获** 的顺序执行。P 持有物理存储，D 通过 IPC 映射；TP 下每个 D rank 导入同一 GPU 上对应 P rank 的分片。

导出的除了 storage handle，还有 tensor 的 dtype、shape、stride、offset 和运行格式信息。D 先在 meta 上创建模型骨架，再挂接这些权重，建立自己的请求状态和执行 buffer。

因此 **权重和 KV 共用，执行状态独立**。D 的 Scheduler 管理哪些请求使用哪些 blocks，P worker 保证底层显存存活。退出时先清理 D，再关闭 P，覆盖消费者的完整使用期。

### 5 分钟详细阐述

这里先区分两种所有权：**物理显存由 P 创建和保活，逻辑 KV blocks 由 D 分配和回收**。P 持有实际 tensor，D Scheduler 决定哪个请求能写哪个 block。二者分别解决存储存活与请求寻址的问题，是共享初始化和运行期管理的基础。

启动前先校验 MRV2、单机 TP、spawn 和固定 KV 字节预算等条件。随后复制 P 的配置，单独设置它的 token budget 与请求数上限，清空 static forward context。P 使用 eager，关闭自身 Graph 和 compilation，使两侧 Attention 层注册与执行状态各自建立。

P workers 正常加载模型，并完成量化、权重吸收和 backend 所需的后处理，再导出实际运行状态。D 使用 meta 构造模型骨架，导入 P 的权重视图，然后初始化自己的 MRV2 请求状态、输入 buffer 和采样组件。这样不用再次加载一整套 checkpoint 权重，D 执行时也有完整的本地 Runner 状态。

**IPC 导出按底层 storage 去重。** 一个 storage 可能对应多个名字或不同视图，manifest 保存它的 handle，再为每个 tensor 记录 dtype、shape、stride、storage offset。导入后按这些信息恢复视图。虚拟地址可以不同，只要映射到同一底层分配；同一 storage 的不同 dtype 视图也需要分别保留，防止误合并。

TP 下，每个 P rank 导出自己的 manifest，D rank i 取对应条目。导入时还检查物理 GPU UUID，确保共享发生在预期设备上。例如 P rank 3 与 D rank 3 配对在同一卡上，二者各自使用独立通信组，但读取本卡相同的权重分片。

权重导入完成后，P 根据固定 KV 预算创建 cache，再按层导出真实 KV tensors。D 恢复相同的 KV 配置和布局，将已有 tensors 绑定到本地 Attention 层。block table 与 slot mapping 按各自批次生成，最终都指向这套共享物理缓存。

**共享并不等于没有额外显存。** 两侧仍各有 workspace、输入输出 buffer、采样状态，D 还保留 Graph 相关资源。大块权重与 KV 池只需一套，但容量规划仍要留出两组执行状态的空间。固定 KV 预算也让两侧初始化基于同一个容量，避免各自 profiling 后得出互不一致的缓存大小。

两侧都绑定完成后再预热，D 捕获 Decode Graph；需要动态 CU 策略时，候选 stream 和对应 Graph 也提前建立。这个顺序保证 Graph 捕获的是正式共享地址，后续不会因换绑权重或 KV 而失效。

存活期同样是初始化协议的一部分。P 导出后保留 owner 引用，D 使用期间 P 必须存活。初始化中途失败和正常退出都先清理消费者 D，再关闭 P；清理 D 时还要处理 Graph、编译 callable 等保留的 tensor 引用。**成功映射、运行时不换址、退出前不失效**，共同构成共享存储的正确性。

handle 如何映射显存、两层 offset 怎样恢复地址，以及共享后如何保证读写正确，见 [GPU IPC 原理与正确性](#gpu-ipc)。

## 四、GPU IPC 是什么，底层原理是什么，为什么能正确共享权重与 KV Cache？ {#gpu-ipc}

### 1 分钟简答

GPU IPC 是 GPU 的进程间通信机制。我的项目主要用它 **让 P、D 两个进程访问同一份 GPU 显存**，避免各自加载一份模型权重或在交接时复制历史 KV。

P 导出底层显存的 IPC handle 和 tensor 元数据，D 通过运行时和驱动建立本地映射，再根据 dtype、shape、stride、offset 重建 tensor。**两侧虚拟地址可以不同，底层分配相同。** 项目使用 PyTorch 的 `_share_cuda_()` 和 `_new_shared_cuda()` 封装这条路径。

正确性由三部分共同保证：**映射与布局正确、读写顺序正确、存储生命周期正确**。权重在 P 完成加载后处理后导出，运行期按只读方式共享；KV 由 D 统一分配逻辑 blocks，P 按授权写入，确认 GPU 完成后才交给 D。TP 下等待所有 rank，取消后等 lease 和在途计算解除再回收，退出时先关闭 D 消费者，再关闭 P 存储拥有者。

### 5 分钟详细阐述

**1. IPC handle 怎样把两个进程连到同一份显存？**

普通进程各有自己的地址空间，直接把 P 的 `data_ptr()` 发给 D，不能建立可用的跨进程映射。即使设备支持统一虚拟寻址（UVA），也不代表两个进程可以直接互用指针。

P 先分配 GPU 内存，再导出一个代表该分配的可传递句柄。D 打开句柄后，GPU 运行时和驱动把这份分配映射到 D 的 GPU 虚拟地址空间，返回 D 可用的本地指针。GPU 执行时通过各自的地址映射访问相同的底层显存，因此不需要另建一份数据副本。

```text
P tensor → P 的本地虚拟地址 ─┐
                            ├→ 同一份 GPU 显存分配
D tensor → D 的本地虚拟地址 ─┘

跨进程传递：IPC handle + storage / tensor 元数据
```

CUDA 的传统接口是 `cudaIpcGetMemHandle()`、`cudaIpcOpenMemHandle()` 和 `cudaIpcCloseMemHandle()`；HIP 有对应的 `hipIpc*` 接口。项目实际调用 PyTorch storage API；ROCm 版 PyTorch 也沿用 `torch.cuda` 命名。当前实现另外校验 **物理 GPU UUID**，每个 D rank 只导入同一张 GPU 上对应 P rank 的存储。

API 依据：[CUDA IPC 内存接口](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__DEVICE.html)。项目源码：[导出 storage、设备校验与导入](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/ipc.py#L45-L97)。

**2. 为什么有 handle 还需要 dtype、shape、stride 和两层 offset？**

handle 解决“映射哪份分配”，tensor 元数据解决“怎样解释其中的数据”。这里要分清三层：

| 层次 | 含义 | 重建所需信息 |
| --- | --- | --- |
| GPU allocation | allocator 从 GPU 运行时取得的底层分配 | IPC handle |
| Storage | tensor 使用的存储区，可能只占 allocation 的一部分 | 在 allocation 内的字节偏移、存储字节数 |
| Tensor view | storage 上的一种张量视图 | dtype、shape、stride、按元素计的 storage offset |

PyTorch caching allocator 可能把多个存储区放进一块较大的 allocation。导出时，storage 的 IPC 参数包含这层字节偏移；项目再单独保存每个 tensor 的视图信息。D 先调用 `_new_shared_cuda(*args)` 重建 storage，再用 `tensor.set_(storage, offset, shape, stride)` 重建视图。

以一个 BF16 tensor 为例，假设其 storage 位于 allocation 内的 `0x100` 字节处，tensor 从 storage 的第 16 个元素开始，BF16 每个元素 2 字节：

```text
P 的 allocation 映射基址：0xA000
D 的 allocation 映射基址：0xB000
storage 字节偏移：         0x100
tensor 字节偏移：          16 × 2 = 0x20

P 的 tensor 首地址：0xA000 + 0x100 + 0x20 = 0xA120
D 的 tensor 首地址：0xB000 + 0x100 + 0x20 = 0xB120
```

这两个地址数值不同，但对应同一个元素。访问其他元素还要按 stride 计算偏移，不能默认所有权重都连续。项目按 storage 去重，一份 storage 只导出一次，再记录它的多个视图；相同视图的 Parameter 别名也在导入时恢复，并把 dtype 纳入判断，避免混淆同一存储上的不同类型视图。

这里的地址只是示例。allocation 内的偏移由 PyTorch IPC 层处理，项目的 `set_()` 只接收 tensor 的元素偏移，**不能再手工把 allocation 偏移加一遍**。

依据：[PyTorch IPC storage 与 tensor 重建说明（v2.8.0）](https://raw.githubusercontent.com/pytorch/pytorch/v2.8.0/torch/multiprocessing/reductions.py)。项目源码：[视图恢复](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/ipc.py#L68-L97)、[Parameter 别名恢复](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/ipc.py#L208-L237)。

**3. 权重怎样保证既共享正确，又不会被另一侧改坏？**

P 先加载 checkpoint，并完成 packing、量化和 MLA 派生权重等后处理；`export_weights()` 在导出前同步设备，保证 D 导入的是已经准备好的运行时数据。D 在 meta device 上构造模型骨架，再挂接导入权重，避免第二次完整加载。

共享的是实际执行所需的权重和格式信息。例如 FP8 的 shuffle、transpose 标志，以及 MLA 的派生权重，都要与 P 保持一致。D 还要恢复本地执行对象的引用，避免模块参数已经导入、MoE router 却仍指向旧 meta tensor。这部分细节见 [DeepSeek 适配](#deepseek-adaptation)。

运行期，双方按只读方式使用共享权重，当前 paired 路径拒绝 reload、update weights 等入口，避免一侧换掉分配或重新处理权重。**IPC 本身不会把权重设成只读，也不会阻止错误的原地写入**；只读约定和受限的更新路径是程序提供的保证。

metadata、输入输出 buffer、workspace 和 Graph 等执行状态各自持有；可变 buffers 在导入时复制或本地初始化。因此“共享权重”不等于共用一个可变的 ModelRunner。

**4. KV 会被持续写入，为什么 D 能读到对应请求的正确内容？**

KV 的保证可以分为 **写对位置、写完再读、用完再回收**。

首先，D 的 Scheduler 和 KVCacheManager 统一管理逻辑 blocks，P 只使用授权中的 block IDs。两侧绑定同一份物理 KV，并保持相同的 dtype、block size 和 backend layout；本地请求槽位可以不同，历史读取使用 `block_table`，新 KV 写入使用 `slot_mapping`。

沿后面的 [40-token 请求例子](#worked-example)，假设 block size 为 16、块表为 `[7, 12, 19]`。P 写完位置 0～39 后，D 首轮输入采样得到的首 token，在位置 40 写入它的 KV：

```text
逻辑块序号 = 40 // 16 = 2
物理 block = block_table[2] = 19
块内 offset = 40 % 16 = 8
slot = 19 × 16 + 8 = 312
```

这个 slot 表示 token 的缓存位置；实际字节地址还要由该 Attention backend 的 K/V 或 MLA 布局解释。只共享显存却使用错误块表，仍会读错请求的数据。

其次，**成功打开 IPC handle，不代表 P 后续的 KV 写入已经完成**。P 提交计算后记录完成 event，pending 队列等执行 event 和输出 copy event 就绪；开启 Chunked Prefill 时，中间 chunk 只更新进度，最后一个 chunk 完成后才发送 `prefill_done`。事件必须覆盖 KV 写入所在 stream 及其依赖，单个事件不会自动等待所有无关 stream。

TP 下，每个 P worker 的 `RankOutput` 先确认本地 GPU 和输出拷贝完成，RPC Future 收齐所有 rank 响应才 ready。P 再发送完成消息，D 核对当前 lease 的 session、sequence 后允许交接。当前实现使用 **P 本地完成确认＋CPU 控制消息**，没有让 D 直接打开 P 的 IPC event 等待。

```text
P 写共享 KV
  → 本地 GPU 完成，TP 下全部 rank 完成
  → 完整 Prefill 结束，P 发送完成消息
  → D 校验授权身份并接受交接
  → D 提交 Decode，读取历史 KV、追加新 KV
```

最后，请求取消不等于 GPU 已停止使用缓存。P lease 与 D in-flight 计数保护 blocks；请求可以先进入 retired 状态，但只有最后一次 GPU 使用结束后才能释放，避免旧 kernel 覆盖新请求。详细的多卡汇聚和取消流程见 [完成与回收](#tp-completion)。

因此，P 可以处理请求 B，同时 D 生成请求 A：当前路径中两者使用各自分配的 blocks；B 的 lease 未解除时，Scheduler 不让 B 进入 D。正确性依靠请求所有权和阶段交接，不需要给每个 KV 元素加跨进程锁。

**5. 为什么还要保证 P 存活，并按顺序关闭进程？**

P 是底层分配的拥有者，导出 manifest 的 `_owners` 保留 storage 引用；`__getstate__()` 不把这些 owner 引用传给 D。PyTorch IPC 参数也包含跨进程引用计数和初始化同步信息，但这些机制不能替代项目的退出协议，也不能自动管理每个请求的后续 KV 写入。

D 结束时要先等待 GPU 使用完成，清理 Graph、编译 callable 和模型对象保留的共享引用，再关闭 P。CUDA 接口明确规定，消费者关闭映射前，生产者释放原分配会造成未定义行为。P 异常退出后，应按故障路径停止推进，不能继续假设旧共享地址有效。

Graph 捕获的是 **D 自己的本地地址**，不要求它与 P 地址相等；要求的是导入映射、权重和 KV 在 replay 期间保持有效且地址稳定。结合前面的映射、寻址和完成协议，正确性条件可以这样记：

| 必须成立的条件 | 项目中的保证 |
| --- | --- |
| 两侧访问正确的分配和视图 | rank 配对、GPU UUID、handle 与 dtype/shape/stride/offset |
| 权重已经准备好且共享期间稳定 | 导出前同步、运行格式恢复、只读使用、限制更新 |
| KV 属于正确请求且写完再读 | 统一 blocks、正确布局和映射、完成确认、授权身份校验 |
| 地址和内容不在使用中失效 | owner 保活、lease/in-flight 延迟回收、D 先退出 |

源码：[owner 保活与序列化](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/ipc.py#L25-L77)、[消费者共享引用清理](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/worker.py#L248-L306)。

## 五、一条请求怎样完成 Prefill，再交给 Decode？ {#request-handoff}

### 1 分钟简答

请求进入 D Scheduler 后，由 D 分配待处理上下文所需的 blocks，并生成 PrefillWork，带上 token history、起始计算位置和授权身份。P 按自己的预算组批，计算上下文并采样首 token。

P 确认计算完成后返回结果，D 校验 lease，再接回原来的请求更新和输出逻辑。请求第一次进入 D Runner 时，还需要建立本地请求状态，因为此前计算发生在 P Runner 中。

关键是 **首 token 与 KV 进度相差一步**：P 写完 Prompt KV、采样首 token；D 以首 token 为输入，写它的 KV 并生成第二个 token。交接只传任务和完成元数据，历史 KV 已在共享缓存中。

### 5 分钟详细阐述 {#scheduler-ownership}

以 A、B 两个请求为例：A 正在 Decode，B 是新到达的长输入。B 仍从正常服务入口进入 EngineCore，由 D Scheduler 管理。协调器发现它还需要上下文计算，就把它交给 P；与此同时，A 继续沿 D 的生成链执行。

**第一步是授权，而不是直接把 B 的输入扔给另一个进程。** D 调用 `grant_prefills()`，复用原 Scheduler 的入场和 KV 分配能力，为完整待处理上下文保留 blocks。授权阶段临时使用较大的选择预算，完成后恢复 D 配置。这里的预算表示允许 P 处理多少上下文，P 的真实 batch 仍由自己的执行预算决定。

授权内容包括完整 token history、block IDs、本次开始前的计算位置、token 数，以及 session 和 sequence。D 同时保存对应的 SchedulerOutput，用于之后接受结果。基础调度会推进 computed-token 计数，所以构造任务时需要扣回本次 scheduled tokens，明确告诉 P 从哪里开始计算，避免把已调度当成已完成。

**第二步是 P 独立组批。** PrefillEngine 维护 waiting、pending 和本地 resident 请求，分别表示待执行工作、已提交未完成的批次和占用 Runner 槽位的请求。P 的 token budget 和最大请求数独立于 D，默认一次处理请求的完整剩余上下文，也保留可选 chunking。

例如 40-token Prompt 开启 chunking、预算为 16 时，可以按 16、16、8 三次执行。同一份授权在中间保持有效，P 更新自己的计算进度，直到完整上下文结束才向 D 发布结果。D 因此不需要逐 chunk 重分配 blocks。

**第三步是确认完成并交回请求。** P 提交后把 batch 放入 pending，确认 GPU 计算与输出拷贝完成；TP 模式要等所有 rank。最后一段完成后提取首 token，安排 P 本地请求清理，再发送完成消息。D 根据 session、sequence 匹配当前 lease，接回保存的 SchedulerOutput，复用 `update_from_output()` 处理采样结果、停止条件和客户端输出。

授权身份保证旧消息不会误更新当前状态。请求已取消时，P 的完成只作为安全收尾；D 不继续交付结果。首 token 已满足停止条件时，请求也可以在这里结束，无需再跑一轮 Decode。

**第四步是建立 D Runner 的本地状态。** 业务 Request 已经有 Prompt 和首 token，但 D Runner 之前没执行过它，不能直接当作本地 cached request。协调器首次调度时构造 NewRequestData，带上完整 history、实际 blocks 和本轮起始位置，移除重复 cached 条目；之后才沿常规增量更新路径推进。

以 40-token Prompt 为例，P 完成时 KV 覆盖位置 0～39，并采样 $y_1$。**$y_1$ 此时是下一轮输入，还没有它自己的 KV。** D 第一次在位置 40 计算 $y_1$，写入对应 KV，再采样 $y_2$。这解释了首 token 的交接与 computed-token 计数应该如何对应。

寻址上，P/D 的本地请求槽位可以不同，但都使用 D 授权的 block IDs。block table 决定历史 KV 从哪里读，slot mapping 决定当前 token 的 KV 写到哪里。例如 block size 为 16、块表为 `[7, 12, 19]`，位置 40 就落在 block 19 的 offset 8。两侧只要采用一致的块表和布局，就能连续使用同一个请求的 KV。

### 用 40-token Prompt 复述一次交接 {#worked-example}

| 阶段 | 请求与 KV 的状态 | 实际执行 |
| --- | --- | --- |
| B 入场 | D 为上下文分配 blocks，建立 lease | B 尚未进入 D Runner |
| 授权 P | 发送起始位置 0、40 tokens 和块表 | P 在本地注册 B |
| P 计算 | lease 保持，A 继续由 D 调度 | 写入位置 0～39 的 Prompt KV |
| P 完成 | D 校验身份，接受 $y_1$，解除 lease | TP 下确认所有 P rank 完成 |
| 首次 D | 建立 D 本地请求状态 | 输入 $y_1$，写位置 40 的 KV，生成 $y_2$ |
| 后续 D | 正常更新、停止与回收 | 每轮计算前一 token，追加 KV，采样下一 token |

## 六、多卡下怎样确认真正完成，取消后怎样安全回收 KV？ {#tp-completion}

### 1 分钟简答

多卡的关键是 **rank 0 有采样结果，不代表所有卡的 KV 已经写完**。如果提前交给 D，其他卡可能读到未完成的 KV；如果提前回收，也可能让旧 kernel 写坏新请求。

我让每个 worker 在后台输出线程里等待本地 GPU event 和输出拷贝，执行器收齐全部 rank 的响应才报告完成。采样结果使用 rank 0 的，但完成判断包含所有 rank。

取消后，P lease 与 D 在途计数继续保护 blocks。请求先逻辑结束，最后一次 GPU 使用完成后再释放。退出则先关 D 消费者、清理 Graph 和编译对象的共享引用，再关 P 存储拥有者。核心是 **把业务结束与 GPU 使用结束分开管理**。

### 5 分钟详细阐述 {#kv-lifecycle}

多卡扩展最重要的变化是完成语义。单卡可以直接查询本地 GPU event；TP 下，每个 rank 在独立 worker 进程，协调器不能只根据一个返回结果判断整批结束。每张卡都可能写本地 KV，P/D 交接必须覆盖全部参与计算的 rank。

P、D 各自使用 MultiprocExecutor，分别广播自己的 batch。两侧通信组有独立 rendezvous，组内继续执行原来的 TP 通信；同 rank 的 P/D 共享本卡存储。适配层沿已有队列实现任务分发，主要补充的是异步完成汇聚。

**完成确认分三层。** 每个 worker 执行模型与采样后记录本地 event，返回 RankOutput。即使非输出 rank 没有采样结果，也必须返回完成包装，因为它仍参与计算和 KV 写入。

接着，WorkerProc 的后台输出线程等待本地 event，再获取异步采样输出，确认回拷完成。等待放在输出线程中，负责接收和提交工作的线程可以继续处理后续 RPC，协调器也不需要在提交点同步等设备。

最后，ParallelWorker 汇聚 collective RPC 的全部 rank 响应，用一个后台 reader 按提交顺序读取底层结果，避免多个线程竞争响应队列。聚合 Future 只有收齐全部响应才完成。协调器看到 ready 后，才取 rank 0 的生成结果更新 Scheduler；其他 rank 的响应提供完成保证，并传播执行错误。

**取消则体现为什么完成判断必须严格。** 假设 B 的 Prefill 已提交，客户端随后取消。业务上 B 可以结束，但已提交 kernel 仍可能继续写它的 blocks。如果立即把这些块给新请求 C，C 写入的 KV 就可能被 B 的迟到计算覆盖。这类问题往往不是立即报错，而是后续生成被静默污染。

所以我用两类状态保护缓存：lease 表示 P 的授权还没有收尾；D in-flight 计数表示已提交的 Decode 轮次尚未完成。取消后把请求放入 retired 状态，停止继续调度，但保留 blocks，直到两类使用都解除再回收。

P 尚未提交的取消工作可以直接结束；已提交工作等待 pending 完成，再以空结果确认收尾。多卡也必须收齐完成。D 校验当前授权身份、丢弃被取消的输出，然后尝试释放 retired 请求，避免重复或旧完成消息误解锁。

D 使用异步调度时，同一请求可能有两轮在途。第一轮完成只将计数从 2 降到 1，不能立即释放；最后一轮完成且没有 P lease 后才安全。因此这里使用计数，而不是简单的“执行中”布尔值。未回收请求还占用入场额度，避免取消后立即补入过多工作，超过尚未释放的本地容量。

**进程退出也遵循相同原则，只是粒度变成整个共享池。** P 是存储拥有者，D 是消费者，必须先确保 D 不再使用共享地址，再结束 P。清理时不能只删除 model：Graph、编译 callable、MoE router 都可能继续持有 tensor 引用。

Worker 在 GPU 工作完成后断开旧 tensor 的存储引用，清理 Graph、编译对象和 router，再释放共享导入状态；执行器最后关闭 P。这套协议保证 **请求 blocks 不早于最后一次 GPU 使用被复用，共享存储不早于消费者退出失效**。

## 七、DeepSeek 的 MLA、MoE 和 FP8 适配难在哪里？ {#deepseek-adaptation}

### 1 分钟简答

难点在于 **模型加载后的运行状态与 checkpoint 参数不完全一致**。MLA 会生成吸收权重，FP8/MoE 会重排权重、处理 scales 和参数槽位；只共享原始参数，D 可能漏掉实际计算需要的数据，或者重复后处理。

我扩展共享 manifest，记录参数、buffers、普通 tensor 属性、布局标记和后处理后的参数槽位。D 导入已处理权重，MLA 跳过重复吸收，MoE 重建本地 kernel；router 中保留的旧 meta bias 也重新绑定到实际参数。

KV 按当前 MLA 后端的真实布局共享，每个 D rank 接对应 P rank。当前覆盖单机 TP 的 DeepSeek-V3/R1 和指定 checkpoint block FP8 格式，重点是 **共享运行格式的数据，并让本地执行对象正确使用它们**。

### 5 分钟详细阐述

DeepSeek 适配是在共享初始化链路上进一步处理模型运行格式。一般模型中，加载参数后建立本地执行状态相对直接；DeepSeek 同时包含 MLA 和 MoE，再叠加 FP8，加载后会生成新的权重视图、修改参数布局，还会把 tensor 引用交给普通 Python 执行对象。D 从 meta 构造后，需要恢复这些实际运行状态。

**第一类问题是 MLA 的吸收权重。** 加载后，`kv_b_proj` 被拆分和处理，得到 `W_UK_T`、`W_UV`，特定路径还会生成其他吸收权重及 scales。这些 tensor 部分是参数，部分只是普通属性。只遍历 named parameters 或 state dict，可能漏掉 Decode 真正使用的矩阵。

因此 manifest 同时覆盖参数、buffers 和普通 tensor 属性，恢复对应的 storage 视图。D 调用后处理时，在已处理权重上下文中检查吸收结果，已有对应数据就直接复用。否则重复吸收、量化或打包可能创建新的私有分配，既增加初始化成本，也破坏共享与 Graph 地址稳定性。

**第二类问题是 FP8 的布局和参数槽位。** 当前支持的 DeepSeek checkpoint FP8 使用 128×128 block 和 dynamic activation。实际 backend 除了读取 FP8 数值，还可能需要 shuffle、transpose、处理 scales，并删除或置空已经消费的参数槽位。

P 后处理后的模块状态因此与 D 刚构造的 meta 模型不同。我在 manifest 中保留 `is_shuffled`、`is_transposed` 标记，以及实际 parameter slots。导入时按 P 的状态恢复：已经删除的槽位删掉，置为 None 的也同步置空，避免 D 后处理误读旧 meta scales 或再次整理已处理权重。

这里的数据共享和 kernel 初始化分开进行。FP8 MoE 复用已有 `weights_already_processed()` 分支，保留权重的运行格式和共享存储，重建 D 本地 kernel 与 workspace；MLA 则补上已处理吸收权重的复用入口。这样既接入现有 backend，又避免重新生成一套权重。

**第三类问题是 router 的旧引用。** DeepSeek 的 `e_score_correction_bias` 参与专家选择。meta 构造时，它会被传给一个普通 router 对象。之后即使模块里的 Parameter 已替换成真实共享 tensor，router 仍可能握着原来的 meta 引用。

这个问题说明，仅检查模型注册参数是否已经离开 meta 还不够。导入阶段需要把 router 的 bias 重新指向已导入参数，确保专家选择读取真实数据。导出时保留不同注册名字和别名，也防止恢复过程中遗漏某个参数入口。

**KV 则以实际 backend 布局为准。** DeepSeek MLA 保存压缩 latent 与 RoPE 部分，典型配置为 512 加 64，逻辑宽度是 576。TP 切 query heads，这份压缩 latent 在各 rank 上保留完整逻辑宽度。我的做法是导出各 rank 已分配的 KV tensors，让 D 使用相同配置绑定，保留 block、dtype 和维度排列。

当前实现覆盖单机 TP，独立 EP、EPLB 等组合在配置阶段拒绝。专家动态重排可能改变共享权重的含义，需要两侧共同协调；当前支持范围先固定布局，确保导入与执行一致。

这些适配把 **后处理数据、共享视图、本地 kernel 和 Python 引用** 连成一套初始化协议。验证时除了看生成是否正常，还要检查没有残留 meta 引用、权重未重复处理、KV 布局一致，以及退出时编译和 router 引用能否安全清理。

源码：[manifest 覆盖范围](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/ipc.py#L101-L136)、[支持格式与导入修复](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/ipc.py#L139-L271)、[MLA 避免重复处理](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/model_executor/layers/attention/mla_attention.py#L1220-L1332)、[复用 FP8 MoE 后处理](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/model_executor/layers/quantization/fp8.py#L708-L713)。

## 八、独立 stream、CU 资源分配和 Decode Graph 怎样配合？ {#execution-resources}

### 1 分钟简答

独立调度让 P/D 各自组批，独立 stream 保持各自的提交顺序，CU mask 则控制两侧能使用哪些计算单元。P 使用 eager，D 保留 Decode Graph；全 CU 模式让两侧竞争资源，重负载下可以切成互补 masks。

我在启动时预热候选 stream 和对应 Graph。运行切换时，旧 stream 记录 event，新 stream 等待它，再切 Runner 的主 stream 和 Graph manager，保证后续 Decode 不越过前一轮计算。

ROCm 还需要单独处理 Graph capture stream 和 replay 队列配置。资源策略既有按负载切换的 constrained，也有根据 Decode 步时间反馈的 auto。关键是 **调整资源时保持执行依赖，避免临时捕获和整轮主机等待**。

### 5 分钟详细阐述

两阶段拆开以后，还有一个问题：它们虽然可以独立提交，但仍共享同一设备的算力、带宽和缓存。长 Prefill 占用大量计算资源时，Decode 仍可能受影响，所以需要把执行组织和资源分配一起考虑。

**调度、stream 和 CU mask 分别控制不同层次。** 调度决定每侧 batch 中有哪些请求；stream 决定本角色内工作顺序；CU mask 限制 stream 上的工作能使用哪些计算单元。独立 stream 提供并发提交条件，实际重叠和争用情况需要 GPU trace 判断。CU 分区限制计算资源，但两侧仍然共享显存带宽和 cache。

P 输入形状变化较大，使用 eager；D 的生成形状更稳定，继续用 MRV2 Decode Graph 降低提交开销。启用异步调度时，D 也保留已有 output placeholders 与 GPU 上的 last sampled tokens，后续执行按 stream 顺序消费真实前序结果，维持自回归依赖。

**资源策略先从全 CU 开始。** 两侧都能使用完整设备，适合一侧较空或竞争不严重的负载。固定 fraction 可以建立互补 CU masks。constrained 则在有 Prefill 压力、活跃 Decode 请求达到 64 时选择 50/50 分区，其他情况下恢复全 CU。这里的 64 是调度层活跃请求数，并不等于某次实际 GPU batch。

另一个 auto 策略会在持续 P/D 重叠和 D 负载满足条件时尝试候选比例，按 batch bucket 观察 Decode GPU 步时间的平滑值，变慢超过容许范围就回退。它是一个有限候选的反馈控制器，内部步时间用于调节资源；客户端 TPOT 和尾延迟仍由服务压测评估。不同策略互斥配置，便于比较各自效果。

**切换的难点是旧 stream 可能还有工作。** 如果直接改 Runner 主 stream，下一轮 Decode 可能在新 stream 上越过上一轮，读取尚未生成的 token 或 KV；如果临时捕获新 Graph，又会引入明显停顿。因此 Worker 按实际 CU mask 保存 stream 和 Graph manager，启动时预热实际需要的候选策略。

运行时先在旧主 stream 记录 event，再让新 stream `wait_event()`，随后切换主 stream、Graph manager 和策略 epoch。这样旧工作可以继续完成，后续批次按依赖排到新 stream，主机不用等整个设备空闲。TP 下策略通过有序 RPC 下发，各 rank 后续 batch 都排在本地策略操作之后，P 侧用汇聚后的 ACK 确认策略已应用。

这个协议保证角色内部顺序。过渡期间两侧仍可能有旧策略工作，P/D 各自按批次依赖切入新策略。手动变更采用 drain 路径，等授权与在途工作收尾后同步设置；auto 和 constrained 使用已预热的 advance 路径，减少运行停顿。

**ROCm 的 Graph 需要额外适配。** HIP 的 CU-masked stream 是 blocking stream，不能直接用于 PyTorch capture，因此提供独立 capture stream，replay 由选中的角色 stream 提交。执行器同时设置 `DEBUG_HIP_FORCE_GRAPH_QUEUES=1` 和 `DEBUG_HIP_GRAPH_SEGMENT_SCHEDULING=0`，处理 Graph 队列与 launch stream 的 CU mask 行为。

最终评估看三件事：P/D 是否实际重叠推进，Decode 步时间和客户端生成间隔是否改善，以及 Prefill 吞吐、TTFT 是否付出过大代价。资源控制的作用是 **在并发收益和相互干扰之间调整配额**，不是给所有负载固定一组最优比例。

源码：[constrained 与 auto 下发](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/engine.py#L131-L177)、[ROCm Graph queue 配置](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/executor.py#L41-L73)、[策略预热](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/executor.py#L190-L215)、[有序 stream 切换](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/worker.py#L80-L168)、[auto 控制器与 mask](https://github.com/tangzzycc/vllm/blob/e3e07d9732a0c6f951117f0c125c76f9e9370baf/vllm/v1/rapidserve/resources.py#L10-L151)。

## 九、怎样验证实现正确，性能结果如何解释？ {#performance-validation}

### 1 分钟简答

我把验证分成 **生命周期正确性、多卡与共享状态、真实模型运行、Serving 性能** 四层。

正确性重点看取消和迟到完成时 KV 是否提前释放、TP 是否等待全部 rank、DeepSeek 是否残留 meta 引用，以及共享初始化和退出是否安全。真实运行再检查完整 Prefill/Decode、生成长度、取消和 shutdown。

性能比较固定硬件、模型精度、TP、KV 容量和输入输出长度，扫描并发，同时看吞吐、TTFT、TPOT 和尾部生成间隔。再用 GPU trace 和消融分析双执行组、P budget、CU 策略与 Graph 的作用。本地最新实现已跑通，性能结果符合预期；解释收益时重点落在 **长 Prefill 对已有 Decode 的影响，以及吞吐与生成速度的取舍**。

### 5 分钟详细阐述

这个项目涉及共享显存和异步执行，所以我先验证正确性，再讨论性能。最需要防范的错误是状态看起来已经结束，但旧 GPU 工作还在访问缓存；也可能模型参数已导入，执行对象却仍握着 meta 引用。

**第一层是请求生命周期。** 测试覆盖 P lease 存在时 blocks 不释放、其他请求的 D 仍能被调度、旧 session/sequence 完成不能影响新授权，以及首 token 就达到停止条件的情况。取消后不交付输出，最后一次使用完成后缓存可以重新分配。

异步 Decode 还需要检查多轮在途：两轮已提交时，第一轮完成不能释放 KV，必须等计数归零。这里关注的是可观察的调度与空间复用行为，直接对应真实运行的读写安全。

**第二层是多卡完成和模型导入。** 完成聚合测试先提供 rank 0 响应，确认整体还没有 ready；最后一个 rank 返回后才允许交接，同时检查 RPC 错误传播。共享测试检查已有 KV 绑定不额外分配、不同 dtype 视图正确恢复、FP8 标记和参数槽位一致、MLA 权重不重复处理，以及 router bias 指向真实 tensor。

退出测试则检查消费者先于拥有者关闭，并覆盖编译对象保留 tensor 的情况。这些测试验证协议与状态；真实 GPU IPC、TP 通信和 Graph 行为还需要目标设备运行。

**第三层是完整模型与服务。** 在目标模型、精度和 TP 配置上，从初始化到 Prompt Prefill、连续生成、取消、shutdown 跑完整条链，观察有没有残留 meta、错误设备映射、死锁和地址布局问题。生成对照需要固定采样参数、检查实际输出长度，并结合任务质量判断；不同 kernel 和执行顺序可能带来数值差异，单次文本对照只是一部分证据。

**第四层是同配置的 Serving 对比。** 基线使用常规 MRV2 混合调度，实验组使用 paired 执行。固定 GPU、模型 revision、权重和 KV dtype、TP、KV 容量、最大请求数、输入输出长度和采样参数，完成预热后扫描并发。paired 额外记录 P token budget、P 请求数、chunking、CU 策略和 D Graph 配置。

指标按用户体验和系统能力一起看。**TTFT** 包含排队、Prefill 和首次输出前的等待；**TPOT** 看首 token 后的平均生成间隔；尾部流间隔观察卡顿；吞吐衡量单位时间完成的工作。HTTP 流式响应可能打包多个 tokens，客户端收到一次 SSE 的间隔和 GPU 单步时间需要分别解释。

吞吐也要明确口径：请求数/秒、输出 tokens/秒、输入加输出总 tokens/秒，以及是否除以 GPU 数。长输入本身会增加总 token 计数，所以不能只看到总吞吐提高，就判断用户生成更快。比较时保留相同长度分布，并与输出速度和延迟一起分析。

并发扫描可以使用固定在途请求数的闭环方式，一个请求结束后补入下一条，得到不同工作点的吞吐与生成速度。要观察随机长请求到达对已有生成的影响，还需要混合负载与开放到达测试。并发数表示服务中的请求数，其中可能有排队或 Prefill 请求，不能直接当作 GPU batch 大小。

**结果解释再回到执行机制。** 用 trace 查看长 Prefill 区间内 D 是否仍有多轮执行，比较常规混合调度、paired 全 CU 和 paired 分区；进一步控制 P budget 与 Graph 配置，观察各项影响。这样才能区分独立组批带来的推进机会、资源分配减少的争用，以及 Graph 降低的提交开销。

长输入混合负载下，主要目标是减少 Prefill 对生成间隔的干扰；高并发时还要观察资源分配是否改善争用。一侧较空时，全 CU 可能更有利。P/D 仍共享设备资源，生成速度改善也可能伴随 TTFT 或某侧吞吐变化，所以应比较整条曲线，而不只选一个最高值。

本地最新实现已经完成复现测试，性能结果符合预期。当前结论和适用范围围绕 **单机 TP、驻留文本模型、greedy 生成及已支持的 DeepSeek 格式**。后续扩展缓存复用、动态专家重排或其他并行组合时，需要继续验证两侧共享布局和请求状态的一致性。
