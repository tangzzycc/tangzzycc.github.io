# Data AML 多模态推理算子优化：面试问题与回答

从 2026-10-12 本轮提问开始，记录用户提出的面试问题及对应回答。面试回答用于直接口述，详细分析补充关键机制与追问要点。

## 1. CUDA GEMM 算子的一般实现与优化思路是什么？

### 面试回答版

我一般按访存、复用和流水线三层优化。先保证 warp 合并访存，再用 shared memory 分块复用 A/B，让每个线程在寄存器里计算多个输出。之后调整 tile 和布局，用预取重叠搬运与计算；精度允许时使用 Tensor Core。最后根据实际 shape 平衡复用、寄存器和并行度，用 profiler 与同配置计时验证收益。

### 详细分析

1. **合并访存与向量化。** 相邻 lane 尽量访问连续地址，减少内存事务；`float4` 等向量化减少单线程搬运指令，两者都需要满足布局、对齐和边界条件。
2. **分块复用。** 每个 block 负责一个输出 tile，将 A/B 的 K 分块搬入 shared memory；每线程再计算多个输出，通过寄存器外积复用 operand，并增加独立累加器。
3. **布局与流水线。** 用 warp tiling、padding/swizzle 匹配计算阶段的读取；预取下一 tile，让搬运与当前计算重叠。同步要保证“写完才读、读完才覆盖”，增加 stage 也会增加资源占用。
4. **按 shape 选参数。** 大 tile 提高复用，但增加寄存器/shared memory，可能降低驻留并行度或产生 spill；小 M/N、长 K 时可以评估 Split-K，但要计入归约成本。Tensor Core 路径需要重新匹配 fragment 布局。
5. **验证与融合。** 用同精度 cuBLAS/cuBLASLt 作基线，结合设备计时和 profiler 定位瓶颈；融合 bias、activation、residual 可减少中间访存，但要保持归约与数值语义。

扩展阅读：[CUDA GEMM 优化笔记](../../../gpu-kernel/GEMM-CUDA-Core优化.md)。

## 2. AMD RDNA 上 HIP WMMA GEMM 算子的实现与优化思路是什么？

### 面试回答版

RDNA 使用 WMMA 矩阵乘累加指令。以我的 gfx1151 实现为例，一个 wave32 协作计算 `16×16×16`，输入 BF16、累加 FP32。小 M、窄 N 时，我让多个 wave 分担 K，在 LDS 合并结果；另一条 tiled 路径让 wave 分担输出列，共享 A，优化搬运和 LDS 布局。CDNA 使用 MFMA，通常由 wave64 协作。两者都围绕分块复用、预取和资源平衡，但 fragment 布局、指令性能和硬件资源不同，迁移时需要重新设计数据搬运、tile 和流水线，再用 profiler 验证。

### 详细分析

1. **WMMA 与 MFMA。** RDNA 的 WMMA（Wave Matrix Multiply-Accumulate）和 CDNA 的 MFMA（Matrix Fused Multiply-Add）都是 wave 级矩阵指令。上述 WMMA 是 BF16 `16×16×16`、wave32；MFMA 常用 wave64，有多种矩阵形状和精度，需按具体架构选择。
2. **小矩阵沿 K 分工。** FlashRT 的 `M=10,N=32,K=1024` 投影用四个 wave 各算 K=256，再在 LDS 合并 FP32 partial，占 4 KiB。这样增加组内并行，不需要 global atomic；输出 grid 仍只有两个 workgroup。
3. **Tiled 路径共享 A。** 每个 wave 负责不同的 16 列，协作搬入 A/W，复用同一 A tile。权重预转置让 K 方向连续；16-byte global 搬运、LDS padding 和 barrier 分别处理搬运效率、bank 映射与同步。当前 FlashRT tiled 路径是单缓冲。
4. **迁移到 CDNA 要重做布局与参数。** Wave32 改为 wave64 后，输入/累加器的 lane 映射、LDS 访问和输出写回都不同；还要按 MFMA 的吞吐、延迟和寄存器/LDS 预算重选 tile、wave 数与 stage 数。不能只替换指令或照搬 padding。
5. **调优与正确性。** FlyDSL 的工作是在已有 GEMM 上按 gfx1151 的设备规模和 shape 调整 tile policy。实际执行保留 hipBLASLt fallback，并验证完整 wave 参与、tail、BF16 舍入和端到端收益；不能把局部算子加速直接当作模型加速。

扩展阅读：[FlashRT WMMA 实现](../../../gpu-kernel/flashrt-rdna35/07-SmallM-WMMA-GEMM-Kernel.md)、[FlyDSL tile 策略](../../../gpu-kernel/flydsl/FlyDSL-1057-RDNA3-GEMM-Tile-Policy.md)、[CDNA MFMA 示例](../../../gpu-kernel/flydsl/03-四个示例读懂FlyDSL.md)。

## 3. AMD 与 NVIDIA CUDA GPU 的内存层次有什么共同点和差异？

### 面试回答版

两者都可以按寄存器、共享片上存储、cache 和 global memory 来理解。CUDA 的 shared memory 对应 AMD 的 LDS，都是 block/workgroup 内显式管理的数据复用空间；global memory 通常由显存承载，访问经过对应的 cache 路径。AMD 的特点是显式区分 lane 私有的 VGPR 和 wave 共享的 SGPR，而 cache 拓扑、共享存储与 L1 的组织也和 NVIDIA 不完全相同。优化原则相通：合并访存、提高片上复用、减少 bank conflict，并平衡寄存器/LDS 占用和并行度；具体容量和参数要按目标架构调整。

### 详细分析

| 层次 | NVIDIA CUDA | AMD HIP | 共同用途与主要差异 |
| --- | --- | --- | --- |
| 寄存器 | 每线程寄存器；部分架构另有 uniform register | VGPR 保存 lane 私有值，SGPR 保存 wave 统一值 | 保存 operand、累加器和地址；超预算可能 spill |
| 显式共享存储 | Shared memory | LDS，HIP 同样用 `__shared__` | block/workgroup 内复用与交换数据，需要同步；容量和 bank 访问规则依架构而变 |
| 硬件 cache | L1、L2 等 | 向量/标量 cache，部分架构有 L0/L1，再到 L2 等 | 自动缓存，不能机械地逐级对应；容量、共享范围和访问策略不同 |
| Global memory | 通常在 GDDR/HBM 中 | 独立 GPU 通常在 GDDR/HBM 中，集成 GPU 可使用系统 DRAM | 保存模型权重、输入输出等，通过合并访存和复用减少流量 |
| 线程私有的内存后备 | CUDA local memory | AMD scratch/private memory | 用于 spill 等，通常由设备内存承载；不是 shared memory/LDS |

1. **Shared/LDS 与 cache 的管理方式不同。** Shared/LDS 由 kernel 显式加载、安排布局并同步，适合可预测的 tile 复用；cache 自动管理，不能将命中视为正确性保证。
2. **物理组织影响资源取舍。** 很多 NVIDIA 架构的 L1/shared 共享片上存储池，可配置容量分配；AMD LDS 通常与 cache 分开组织，但仍限制 workgroup 驻留。迁移时需重新估算资源，不能沿用固定大小。
3. **SGPR 强调整个 wave 的统一状态。** AMD 可用 SGPR 保存统一的指针、循环边界等；lane 各不相同的数据使用 VGPR。实际分配由编译器决定，也不能说 NVIDIA 完全没有统一寄存器机制。
4. **名称与物理内存要分清。** CUDA local memory 是线程私有地址空间，AMD LDS 的 local 指 workgroup 共享片上存储，二者不对应。UMA 集成 GPU 共享系统内存也不代表访存、cache 和同步没有成本。

扩展阅读：[AMD GPU 内存与硬件模型](../../../gpu-kernel/flashrt-rdna35/00-AMD-GPU硬件模型与术语.md)。

## 4. CUDA Graph 的加速原理是什么？

### 面试回答版

普通 eager 执行会由 CPU 逐个分发算子、提交 GPU kernel。CUDA Graph 先记录一段 GPU 操作及其依赖，实例化后通过一次 graph launch 重放，省去重复的 Python、框架分发和逐 kernel 提交开销，减少 GPU 等待 CPU 的空隙。它特别适合执行结构稳定、包含大量短 kernel 的推理，例如小 batch Decode。Graph 本身不会自动融合算子或减少计算量；输入内容可以变化，但常规 replay 要保持被捕获的地址和执行结构稳定。

### 详细分析

1. **执行过程。** 先 warmup，再通过 stream capture 或显式建图记录 kernel、memcpy 等节点和依赖，实例化可执行图，后续反复 replay。计算仍在 GPU 上执行，重放的是操作与依赖，不是上一次结果。
2. **省掉什么。** 常规 replay 绕过被捕获区域的逐算子 host 执行，降低提交成本与 kernel 间 CPU 空隙；图中通常仍有多个 kernel，不能说变成一个融合 kernel。
3. **为何小 Decode 常受益。** 短 kernel 的提交开销占比高，更容易受 CPU 供给速度限制；大 GEMM 已由 GPU 计算主导，Graph 收益可能较小。Eager 的同 stream kernel 也无需逐个同步，收益来自减少提交，而非移除不存在的同步。
4. **动态输入与限制。** 常见做法是固定输入 buffer、更新内容，并为不同 batch 捕获 buckets、配合 padding。数据相关的 CPU 控制流和同步等会限制捕获；Graph API 可更新部分节点参数，但不是任意 shape 都能直接重放。捕获、显存与 padding 也有成本。

扩展阅读：[CUDA/HIP Graph、Compile 与 Fusion（第 10.12 节）](../vllm-pd/03-性能证据与面试问答.md)。

## 5. torch.compiler / torch.compile 是什么？与 CUDA Graph 有什么区别？

### 面试回答版

`torch.compiler` 是 PyTorch 编译相关功能的命名空间，常用入口是 `torch.compile`，用于编译模型或函数。在常见默认路径中，TorchDynamo 捕获 Python 执行中的 tensor 计算图，TorchInductor 做图优化与代码生成，比如融合逐元素算子、减少中间访存；训练还会涉及 AOTAutograd。Compile 主要优化计算的实现，CUDA Graph 主要优化重复提交，两者可以结合。编译收益取决于算子、shape 和 backend，首次编译、graph break 和重编译也有成本。

### 详细分析

1. **入口与流程。** 常用 `compiled_model = torch.compile(model)`。Dynamo 通过 Python frame/bytecode 机制提取 FX 图并建立 guards，Inductor 通常为 GPU 生成 Triton kernel，或调用现有高效库；不能说整个模型都会变成一个 Triton kernel。
2. **加速来源。** 比如 `y = relu(x + bias)` 可融合成一个 kernel，减少一次 launch 和中间结果写读；还可优化调度、布局与内存复用。大型 GEMM 可能仍调用 cuBLAS 等库，收益需看完整执行链。
3. **动态图的代价。** Shape、dtype 或控制条件变化可能触发 guards 失败与重编译；不支持的 Python 行为可能造成 graph break，默认情况下图段与 eager 交替执行。动态 shape 支持可以减少部分重编译，但不是所有控制流都能捕获。
4. **与 Graph 配合。** 常见顺序是先编译优化，再捕获稳定的 GPU 执行进行重放；某些 compile 模式和后端会使用 CUDA Graph。`reduce-overhead` 模式可在适用条件下尝试通过 CUDA Graph 降低 Python 开销，具体行为依版本和 backend，不代表所有模型必然使用 Graph。

| 技术 | 主要优化对象 | 是否自动融合算子 |
| --- | --- | --- |
| CUDA Graph | 重复的 CPU 分发、提交和 GPU 等待空隙 | Graph 本身不自动融合 |
| torch.compile | 捕获图的实现、生成代码和数据流 | 编译后端可进行融合 |

扩展阅读：[PyTorch torch.compile](https://docs.pytorch.org/docs/stable/generated/torch.compile.html)、[torch.compiler](https://docs.pytorch.org/docs/stable/torch.compiler.html)。

## 6. FlyDSL 是什么？它与 CuTe 有什么共同点？

### 面试回答版

FlyDSL 是面向 AMD GPU 的 Python Kernel DSL，通过 MLIR 和 LLVM 生成设备代码。它与 CuTe 的共同点是用 Layout 描述坐标、线程和数据的映射，再用 Copy/MMA atom 组合搬运和矩阵计算。这样可以用更高层的表达组织 tile，同时控制寄存器、LDS 和硬件指令。区别主要在目标硬件与后端：FlyDSL 面向 AMD 的 WMMA/MFMA，CuTe 属于 NVIDIA CUTLASS 生态；其中 CuTe DSL 是 Python 接口，CuTe 本身也有 C++ 模板实现。

### 详细分析

1. **Layout 是核心。** 用 shape/stride 和组合、分块、分区等操作表达“哪个坐标对应哪个地址、哪个线程持有哪些值”。Layout view 的变化本身不代表实际搬运数据。
2. **Copy/MMA atom 对应底层操作。** Copy atom 表达搬运方式，MMA atom 表达矩阵指令及 fragment 分布；TiledCopy/TiledMma 将它们扩展到更大 tile，让搬运和计算的数据布局匹配。
3. **抽象相似，硬件约束不同。** AMD 的 wave、LDS 和 WMMA/MFMA 与 NVIDIA 的 warp、shared memory 和矩阵指令不同，迁移仍需核对布局、同步和流水线。
4. **编译路径。** FlyDSL 用 Python 构造并编译 GPU 程序，同一 specialization 可复用编译产物；不能将它与 Python eager 执行等同，也不能把所有 CuTe 实现都说成同一条 MLIR 编译链。

扩展阅读：[FlyDSL 编程模型与编译流程](../../../gpu-kernel/flydsl/01-FlyDSL编程模型与编译流程.md)、[Layout 与 Tile 编程](../../../gpu-kernel/flydsl/02-Layout代数与Tile编程.md)。

## 7. 简历中的 Fused RoPE kernel bug 如何产生，如何修复？

### 面试回答版

这个 bug 出在 wave32、head dimension 为 96 的路径，有两个问题。旧实现按 `ceil(96/32)` 选择每 lane 三个元素，但三个 BF16 是 48 bit，底层 copy/shuffle 路径无法完整表示和重建，导致编译错误。我把向量宽度限制在原生的 1、2、4、8 中，这里选 4，使用 24 个 lane。随后两半各占 12 个 lane，旧 XOR 配对又不成立，所以对非二次幂跨度改成前半加 12、后半减 12。最后对照 Q/K 和 KV cache 验证数值，并检查原有维度的生成指令未改变。

### 详细分析

1. **Kernel 的职责。** 对 Q/K 应用 NeoX RoPE，并把旋转后的 K 与原始 V 写入 cache。NeoX 将前半元素 i 与后半元素 `i+D/2` 配对，V 不参与旋转。
2. **向量宽度错误。** 旧 width=3 的跨 lane helper 按 32-bit word 重建，`3//2=1` 只能还原两个 BF16，出现 `(2,)` 与 `(3,)` 的形状不匹配。新宽度还须整除 D 和 D/2，并满足 `D/width≤wave_size`；D=96、wave32 因此选 width=4。
3. **Lane 配对错误。** Width=4 时每半 12 lane。比如 lane 4 的伙伴应为 16，但 `4 XOR 12=8`。修复对二次幂跨度保留 XOR，其他跨度按前后半区显式加减；四个 BF16 按两个 32-bit word 交换后重建。
4. **验证范围。** 已有 PR 记录覆盖 FP16/BF16 和两种 cache layout，对照 Q、K、key/value cache；D=64/128/256 在 gfx1151 上的 ISA 保持一致。D=96 旧实现无法运行，因此这是正确性修复，没有可报告的旧版相对加速。

扩展阅读：[Fused RoPE D=96 修复笔记](../../../gpu-kernel/flydsl/FlyDSL-1113-Fused-RoPE-Head-Dim-96.md)、[FlyDSL PR 面试问答](../开源贡献面试-FlyDSL-PR.md)。

## 8. AMD Instinct MI355X 的关键规格及其对推理的意义是什么？

### 面试回答版

MI355X 是 AMD CDNA 4 数据中心加速器，单卡有 288 GB HBM3E、8 TB/s 显存带宽，BF16/FP16 稠密矩阵峰值约 2.5 PFLOPS，FP8 约 5 PFLOPS，支持 MXFP4/MXFP6。它有 256 个 CU、1024 个 Matrix Core，通过 Infinity Fabric 连接其他 GPU。推理中显存决定模型和缓存容量，带宽影响权重及 KV 读取，矩阵算力影响大 GEMM；MoE 跨卡执行还要考虑互联和负载均衡。峰值规格不能直接换算成模型 token/s。

### 详细分析

以下为 **2026-10-12 核对的 AMD 官方单卡规格**，算力均为理论峰值。用户原提问的“MI335X”已确认为 MI355X。

| 项目 | MI355X 参数 |
| --- | --- |
| 架构与计算资源 | CDNA 4；256 CU；1024 Matrix Core；16,384 stream processors |
| 显存 | 288 GB HBM3E，峰值带宽 8 TB/s，支持 ECC |
| Last Level Cache | 256 MB |
| BF16/FP16 矩阵算力 | 稠密 2.5 PFLOPS；结构化稀疏 5 PFLOPS |
| OCP-FP8（E4M3/E5M2）矩阵算力 | 稠密 5 PFLOPS；结构化稀疏 10.1 PFLOPS |
| MXFP4 / MXFP6 矩阵算力 | 各 10.1 PFLOPS，需采用对应 microscaling 格式 |
| FP32 / FP64 算力 | FP32 157.3 TFLOPS；FP64 78.6 TFLOPS |
| 峰值时钟与功耗 | 2.4 GHz；典型板功耗 1400 W |
| 模块与主机接口 | OAM；PCIe 5.0 ×16 |
| GPU 互联 | 7 条 scale-up Infinity Fabric link，官方峰值 153 GB/s/link；另列 1 条 scale-out link、128 GB/s |

1. **三种带宽分开。** 8 TB/s 是卡内 HBM 带宽；Infinity Fabric 用于 GPU 间互联；PCIe 是主机接口。官方 link 峰值不等于实测 collective 带宽，比较时还需统一单/双向和拓扑口径。
2. **稠密、稀疏和 dtype 分开。** 结构化稀疏峰值要求满足硬件支持的模式；MXFP4/MXFP6 也需要对应数据格式和执行路径，不能用最高数字描述普通 BF16 GEMM。
3. **容量不等于速度。** 8 卡标称合计显存为 2304 GB，但需要并行切分才能使用；实际吞吐还受 shape、有效 batch、量化、通信、KV 和调度影响。

来源：[AMD MI355X 官方规格](https://www.amd.com/en/products/accelerators/instinct/mi350/mi355x.html)。

## 9. DeepSeek-V3 的结构和参数量是什么？

### 面试回答版

原版 DeepSeek-V3 是采用 MLA 和 DeepSeekMoE 的自回归 Transformer，主模型总参数约 671B，每 token 激活约 37B。它有 61 层、隐藏维度 7168，前 3 层是 Dense FFN，后 58 层是 MoE；每个 MoE 层有 256 个路由专家，每 token 选 8 个，另有一个始终执行的共享专家。MLA 用低秩 KV 表示降低缓存开销，训练还使用 MTP。37B 代表每 token 的激活规模，部署通常仍需保存全部专家权重。

### 详细分析

以下对应 **原版 DeepSeek-V3**，依据官方仓库及模型配置，不将 V3.2 等后续版本混入。

| 项目 | 参数 |
| --- | --- |
| 主模型参数 | 总计约 671B；每 token 激活约 37B |
| 层数与隐藏维度 | 61 层；hidden size 7168 |
| FFN 结构 | 前 3 层 Dense，后 58 层 MoE；SwiGLU |
| MoE 专家 | 每层 256 routed experts，Top-8；1 shared expert |
| FFN 中间维度 | Dense 18432；单专家 2048 |
| MLA | 128 个 Query head；Q 低秩维度 1536；KV 低秩维度 512 |
| Attention head 维度 | Q/K 内容维度 128、RoPE 维度 64；V 维度 128 |
| 词表与上下文 | 词表 129280；官方报告上下文 128K |
| MTP | 官方完整权重另含约 14B MTP，合计约 685B |

1. **MoE 降低激活计算，不按同样比例减少显存。** 每 token 只执行 Top-8 路由专家及共享专家，但不同 token 可能选择其他专家。仅按主模型参数粗算，BF16 权重约 1.34 TB、FP8 约 671 GB，还需计入未量化参数、scale、MTP、KV 和 workspace。
2. **MLA 压缩 KV。** 常见压缩缓存保存 512 维 KV latent 加 64 维解耦 RoPE Key，即每层每 token 576 个元素；Q latent 不进入历史 KV。收益需结合具体 backend 的压缩缓存与矩阵吸收路径。
3. **路由与 MTP。** 原配置使用 sigmoid 分数、分组限制和负载均衡策略；MTP 是多 token 预测训练目标，相关模块可用于投机解码，不代表普通自回归推理默认每次输出多个 token。
4. **优化重点。** MLA Attention、FP8/Grouped GEMM、路由与 gather/scatter，以及 EP dispatch/combine。37B 激活量不能单独预测吞吐，因为 batch 会改变实际触及的专家数量与通信。

官方报告的 128K 上下文与 HF 配置的 `max_position_embeddings=163840` 是不同口径，回答标称上下文时使用 128K。
