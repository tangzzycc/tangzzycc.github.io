# W4A4 与稀疏元数据：指令形状、Scale 和 Bitmap

<div class="study-notes study-analysis" markdown="1">

来源：提供的「腾讯 AI Infra 部门二面」「小鹏汽车三面」「阿里平头哥一面」记录；对应 GPU与算子优化[第 19～21、52 题](../index.md#q50)，并复用[第 3、8～12、15～18、49 题](../index.md#q16)的量化与流水线知识。

## 1. W4A4 不能替代完整计算约定 {#quantization-contract}

- <strong class="study-key">存储编码。</strong> INT4 的 signed/unsigned、FP4 的编码及 bit 打包要明确；4 bit 位宽不足以决定解码方式。
- **量化参数。** 每 tensor、channel 或沿 K 分组的 scale/zero-point 需要与 kernel 匹配；动态激活 scale 归约与转换也是成本。
- **乘法与累加。** 支持的 INT4 MMA 常用 INT32 累加，再缩放/转换；FP4 路径按其浮点与 block-scale 约定计算。
- **零点。** 若表示为 `s(q−z)`，整数乘加后还涉及零点修正；分组 scale 变化时也不能把整个矩阵用统一 scale 处理。

低 bit 的容量收益与计算收益需分开验证；已经置零但仍用稠密 kernel 执行，不会自动获得跳过工作的收益。

### INT4 解包、符号扩展与累加上界怎么检查？

一个 byte 的低/高 nibble 可分别取得 `u=byte&15`、`v=(byte>>4)&15`。二进制补码 signed INT4 的 code 8～15 表示 −8～−1，可用 `q=u<8?u:u−16` 解释；不是将 15 当成正整数 15。若量化使用 0～15 加非零 zero-point，解码规则又不同。

对 signed INT4，两个 −8 相乘为 64，长度 K 的同号最坏原始点积可达 64K，INT32 容量是否够要按 K 和约定数值范围计算。实际还需考虑零点修正、分组缩放与输出转换。INT32 累加避免了逐项低精度浮点舍入，但不消除输入量化误差，也不代表任意 K 不会溢出。

单位测试式的手算可以先选一个 byte 包含负/正边界值，再验证每个逻辑 K 位置的 scale 和稀疏索引。若 packed 内存沿某个轴重排，两个相邻 nibble 未必是原矩阵相邻 K 元素；scale 与矩阵 lane 映射需要一并解释。

## 2. M16N8K64 只给出逻辑运算形状 {#mma-shape}

`A[16,64]×B[64,8]→D[16,8]` 是逻辑形状，不是完整 GEMM 的限制，也不是线程/block 数。读取完整 mnemonic 才能判断 fragment、dtype、稀疏模式和元数据。

PTX 的一个稀疏 INT4 示例为：

```text
mma.sp.sync.aligned.m16n8k64.row.col.s32.s4.s4.s32
```

其中 `.sp` 表示需按规定压缩 A 并提供稀疏位置元数据，`s4` 为有符号 4 bit 输入，`s32` 为对应输出/累加类型。它不是“只要任意稀疏就能使用”的指令。CUDA WMMA 接口与 PTX MMA 指令族也不是同一层，不能仅凭记录中的 WMMA 名字确认此路径。

## 3. Bitmap 与硬件稀疏元数据分开理解 {#bitmap-layout}

| 格式 | 描述内容 | 消费方式 |
| --- | --- | --- |
| 自定义元素/tile Bitmap | 哪些元素或 tile 存在、需要执行 | 软件解码、计算压缩偏移并调度工作 |
| 硬件 MMA 稀疏元数据 | 固定结构化组中非零元素的位置 | 按指令规定布局由稀疏 Tensor Core 路径消费 |

假设 4 bit bitmap 描述 4 个 K 方向 tile，`0101` 表示保留 tile 0、2，压缩数据按 tile 顺序存储。第 i 个保留 tile 的紧凑偏移可由更低位 set bit 的 popcount 得到；这是教学编码，不是记录中项目格式，也不等于 2:4 稀疏位置编码。

Bit 密度、tile 密度和元素非零率不同。一个只剩少量非零元素的 tile 仍可能需要完整 tile 的矩阵运算；元数据读取和不规则负载也会抵消节省。

### Bitmap 怎样恢复逻辑位置和压缩偏移？

固定区域包含 8 个 tile，bit i 表示 tile i 是否存在，假设 bitmap 为 `00101001₂`，即 tile 0、3、5 保留。紧凑存储依次放这三个 tile。访问逻辑 tile i 前先检查 bit i；若存在，它在紧凑数组的位置为 `popcount(bitmap & ((1<<i)−1))`。例如 tile 5 的紧凑位置是 2，因为较低位中 0、3 两位为 1。

跨区域还有一层偏移：每个区域紧凑块数不同，需要区域起始指针或对前面 bitmap 的 popcount 做 prefix sum。Bitmap 只回答哪些位置存在，起始表回答本区域数据从哪里开始；缺少其中一项就不能任意随机寻址。

如果描述的是整 tile 的存在性，一个保留 tile 内的零值仍可能参与 dense MMA；若描述元素，则解码更细但 irregular gather 更多。压缩省掉的载荷必须覆盖 bitmap、前缀偏移、popcount、分支、解包和负载偏斜，不能把“1 bit 比 32-bit 索引小”直接当加速证明。

## 4. 什么时候适合低 Bit 稀疏路径？ {#lowbit-workload}

- **匹配模式。** 权重或激活有可稳定利用的稀疏模式，精度校准能满足任务要求，目标硬件支持相应计算。
- **足够工作。** 保留 tile 有足够复用和矩阵工作，能摊薄解码、scale 与 launch；小矩阵可评估 Split-K，但归约成本必须计入。
- **流水线。** 索引、低 bit 数据和 scale 要一起正确供数；double buffering 复用槽位前，必须确保所有依赖已完成。
- **验证。** 固定实际量化/剪枝后的模型与负载，先检查数值和质量，再看元数据流量、有效矩阵工作、延迟与端到端收益。

原记录的“4 Tile 对应 1 Bitmap”只作为格式设计的线索；`split key`、`LSBD` 未给出准确含义，不据此编造算法。可确认的 Split-K 与双缓冲基础已在[Kernel 流水线](03-Kernel流水线与矩阵计算.md)中整理。

## 5. 低 Bit 下如何控制索引成本？ {#metadata-cost}

一个 4-bit 非零值若对应一个 32-bit 列索引，单索引载荷是数值载荷的 8 倍，还未计行指针与 scale。可评估块/tile 共享索引、局部偏移、bitmap+popcount 等方案；收益要同时计块内零值、寻址、负载偏斜和供数成本，不能只比文件大小。

INT4 常将两个 4-bit 值打包进一个 byte；解包需掩码/移位，对 signed INT4 正确符号扩展，并按逻辑 channel/group 对齐 scale。稀疏索引决定哪份压缩数据属于哪个逻辑位置，单纯连续加载压缩值并不能恢复矩阵语义。

## 6. 跨端侧平台验证 W2A4/W4A4/W8A8 {#platform-validation}

1. 明确位宽之外的编码、scale、zero-point、稀疏布局、累加与输出 dtype。
2. 核对具体芯片代际、SDK/backend 和完整指令。W2 打包存储可能先扩展为 INT4/INT8/浮点输入，不代表存在原生 W2A4 MMA。
3. 用量化后的数学参考验证 kernel，覆盖符号、边界、尾 tile、分组 scale 和稀疏模式；再与原始模型比较任务质量，分开实现错误与量化误差。
4. 用代表性 Prefill/Decode shape 测真实 kernel、元数据/转换流量、总内存与端到端延迟，并记录持续功耗、温度和频率。

不根据 Orin/Thor 的产品名字承诺支持矩阵格式或倍数加速；原生格式、软件解码和反量化到浮点是不同执行路径。

### 怎么区分量化算法误差、加载错误与执行错误？

先用原始 FP 模型评估任务质量，再用软件量化参考表示同一编码/scale，测算法误差；真实 kernel 与该量化参考比较，检查符号、尾组、索引与累加；真实模型若继续偏离，则逐层检查 checkpoint 转换、packed layout、融合与状态。直接用最终自由生成文本无法分离这些原因。

目标平台的执行支持还要落实到完整指令和生成代码。W2 的存储可能扩成 INT4/INT8，INT4 权重可能反量化到 BF16，低 bit 激活可能增加运行时 scale 归约；这三类路径都不能由 W2A4/W4A4 标签确定。Prefill、Decode 和持续功耗分别测，避免只用某个小矩阵峰值证明完整部署加速。

## 7. 反量化独立执行与融合的取舍 {#fused-dequantization}

独立反量化把压缩权重转换成高精度中间张量，再交给 GEMM，会增加写回/再读和容量，但可以复用反量化结果或使用成熟 kernel。Tile 内融合解包、scale 和计算可减少中间流量，代价是寄存器、解码指令、布局和流水线复杂度。

分组 scale 沿 K 改变时，整数部分和需按所属 group 正确缩放，零点也需要相应修正，不能把所有部分积统一乘一个 scale。使用 Triton/CUDA/CUTLASS 是实现选择，不自动改变数学约束或保证编译出所需 MMA；确认实际指令和融合边界后计时。

对一份 P 元素 INT4 权重，独立转成 FP16 的稳态路径至少读 P/2 bytes 压缩值、写 2P bytes 中间权重，再由 GEMM 读 2P bytes；不计 scale、cache 与其他访问时，共约 4.5P bytes。融合路径不物化完整 FP16 权重，可避免其中的中间写回和再读，但跨 CTA 的复用与反复解包会改变真实流量。

!!! note "沿 K 分组的缩放位置"
    若两组部分积为 a、b，scale 产品分别为 s₁、s₂，输出应为 `s₁a+s₂b`。除非 s₁=s₂，不能先得到 a+b 再乘某一个 scale。融合 kernel 需要让 group 边界与累加/缩放步骤对应，不能只在最后增加一次乘法。
