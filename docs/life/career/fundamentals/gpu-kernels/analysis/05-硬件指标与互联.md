# 硬件指标与互联：容量、算力、带宽和选型

<div class="study-notes study-analysis" markdown="1">

来源：提供的「算能科技二面」记录；对应 GPU与算子优化[第 55～56 题](../index.md#q23)。记录中的具体卡型和采购选择提炼为通用选型方法。

## 1. 三种资源分别限制什么？ {#capacity-compute-bandwidth}

| 指标 | 主要问题 | 评估方式 |
| --- | --- | --- |
| 显存容量 | 能否容纳模型、上下文和并发 | 权重、KV、激活、workspace、通信缓冲及运行余量 |
| 矩阵计算吞吐 | Prefill 等大矩阵处理速度 | 匹配 dtype、shape、稠密/稀疏口径和实际 kernel |
| 设备显存带宽 | 权重与历史 KV 的读取速度 | 实际字节流量、复用与达到的带宽 |
| 卡间互联 | TP/EP/P/D 的交换成本 | collective、消息大小、拓扑和有效带宽 |

例如 32B 参数按 BF16 存储，纯权重约 `32×10^9×2=64 GB`，还没计 KV 和运行空间。INT4 的理想权重载荷约 16 GB，实际需加 scale、对齐及未量化部分；容量判断不能只用理想载荷。

容量判断可拆成 `权重+活动KV+激活/工作空间+Graph及runtime保留+安全余量`。权重通常随副本数复制，KV 随活动请求和历史增长；TP 分片与模型结构决定每卡比例，不能只用“参数量×每参数字节”宣称模型能部署。

算力影响可以并行执行的矩阵工作，设备内存带宽影响权重/KV 供给，互联带宽与延迟影响多卡交接。两张卡总算力相同而每卡容量、拓扑不同，可能只能运行不同 TP 配置，最终比较的已经是不同执行路径。

## 2. 算力与带宽要连到工作负载 {#workload-roofline}

- <strong class="study-key">沿用 Roofline。</strong> `I=F/Q`，计算上界为 `min(P_peak,BW×I)`；F 为运算量，Q 为对应存储层的实际字节流量。
- **典型差异。** 大 Prefill 有更多权重复用，小 batch Decode 常需要更好的数据供给；长上下文又可能让 KV 主导。
- **产品比较。** 同一型号家族的不同形态也可能有不同互联、功耗和容量。比较 RTX、数据中心 GPU 或自研加速器时，先明确 SKU 与软件支持，再比较满足服务目标的性能和成本。

## 3. PCIe 拓扑为什么重要？ {#pcie-topology}

- **路径。** 同一交换机、跨 root complex、跨 CPU/NUMA 的路径不同；P2P 可达性、路由和平台配置都要实测。
- **共享。** 多个 GPU 可能共享上行链路，集体通信也可能与 KV 搬运争用链路；双向标称值不能直接当单向有效值。
- **部署。** TP 需要频繁归约，EP 常有多目标交换，P/D 可能搬大量 KV。独立副本的层内通信较少，但模型容量、MoE 组通信和缓存交接仍要单独判断。

### PCIe 的标称带宽为什么不能直接代入推理预测？

链路代际和 lane 数决定编码后的理论通道能力，但有效载荷还受协议、包大小、DMA、软件提交及拓扑限制。多卡共享交换机上行时，两条独立传输会争用同一链路；跨 root complex 或 NUMA 时，还可能经过 CPU 互联或 Host 暂存。GPU/GPU P2P 与 Host/GPU H2D 的可用路径也不相同。

因此一张“峰值 GB/s”表不足以描述 TP 小消息归约、EP 多目标交换和 P/D 大块 KV 搬运。应按真实源/目标对、消息尺寸、并发数和方向测曲线；全双工总和不能当作一次单向拷贝的带宽。链路较慢但模型能单卡放下时，增加独立副本可能比增加 TP 更合适，前提是单请求延迟与容量满足目标。

## 4. 如何证明选型合理？ {#hardware-validation}

固定模型、精度、长度分布和到达率，比较容量、TTFT、TPOT、尾延迟、goodput 与单位成本。用实际 kernel 和 collective 测试解释结果；框架、算子、量化格式和运维支持也是能否部署的条件。
