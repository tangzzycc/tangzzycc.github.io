# 推理框架：请求流程、职责与优化边界

<div class="study-notes study-analysis" markdown="1">

来源：提供的「科大讯飞二面」记录；对应推理优化[第 1～2、10 题](../index.md#q8)。

## 1. 一个请求的执行闭环 {#request-lifecycle}

- <strong class="study-key">入口。</strong> 解析协议、应用模板、tokenization 和采样参数校验；有路由层时选择目标实例，预处理位置依部署而变。
- **调度与执行。** 请求进入队列，Scheduler 安排本轮 token 与缓存资源；执行侧准备张量、位置和 Attention 元数据，完成模型计算与采样。
- **状态与输出。** 更新已计算进度、生成 token 和停止条件，前端解码并流式返回。资源回收需等所有在途访问达到安全边界。
- **可选路径。** Prefix cache、投机解码、多模态和 P/D 会增加状态与依赖；Router 不一定是每个框架实例内部的固定模块。

沿请求 `[A,B,C]` 跟踪状态：入口产生 token IDs 和采样条件；Scheduler 判断剩余计算长度，给它分配物理 KV 页，并把“本轮算哪些 token、位置是什么、历史在哪”交给 Worker。Worker 准备位置与 block table，执行前向和采样；完成信息回来后，Scheduler 才推进已计算长度和输出状态，前端再返回 token。

例如一个 chunk 只算了 A/B，C 尚未完成，请求可能已占有 KV 空间，但还不能按完整 prompt 的最后位置采样首 token。**队列状态、已计算进度、已分配容量和数据就绪是四个不同事实。**
{.study-mechanism}

取消也要经过这个闭环：停止未来调度不代表已提交 GPU 工作马上停止。物理页和输入缓冲只能在所有在途访问结束后回收，否则其他请求复用页时可能读到迟到写入。

## 2. 三类职责 {#role-boundaries}

| 角色 | 主要决策或动作 | 依赖的信息 |
| --- | --- | --- |
| Router | 选择服务实例、转发与负载分配 | 健康状态、排队、预计负载、缓存局部性 |
| Scheduler | 决定本轮请求集合与 token 工作量 | 请求进度、预算、KV 可用空间和执行依赖 |
| Worker / 执行侧 | 持有模型与设备资源，准备并执行 GPU 工作 | 调度计划、模型参数、真实 KV 与元数据 |

这是架构职责，具体类、进程和采样位置因版本而异。逻辑 block ID 指明存储位置，真实 K/V 在设备张量中。

### Scheduler 为什么必须区分已生成、已计算和本轮计划？

请求可保存 token 序列、已计算数量、物理块映射、采样/停止状态，以及本轮计划的 token 区间。Prefill 只完成一部分时，已分配的块不一定都包含有效数据；刚采样的新 token 已在输出列表中，但它自身 KV 可能要下一次 Decode 才生成。用一个“长度”代替这些进度，会在 prefix reuse、投机与 P/D 中发生偏移错误。

Scheduler 输出的是控制计划：请求 ID、要计算的位置、token 预算与缓存映射；Worker 执行真实读写并报告完成/采样结果。Block ID 是本进程缓存池索引，不能跨 worker 当成指针。异步执行下，计划已提交也不等于完成，状态推进与回收需要清楚的完成边界。

### 异步调度为什么不能提前释放本轮 KV？

CPU 准备下一轮时，GPU 仍可能读取当前页。若 CPU 看到请求将结束就立刻把页交给另一请求，新旧 kernel 的读写可能重叠。可以先标记逻辑结束、停止后续计划，再等待在途访问安全完成后进入可复用池；取消、抢占与失败也应采用一致的生命周期。

相关问题的具体图形状与执行约束见[Graph 和异步调度](15-芯片适配与执行优化.md#graph-fusion)。这里描述通用职责，不绑定某个框架版本的类名或进程数量。

## 3. 框架优化与 Kernel 优化 {#system-vs-kernel}

- **算子。** 固定 shape 下减少访存、计算或同步成本；结果首先体现为单次 kernel 时间变化。
- **系统。** 改变请求组批、资源管理与关键路径等待；也可能改变实际 shape 和 kernel 调用次数。
- **归因。** 若算子占关键路径比例 p、加速 s 倍，其他成本固定时整体理想加速为 `1/((1−p)+p/s)`；排队与并发变化还需服务实测。

Kernel 优化固定算子输入，把一次执行做快；框架优化决定有多少次执行、什么 shape、等待多久以及资源是否可复用。例如 prefix cache 减少实际 Prefill token 数，Continuous Batching 改变活跃 batch，Graph 缩短 CPU 提交间隙。它们会改变 kernel 面对的负载，所以孤立算子加速比例不能直接乘到服务吞吐上。

判断瓶颈时先看完整时间线：排队、CPU 准备、GPU kernel、collective、KV IO 分别占哪一段关键路径，再深入对应 kernel。只看总 GPU utilization 容易把“没有及时提交工作”和“提交后算子供数低效”混在一起。
