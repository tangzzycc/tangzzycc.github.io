# 组批与收益验证：Continuous Batching、Mix Chunk 和路由基线

<div class="study-notes study-analysis" markdown="1">

来源：提供的「百度昆仑芯一面」「百度基模团队一面」记录；对应推理优化[第 12、22、81～82 题](../index.md#q76)，并复用已有 TTFT/TPOT、Chunked Prefill、P/D 配比与缓存路由知识。

## 1. Continuous Batching 动态更新执行集合 {#continuous-batch}

固定生成 batch 中，短请求先完成后可能留下空位，后续工作受长请求拖累。Continuous Batching 在模型迭代边界移出已完成请求、加入新请求或 Prefill 工作，按 token/KV 预算组织下一轮。

例如 A、B、C 共同 Decode，B 完成后下一轮可让 D 入场；D 的 prompt 如何处理，还取决于 chunk、混合组批或单独 Prefill 的调度。Continuous Batching 不意味着每轮都必须包含 Prefill，也不是在运行中的 kernel 任意插入请求。

与入场前攒批的动态组批相比，它在生成过程中持续重组执行集合。有效吞吐仍受新请求等待、KV 容量、长短请求、公平性与同步边界影响，批越大也可能让 TPOT 变慢。

普通请求级动态组批在开始执行前积攒一批请求，常见直观模型是在这一批结束后再形成下一批；Continuous Batching 则在模型迭代边界让已结束请求退出、新请求进入。例：A 要生成 2 token、B 要生成 5 token，A 完成后留下的位置可让 C 加入，而不必等 B 的 5 token 全部完成。

新请求可能还需要 Prefill，其 token 数与老请求 Decode 的一行不相同，因此真实 Scheduler 不只是替换槽位，还要安排 prefill/decode token 预算、KV 空间与就绪依赖。活跃集合更新也意味着每轮 shape、位置与页表可能不同，Graph 分桶和输入准备必须一起适配。

## 2. Mix Chunk、Chunked Prefill 与 P/D 分离 {#mixed-chunk}

记录里的 Mix Chunk 未给出框架定义，此处按“Prefill chunk 与 Decode 混合调度”理解：

| 策略 | 改变的边界 | 可能收益 | 可能代价 |
| --- | --- | --- | --- |
| Continuous Batching | 迭代中的请求集合 | 填补完成空位、改善利用率 | 调度与资源约束，合批扩大可能拉长迭代 |
| Chunked Prefill | 单 prompt 每轮推进粒度 | 限制长 Prefill 占用，增加调度机会 | 更多提交和历史访问，小矩阵效率下降 |
| Prefill/Decode 混合 | 同轮执行的工作组成 | 控制干扰并复用执行资源 | 大 chunk 仍会拖长 Decode，资源竞争 |
| P/D 分离 | 两阶段执行资源池 | 独立配置、隔离与扩缩容 | KV 交接、额外副本、配比与排队 |

不存在固定“Mix Chunk 必然推高 TTFT、降低 TPOT；P/D 必然均衡改善”的结论。应明确原基线、chunk/batch、到达率、模型与互联，再分别测 TTFT、TPOT/ITL、吞吐和 goodput；两类机制还可以结合。

### Mixed batch 的 TPOT 为什么可能改善，也可能回退？

一个 iteration 中加入少量 Prefill 行，可改善权重 GEMM 的 M 和数据复用；如果这些行成本可控，整体设备利用可能提高。但老 Decode token 要等该 iteration 的全部依赖路径推进，过多 Prefill 或长历史 Attention 会拉长 ITL。Chunking 缩短一次 Prefill 独占，仍留下共享 HBM、SM 和通信竞争。

与 P/D 比较应固定总卡/成本与相同输入输出、到达率、缓存条件。Mixed 没有跨侧 KV 交接，却共享资源；分离隔离调度与阶段资源，却有传输、重复权重和配比损失。两者可结合，没有通用“TTFT 一定升、TPOT 一定降”的方向。

## 3. 不同基线的百分比为何差很多？ {#baseline-gap}

轮询不看即时负载，可能让长请求和缓存热点造成排队；Load-only 已解决多数负载偏斜，混合路由相比它只剩缓存局部性的增量收益。

例如轮询 TTFT P99 为 1000 ms、Load-only 为 203.42 ms、混合策略为 200 ms：

- 相比轮询下降 `(1000−200)/1000=80%`。
- 相比 Load-only 下降约 `(203.42−200)/203.42=1.68%`。

这些教学数字复现记录中的比例，不代表项目实测。结论应是要检验大部分收益是否来自负载均衡，以及约 3.42 ms 的增量是否超出波动，不能把两项降幅相加或据此断言缓存没有价值。

## 4. 如何验证 P50、长尾与吞吐？ {#latency-validation}

1. 固定模型、精度、硬件预算、长度/前缀分布、到达率与采样口径；比较轮询、仅负载、仅缓存、混合路由。
2. 定义客户端时间戳、TTFT/TPOT/ITL 与吞吐口径，统计拒绝、失败与排队；不能只保留完成的快请求。
3. 报告 P50/P95/P99、SLO 达标率和 goodput，记录样本数与重复实验波动；P99 对样本量和突发很敏感。
4. 分解排队、未命中 Prefill、恢复/交接、Decode 干扰与各实例负载，解释机制。
5. 扫描到达率、冷热缓存和突发。封闭式客户端的并发测试与独立到达的在线流量不同，不能互相替代容量结论。

逐请求时间数据可用于配对分析，P99 数值本身却不表示两组中的同一个请求。不要用一次低样本测量证明很小的百分点提升稳定成立。

### 为什么只统计完成请求会让高负载结果失真？

若策略把超时、拒绝或尚未完成请求排除，剩下短而容易的请求 P50/P99 可以看起来很好，但实际成功供给下降。固定测量窗口要记录提交、完成、失败、拒绝与在途，并说明停止生成条件和输入输出 token 口径。长尾估计也依赖足够样本，不能用少数请求声称稳定 P99 改善。

开放到达过程下，客户端按预定速率持续提交，可以观察服务积压；闭环客户端每完成一条才发下一条，会在服务变慢时自动降低到达率，可能掩盖排队。对比路由/调度需固定到达方式，不能让某策略承受不同的实际负载。

## 5. 长 Prompt 的收益边界 {#prefix-length}

长且可复用的前缀通常节省更多 Prefill；短输入、低复用、远端恢复昂贵或排队主导时，局部性收益可能小。输入总长度、实际共享前缀长度、缓存层级和当前实例负载都应分桶。

记录中的平均 52K 输入与 8K 边界是特定场景的线索，不是通用阈值。用多种长度与命中比例扫描，检查缓存节省是否覆盖路由、搬运与偏斜成本；新模型、硬件或到达率可能改变交叉点。

### 为什么不存在通用的 8K 或 52K 收益阈值？

长度只是工作代理，净收益取决于相同前缀实际减少的 Prefill、缓存恢复、目标排队、后缀历史访问与资源竞争。更快的 Prefill kernel 或更慢的 Host/网络会移动恢复阈值；高共享、低队列与长重复前缀更有机会，低重复或热点严重时可能回退。

因此面经里的长度与百分比是特定 workload 的观测。应沿长度、共享比例、到达率和缓存层级扫曲线，再解释哪项成本发生变化。路由与恢复要共同建模，具体增量比较见[Load-vs-Recompute](20-RadixCache与分层恢复.md#load-vs-recompute)。
