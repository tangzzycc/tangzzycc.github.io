# 框架选择与并行部署：vLLM、SGLang、P/D 和通信

<div class="study-notes study-analysis" markdown="1">

来源：提供的「英特尔校招面经」；对应推理优化[第 25、65、75、84 题](../index.md#q63)。保留可解释的设计维度，具体能力按使用版本与模型/backend 核对。

## 1. vLLM 与 SGLang 比较什么？ {#framework-comparison}

| 维度 | 比较内容 | 常见误区 |
| --- | --- | --- |
| KV 存储管理 | 分页、缓存池、分组、回收和特殊模型状态 | 将分页与前缀复用当作互斥方案 |
| 前缀复用 | Cache key、匹配索引、粒度、淘汰与调度 | 认为只有 SGLang 支持前缀缓存 |
| 请求调度 | token 预算、chunk、组批、抢占、公平性 | 不固定配置就宣称某框架延迟更低 |
| 执行后端 | 模型、Attention/MoE kernel、低精度与 Graph 路径 | 用支持名单推断每种组合都同样成熟 |
| 分布式部署 | TP/DP/EP、P/D、connector 和路由 | 将部署生态与单实例运行时混为一层 |

vLLM 的代表性设计是 PagedAttention 与分页 KV 管理；SGLang 论文中的 RadixAttention 用 radix tree 组织可复用前缀，并结合相应调度。理解这两个代表性设计，要先区分物理存储与逻辑复用。

SGLang 的早期论文包含前端语言与运行时，如今比较 Serving 时还应明确用户是在比较程序接口、运行时还是外部 Router。最新能力和默认开关可能变化，代表性设计不意味着独占某功能。

验证应固定模型、精度、输入输出长度、前缀共享、到达率、硬件及并行配置，比较质量、容量、TTFT/TPOT、goodput 和运维约束。对差异做单因素验证，不能把论文中的峰值加速直接当当前部署结论。

### PagedAttention 与 RadixAttention 为什么可以同时存在？

分页是物理存储机制：请求逻辑 token block 通过 table 映射到离散页，降低连续分配和尾部浪费。Radix 索引是逻辑复用机制：按兼容 token 前缀识别已经计算的状态，再引用其真实页/槽。一个系统完全可以用 radix tree 查前缀、用分页池保存数据，二者处理不同层次。

比较框架时，沿同一请求问四个问题更具体：如何识别可复用前缀；如何把活动 KV 分配/回收；本轮如何安排 prefill/decode 工作；执行后端支持哪些布局与状态。相同功能名也可能有不同 page 粒度、驱逐、抢占、Graph 与多 rank 协调，不能用某个代表性论文标题概括所有现代行为。

## 2. P/D 两侧并行配置分别建模 {#pd-parallel}

- <strong class="study-key">P 侧。</strong> 输入长度、缓存命中与到达率决定工作；TP、本地 GEMM 效率、chunk 和副本数一起影响 TTFT 与容量。
- **D 侧。** batch、历史长度、输出长度与 KV 容量决定服务能力；过大 TP 的通信和小矩阵可能抵消收益，DP 扩展并发也需负载分配。
- **MoE。** 分别画出 Attention DP/TP 与专家组；例如已整理的 vLLM EP 路径使用 `EP=DP×TP`，不能再把 EP 乘进设备数。
- **预算。** 两侧权重、副本、KV、运行缓冲与网络都需计入，固定总设备或成本，再扫描配置与 P/D 配比。

P/D 分离迁移请求阶段，TP 分片层内计算，DP 提供副本，EP 分布专家；它们作用的边界不同。更多并行度不是通用最优，容量、互联和 SLO 可能给出不同限制。

若 P 的 Attention 使用 TP=4，而 D 用 TP=2，每个目标 D rank 可能需要合并两个源 rank 的 head 分片。GQA/MQA 可能还有复制，MLA 等布局也不同。源页编号、head 分组、层布局和 quantization scale 不一定与目标一致，所以传输不只是按总字节一次 memcpy；必须核对 connector 是否支持两侧布局，并明确重新分片、目标落点及同步成本。

MoE 的 P/D 侧还各自选择 Attention DP/TP、专家 EP 与专家内部 TP。扩 P 的输入能力不一定能扩 D 的历史带宽，跨侧 EP 组通常也不能简单复用同一 collective 身份。固定设备预算后，先验证容量和组兼容，再比较层内通信、KV 交接和服务目标。

## 3. 通信方式不是同一层次的选项 {#transport-layers}

| 对象 | 所在层次与作用 | 推理中需核对什么 |
| --- | --- | --- |
| PCIe | 主机/设备和设备间互联总线 | P2P、交换机、root complex、NUMA 与共享上行 |
| NVLink/NVSwitch | NVIDIA 系统的高带宽互联与交换组织 | 卡型与系统拓扑、实际 GPU 路径；不能一概等同同节点 |
| RDMA | 网络远程访问注册内存的机制 | NIC、网络、注册、拥塞及传输完成协议 |
| GPUDirect RDMA | 支持的 NIC 可访问 GPU 内存的路径 | GPU/NIC/驱动与拓扑支持，设备数据可见性 |
| NCCL 等 | 组织 collective 的通信库 | 算法、调用 shape、消息大小与实际 transport |

一条跨节点 GPU 传输可以同时经过 PCIe、RDMA 网络和 GPUDirect 路径；GPUDirect RDMA 减少 CPU/主机内存暂存，不表示完全没有主机控制，也不消除 GPU 内存及网卡带宽成本。

NVLink 可用于 GPU 间互联，RDMA 常用于节点间通信，但不能把产品/系统拓扑差异抹平。无 P2P 或不满足直接访问条件时，实际路径还可能经过主机暂存，需由 profiling 与通信测试确认。

### RDMA 完成为什么还不等于整个请求可开始 Decode？

RDMA 依赖注册/可访问内存、源目标地址和相应传输权限；GPU 直访还需 GPU/NIC/驱动及拓扑支持。数据传输完成只满足数据路径的一部分：目标还必须建立正确的页映射、有效长度、模型/scale 布局和执行可见性；源 allocation 也要保留到安全完成。

控制消息可以很早到达，但不能据此认为 GPU 数据已经到达；反过来数据落地也不代表 Worker 已把请求纳入 Scheduler。确认的顺序和所用完成接口要按 connector/runtime 契约实现，不能用普通主机布尔值代替设备同步。

## 4. TP 与 EP 偏斜从哪里来？ {#tp-ep-skew}

| 比较点 | 常规 dense TP | EP |
| --- | --- | --- |
| 逻辑工作 | 同一批 token 的不同矩阵分片 | 不同 token 被路由到不同专家 |
| 偏斜来源 | 形状/分片、硬件、通信路径、rank 到达 | 路由热度、专家放置、入口负载，再叠加硬件因素 |
| 主要证据 | 每 rank 计算、通信与到达时序 | 每专家 token 数、每 rank 计算、dispatch/combine 与等待 |
| 常见处理 | 合理分片、设备与拓扑、定位慢 rank | 重新映射、热点复制、组批及执行优化 |

等分形状只说明逻辑工作相近，TP 仍可能有尾部或设备偏斜；EP 中即使专家等大且均分，token 数也可能变化。专家内部再用 TP 时，两者可同时出现；不能用“TP 一定均衡、EP 一定不均衡”代替实际诊断。

资料：[SGLang 论文 §3 RadixAttention](https://arxiv.org/html/2312.07104v2#S3)、[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)、[NVIDIA GPUDirect RDMA](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html)。查阅日期 2026-10-13；框架具体行为以部署版本为准。
