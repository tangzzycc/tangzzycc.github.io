# P/D 分离：阶段隔离与 KV 交接

<div class="study-notes study-analysis" markdown="1">

来源：提供的「科大讯飞二面」「小米基模组一面」「阿里平头哥一面」记录；对应推理优化[第 17～21、24、66 题](../index.md#q17)。

## 1. 分离改变什么？ {#pd-boundary}

- <strong class="study-key">执行边界。</strong> P 侧处理 prompt，D 侧持续生成，通常各有调度与设备资源；可以分别配置 batch、并行策略及资源数量。
- **主要收益。** 隔离大 Prefill 对 Decode 的干扰，并按输入、输出负载独立扩缩容。
- **与切块不同。** Chunked Prefill 在迭代间分摊 prompt 工作；P/D 分离把阶段交给不同执行实例，两者可同时使用。

独立跨设备部署让 P、D 各有模型执行与 KV 池，P 可偏向大 token batch 与矩阵效率，D 可偏向小迭代与稳定生成。需要衡量的是隔离后消除的干扰，能否覆盖复制权重、KV 交接和独立队列带来的成本。

同设备的双进程/双执行队列解耦也属于阶段调度边界变化，但数据可以经受控共享映射交接，不一定经过网络。它仍需同步、生命周期与设备资源竞争管理；同 GPU 上同时提交 P/D，不代表计算与带宽已经物理隔离。

## 2. 为什么不保证更快？ {#pd-cost}

- **交接下界。** 传输时间至少受 `KV 字节数/有效传输带宽` 限制；假设 512 MiB、有效 50 GB/s，仅载荷传输约 10.7 ms，不含排队与同步。
- **利用率。** P/D 配比不合适会让一侧排队、另一侧空闲；独立实例还通常各自保留权重和缓存池。
- **公平比较。** 固定总资源或成本、模型、负载与精度，比较 TTFT、TPOT、尾延迟与 goodput，不只报某一侧 kernel 时间。

与混合执行相比，可把收益理解为 `减少的阶段干扰与排队−新增交接与利用率损失`。输入很短、输出很长时，Prefill 本来占比小，分离后可能浪费 P 资源；输入很长且在线 Decode 严格要求短迭代时，隔离价值更大，但交接 KV 也更多。缓存命中还会缩短 P 工作，原先按无缓存估计的配比可能失衡。

如果 P 先返回首 token，交接等待可能主要体现在首 token 后的间隔；如果 D 必须就绪后才返回首 token，则会直接进入 TTFT。应标出 t_first 和各阶段完成时间，不能用一个统一的 TTFT 公式归因所有实现。

## 3. 通信与调度开销 {#communication-scheduling}

- **数据。** KV 复制占互联或网络带宽，也可能争用 GPU 内存带宽；布局、精度或并行配置不一致时还要转换。
- **控制。** Router 选 P/D，D 预留空间，两侧交换进度和完成信息；超时、失败、取消与重试需维护身份和所有权。
- **关键路径。** P 返回首 token、D 重算采样边界或等待交接的方式因实现而异；不能宣称所有传输都计入 TTFT，或都能完全隐藏。

### P/D 交接为什么通常需要控制面和数据面两条路径？

控制面协商请求身份、目标执行组、兼容布局、目标页和容量，再通知源/目标何时可传、可执行；数据面实际搬运 K/V 张量或建立受支持的共享访问。Router 可以知道前缀位置和负载，却不必持有所有 GPU 数值，也不应把“已选 D”当作“D 数据就绪”。

一个请求可先进入 waiting-prefill，完成 P 后进入 KV-transit，目标可用后进入 waiting-decode，再参加 D 的 batch。每个等待状态对应不同资源：排队、源引用、目标容量预留、链路或活动 KV。超时应明确释放哪一项，不能删除队列项后就认为全部 GPU 访问停止。

不同 TP 布局还会使源/目标 tensor 分片不同；传输量可能包含重复 KV、scale、重排或未对齐尾块，不只是逻辑前缀载荷。首 token 在 P 还是 D 采样也改变必须交接的执行进度。

## 4. KV 怎样安全交接？ {#kv-handoff}

- **准备。** 对齐模型与缓存契约，协商请求身份、逻辑前缀和目标物理页；本地 block ID 不能直接当作跨实例有效地址。
- **搬运。** 数据传输组件以 push 或 pull 访问实际 GPU 存储，可按层或分片推进；Router 通常传控制信息，不亲自复制 GPU 张量。
- **消费。** 源写入完成后才能传，目标对应层 KV 就绪后才能读取；必须同时保证目标布局和有效长度正确。
- **回收。** 源数据保持到传输安全结束，再释放引用；首 token、采样参数、计算进度和停止状态需要一致交接。

可以用四个事件表达交接顺序：源计算完成 Eₚ；目标分配容量 Eₐ；实际搬运完成 Eₜ；目标开始读取 E_d。正确依赖至少包括 `Eₚ、Eₐ→Eₜ→E_d`。如果按层流水传输，只需保证 D 执行到某一层之前，该层所需数据已经就绪；不代表全部层可以提前自由读取。

!!! danger "共享地址也需要就绪和生命周期协议"
    同设备 IPC 能避免一份实际数据复制，但地址可访问不证明 KV 已写完，也不保证源进程不会提前复用页。**完成事件、有效长度、页映射和引用生命周期必须共同成立。**

源页至少保留到搬运不再访问源或所有共享消费者结束。目标还需知道 prompt/已计算长度、最后 token 与采样进度、adapter/模型契约，以及混合模型的递归或卷积状态。取消和重试要通过请求身份/代际区分迟到完成，防止释放新请求的页。

### 同设备 IPC 怎样避免复制，为什么仍不能省同步？

共享机制让另一个进程取得同一设备 allocation 的有效映射；接收进程的地址值不一定和源相同，且 allocation 持有者要按协议保持存活。模型权重可在兼容执行条件下只读共享，KV 可在明确的生产/消费边界下共享；共享了 allocation 不代表框架缓存 allocator 自动共享页的分配和引用账本。

P 写完一个前缀后，D 才能通过事件/就绪协议读取；D 结束前，源不能把对应页作为其他 P 输出。若两个进程各自认为同一页空闲，就会出现 allocator 层面的双重分配。统一所有权、页代际与完成确认比“传一个 IPC handle”更关键。

### 按层流水传输怎样与 D 的逐层执行重叠？

P 的早层 KV 可以在后层计算期间先传到 D，D 的早层也可在后层仍传输时开始。每层都需同时满足源数据完成、目标页可写、该层传输完成和请求输入边界正确。D 层 i 的输出还要驱动层 i+1，所以早层就绪不证明全模型就绪；数据路径和计算路径共同形成 DAG。

若早层提前计算会让首 token 输入/KV 边界不一致，必须按该实现的重算或采样协议处理。异构 layout、量化格式与混合递归状态可能限制流水粒度，因此不能仅凭“传输按层”承诺全部成本可隐藏。

## 5. Worker 绑定与目标容量准入 {#admission-binding}

固定 P→D 绑定简化连接和数据交接，但某条链路或 D 组繁忙时，其他 D 组即使空闲也不能直接利用。动态目标选择应同时考虑在途分配、活动 Decode、预计历史/输出工作、目标 KV 空间和传输路径。

一种可评估的协议是：筛选兼容执行组→选择目标→登记负载并预留 KV→P 计算与传输→D 就绪后入场→结束后安全释放。不是所有系统都必须在 Prefill 前完成绑定；需说明选择时点、容量担保和失效回退。

到达输出长度未知时，不能只为当前 prompt 预留后认为永久安全；可保守限额、逐步分配并保留抢占/迁移方案。迁移带来状态与数据成本，失败、取消和迟到完成需避免重复释放。Replica 的单位是完整执行组，TP ranks 不分别接独立请求。

队列长度、KV 空间和单位工作成本结合起来才是负载代理；一条长上下文请求可能比多条短请求更贵。已分配但尚未上报的工作也需记账，避免多个 Router 同时选中同一看似空闲目标。

### 目标已经预留容量，取消与迟到完成怎样避免重复释放？

为一次交接记录 request ID、generation、源引用、目标预留页、传输状态与已确认消费状态。取消先禁止新执行，再将仍在途的数据访问标记为待回收；完成消息到达后只释放该代拥有的资源。若 request ID 被重试复用，没有 generation 校验，旧完成可能错误释放新一轮的页。

如果 P 已完成而 D 容量不足，源 KV 可能积压并反向耗尽 P 池。动态绑定应限制在途预留和源积压，同时规划输出增长与失败回退；只看 D 现在的活动请求数不能保证整条链路稳定。
