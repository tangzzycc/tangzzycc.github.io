## 1. TP=2 的“衰减”先定义基线 {#tp-efficiency}

| 指标 | 合理对照 | 能回答什么 |
| --- | --- | --- |
| 单副本执行 latency | 同一请求与负载的 TP=1/2 | 切分与通信是否降低执行时间 |
| 系统 throughput | 固定 GPU 预算下 TP 与多 DP 副本 | 哪种组织提供更多服务容量 |
| 每卡吞吐 | 系统 throughput/设备数 | 资源效率及成本 |
| SLO goodput | 相同延迟约束与 workload | 达标服务能力 |

单卡可运行时，设 t₁=10 ms、TP=2 为 t₂=6 ms，则 latency speedup=10/6≈1.67，按理想两倍缩短归一化的并行效率约 83.3%。这不是“系统吞吐下降 16.7%”的直接证明。

在忽略排队、一次独立工作且设备相同的简化条件下，两份 TP=1 副本合计可约处理 200 单位/s，一个 TP=2 组约 166.7 单位/s；真实 batch、KV、通信与并发会改变曲线。单卡放不下模型时，不能构造虚假的 TP=1 实测基线。

PP 也能用于推理，尤其容量约束、跨节点互联或足够独立工作时。它主要并行不同 micro-batch，不能直接消除单请求 stage 依赖；是否比 TP 合适需测量，而不是“训练才开 PP”。

## 2. 换设备与卡数改变曲线 {#hardware-curves}

新 GPU 改变算力/带宽比、容量、SM 数与执行机制；卡数和 TP/PP/EP 改变本地 shape、通信、KV 复制及任务分配。副本数还会改变组批、路由和共享资源竞争。

可以复用已验证的模型结构与部分缩放参数，但需重新标定关键 shape、完整 forward、通信路径和系统曲线；保留原数据版本并标明预测区间。不能只将原 throughput 乘卡数比，或用峰值算力比缩放全部 latency。

### 换设备为什么连最优 TP 和 batch 都会变？

新设备的计算/带宽比改变 Roofline 转折点，SM 数、shared/register 与矩阵指令改变本地 tile 效率，容量改变可用 batch/KV，互联拓扑改变 collective 成本。原卡最优 TP 对应的 local shape 不一定能给新设备足够任务；增加绝对速度也可能让旧供数、解码和同步成为新主导。

应重新标定代表性 Linear/Attention/MoE、Graph/提交与通信，再验证完整服务；仅按峰值 TOPS 比例缩放旧 latency 会忽略数据与状态成本。相关单 kernel 迁移分析见[架构调参](../../gpu-kernels/analysis/14-GEMM切分与Persistent调度.md#architecture-retuning)。

## 3. 搜索空间通常离散且不保证凸 {#discrete-search}

1. 列出总设备/成本、模型与 KV 容量、格式及并行兼容条件。
2. 明确通信组及实际设备数，筛掉无效 TP/DP/PP/EP 和 P/D 组合。
3. 粗扫 batch、chunk、P/D 配比及并行参数，用同 workload 与计时边界比较。
4. 按 SLO 和成本筛选，保留非支配候选，对附近配置细化并实测确认。
5. 在长度分布、前缀命中、到达率和突发变化下验证边界。

设备数是整数，head/量化分组有可分条件；kernel/Graph 桶、KV 容量和排队阈值会造成阶跃或不连续。某区间的凸近似可帮助局部搜索，但必须验证，不能根据“有拐点”证明全局最优。

网格搜索的成本可用结果缓存、容量剪枝、粗到细扫描或多保真模型控制。候选预估差距接近模型误差时，应测多个点，不让仿真排序的偶然噪声决定最终部署。

### 配置搜索如何处理不连续性能与预测误差？

先按模型容量、head/专家组约束、connector 支持和总资源筛选可行点，再用已校准模型评估 TP/DP/PP/EP、batch、chunk 与 P/D 配比。Tile 分发、Graph 桶、KV 抢占和 collective 算法会导致非平滑变化，不能假设配置变量连续或目标凸。

将候选按成本和 SLO 下的 goodput 比较，保留 Pareto 非支配点；对边界附近或差距小于模型误差的候选，实测复核。预测 TTFT=79 ms 与 81 ms、误差却±5 ms 时，不能仅凭 80 ms 阈值坚定选一个点。最终配置应在真实 workload 的长度与突发变化下检查余量。

## 4. Throughput 不普遍等于 Latency 的倒数 {#little-law}

Latency 是一次工作的停留时间；throughput 是单位时间完成多少工作，可按 requests/s 或 tokens/s，必须先统一单位。

稳态、同边界且数量平均有限时，Little 定律给出：

$$
\bar N=\lambda\bar W.
$$

N 为系统内平均请求数，λ 为平均到达/完成请求率，W 为平均停留时间。只有固定 N 且满足该口径时，才有 `λ=N/W`；并发为 1 的特殊场景才简化为 `λ=1/W`。TTFT 和 TPOT不是完整请求停留时间，不能直接代入请求级 Little 定律。

例如单请求 100 ms，若 10 个独立请求能够同时执行且没有额外竞争，服务率可能达到约 100 请求/s，而非 `1/0.1=10 请求/s`。真实共享 GPU 会改变单请求速度，例子只说明并发的重要性。

Pareto 点不存在另一个所有目标都不差、至少一项更好的配置；前沿不必是一条双曲线。固定成本下先满足 TTFT/TPOT 尾延迟目标，再按 goodput、成本或业务偏好选点，详见 [配比与 Pareto 算例](12-缓存层级与部署配置.md)。

Little 定律在稳定系统及相同边界下写为 `L=λW`，L 是平均在途请求数，λ 为平均完成请求率，W 为平均响应时间。例如平均有 20 条在途请求、平均耗时 2 s，则 λ=10 请求/s，而 1/W=0.5 请求/s；并发使二者不同。

在线负载从提交到完成计时，而离线紧密供给常弱化到达与排队。模型 step latency、请求完成时间、每 token 时间和输出 token 吞吐有不同分子分母，画 Pareto 曲线前必须统一口径。系统持续过载、队列增长时，不能直接套稳态 Little 定律解释瞬时数据。

## 5. 端到端误差与 Online/Offline 的含义 {#online-error}

GPU forward 模型未计 tokenizer、Host loop、CPU 提交、采样、网络或流式输出时，TTFT 可能明显偏乐观。采样可能在 GPU、CPU 或不同阶段，不从图片断言所有首 token sampling 都在 CPU。

误差需统一 trace、到达时间、输入输出长度、缓存冷暖、计时边界与指标分母，再分解差异。图片里的 TTFT≈9%、TPOT≈2%、吞吐≈4% 是原实验描述，不可迁移；高利用率下小服务时间误差还可能放大排队长尾。

这里将 Online 理解为保留更多真实框架/组件与实际 workload，Offline 为虚拟事件加查表；具体项目可能使用不同定义。应明示哪些组件运行、哪些时间是模拟，是否使用实时时钟或虚拟完成事件。更多真实组件可能更慢，也可能遗漏设备竞争，因此不保证自然更准。

图片中的“8 卡一次 4～6 秒”依 trace 请求数、事件数、搜索范围、Host 机器和模型复杂度而变，设备数本身无法确定仿真墙钟时间。内部 AIC 数据不可得时可用公开 profiling、自己的实测或带不确定性的理论模型建立基础仿真，不能据此说外部无法实现此类方法。
