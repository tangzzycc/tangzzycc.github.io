# 芯片适配与执行优化：精度对齐、Graph、KV 量化和重叠

<div class="study-notes study-analysis" markdown="1">

来源：提供的「百度昆仑芯一面」记录；对应推理优化[第 15～16、33、37～38 题](../index.md#q68)。H20 精度对齐与自研芯片适配提炼为通用执行契约，不收录个人项目经历。

## 1. 从最小可运行模型到完整服务 {#backend-contract}

| 层次 | 接入内容 | 要保持的契约 |
| --- | --- | --- |
| Device/runtime | 设备识别、内存、执行队列、事件、数据搬运 | 地址、所有权、异步完成与可见性 |
| 模型与权重 | 网络实现、checkpoint 映射、dtype/量化布局 | 参数语义、位置、mask 与输出形状 |
| 算子/backend | Linear、Norm、RoPE、Attention、MoE、采样 | 张量布局、有效长度、误差与工作空间 |
| 状态与调度 | KV 分配、元数据、组批、抢占、取消 | 每请求进度、缓存有效性与安全回收 |
| 分布式与优化 | collective、P/D、图执行、融合 | rank 组、数据交接及端到端正确性 |

先跑单请求基础前向，再覆盖 Prefill/Decode、不同长度与组批、缓存复用、取消及多卡执行。某芯片有对应矩阵 API，不代表已经支持框架需要的分页 KV、动态图调度或分布式同步。

CUDA Graph 是 NVIDIA 执行机制；自研芯片可能有对应图执行或 command buffer，但不能直接假设接口和捕获约束相同。缺失的优化可以保留正确回退路径，是否可接受由服务目标决定。

### 从数学算子到后端 kernel，中间还需要适配什么？

Checkpoint 需要把张量名、转置、融合 QKV、专家维与 packed 量化布局映射到目标层；执行输入需要位置、有效长度、block table 与采样元数据；kernel 输出又要符合下游 residual、Norm、RoPE 与状态写入格式。只写一个 `matmul` API 不能保证分页 Attention 或多模态路径正确。

可先固定一个短输入，逐层比较相同历史下的中间输出和 logits；再覆盖 Decode KV 追加、变长 packed batch、前缀共享、取消/抢占和混合层状态。每增加 Graph、fusion、量化或通信优化，都要沿同一语义边界验证，否则多项同时变化难以定位首次错误。

后端还需暴露内存分配、stream/event、异步 copy、collective 与图执行能力，并保留 unsupported shape 的正确回退。接口统一方便上层调度，但不能隐藏必须参与资源规划的容量、共享访问和实际复制成本。

## 2. 精度对齐先定位首次误差 {#numerical-alignment}

1. <strong class="study-key">固定参考。</strong> 相同权重、tokenizer/processor、模板、输入、位置、mask 和采样处理；先明确参考 dtype 与容差。
2. **共享历史。** 使用同一输入历史做 teacher-forced 对照，比较算子输出、层中间值与 logits，避免生成分叉掩盖误差起点。
3. **逐层定位。** 检查权重转换、布局、RoPE、归约/累加、量化 scale，以及 fused kernel 的数学边界。
4. **服务验证。** 再覆盖自由生成、长上下文和任务质量；统计 token/logit 差异与质量指标，不只看一条文本。

普通浮点路径改变归约顺序也可能有差异；量化引入另一类误差。采样序列一致、中间数值容差达标与任务质量达标是不同证据。优化阶段每次变更都沿相同边界回归，再独立测量性能。

数值对照可记录最大绝对误差、平均误差、相对误差和 logits 排名；接近零时相对误差会很大，需要稳定分母或联合容差。若两条 logits 只差很小数值，归约顺序的微小变化可能改变 argmax，之后自由生成历史就分叉，后面的差异不再定位最初错误。

Teacher forcing 让两端每步使用相同的正确历史，按层找到首次偏离。先检查 checkpoint 张量名称、转置/packed 布局与 scale，再检查 mask、RoPE 与累加；修复后再测自由生成和任务质量。跨芯片不必要求所有浮点结果 bitwise 相同，但必须定义合理的参考、容差和最终质量标准。

## 3. Graph 减少提交成本，融合减少中间开销 {#graph-fusion}

- **Graph。** 捕获/实例化后重放设备工作，降低短 kernel 的 CPU 提交成本；不自动减少算术量或消除数据依赖。
- **动态请求。** 常按 batch/token shape 捕获若干桶，更新稳定 buffer 的内容与元数据，满足已捕获图的执行约束。Padding、启动 profiling 和图内存需要计入。
- **回退。** 不支持捕获或 shape 不匹配的部分可走 eager 或分段路径；是否可更新 graph 节点取决于具体机制，不能认为图只能用于完全静态请求。
- **融合。** 把可组合算子中间值保留在片上，减少 global 读写和 launch；也可能增加寄存器/shared 压力，或改变数值顺序。

比较 graph/fusion 开关时固定 shape 与负载，分别看首次启动、稳态 kernel 时间、CPU 间隙、显存与最终 TTFT/TPOT。两者作用可互补，不能将各自加速比直接相乘。

!!! note "Graph 优化的是提交路径"
    请求数量和 token 内容可以改变，只要映射到受支持的图形状并正确更新数据。**静态图形状不等于静态请求内容。** 不匹配的 shape 或不支持的算子可用 eager/分段回退；捕获内存、填充浪费和初始化成本也需计入。

### Graph capture、replay 与动态 buffer 的关系是什么？

Capture 记录设备工作及依赖，实例化准备可执行图，replay 重用提交结构；它没有把模型变成“预先算好的结果”。Kernel 的参数、地址和工作形状需要满足该图的契约。常见做法把请求内容写入稳定 buffer，再用 batch/token 桶选择图，同时更新有效长度和 KV 页表。重新分配张量不会让旧图自动追踪新指针；捕获完成后临时张量被释放而地址仍被图引用，会产生生命周期错误。

若 batch=3 使用 4 行桶，第 4 行需要安全的输入与缓存地址，并由有效 mask/元数据排除真实输出和状态更新；不能让 dummy token 分配、改写或释放真实请求 KV。不同桶还可能保留不同 workspace/内存池，实际显存不能只算模型权重和 KV。

### 异步调度与投机接受长度为什么会冲突？

异步调度可在 GPU 执行本轮时准备下一轮的 CPU 计划。普通一 token Decode 的下一轮工作量较易预测；投机验证后接受 0～γ 个候选，下一位置、有效 KV 与输出预算只有完成后才能确定。CPU 提前准备计划时，不能把最大候选长度当已提交长度。可以延迟依赖接受结果的字段、使用安全的设备侧结果传递或回退路径，但必须让所有状态和图输入一致。

Graph 减少 launch 提交；compile 常处理图提取、specialization 与融合；融合减少中间流量。这些优化可协同，也可能受动态控制、算子支持和资源限制，不能把一次 eager→graph 的收益全部归为算术加速。

## 4. KV 量化的写入与读取路径 {#kv-quantization}

选择 K/V 编码、scale 粒度、校准及存储布局；新增状态写缓存时量化，Attention 读历史时解码或用支持的低精度路径计算。Scale 与数据要共同可用，P/D 两侧也需约定相同格式或转换方式。

已有算例中，32 层、8 KV heads、head_dim=128 的 BF16 载荷每 token 为 128 KiB；同配置 FP8 的理想 K/V 主载荷为 64 KiB，实际还需 scale、对齐和未压缩字段。容量减少不等于整体显存或总耗时减半。

验证要覆盖长上下文质量、不同输入分布、每层误差、实际 KV 流量与转换成本。低 bit 权重与 KV dtype 独立，不能从 W4A16 推断 KV 也量化。

### K/V 误差怎样通过 Attention 影响输出？

看单个 Query：q 为 `[1,d]`，K 为 `[S,d]`，V 为 `[S,d_v]`，score `s=qKᵀ/√d` 和概率 a=softmax(s) 都是行向量，输出 o=aV。K 误差 ΔK 先改变 score，再改变概率；在小扰动下有：

$$
\begin{aligned}
\Delta s&=q\Delta K^\top/\sqrt d,\\
J&=\operatorname{Diag}(a)-a^\top a,\\
\Delta a&\approx\Delta s\,J,\\
\Delta o&\approx\Delta a\,V+a\Delta V.
\end{aligned}
$$

J 为 `[S,S]` 的 softmax Jacobian，式中 `Diag(a)` 把 a 的元素放到对角线上，外积 `aᵀa` 与行向量约定一致。这是一阶近似，忽略了高阶扰动及 `ΔaΔV` 交叉项。K 的误差改变权重分布，V 的误差改变被加权内容，不能只看平均 KV 元素误差。

如果多项 score 很接近，小误差也可能改变排序；如果 q 的某些通道幅度大，相应 K 通道误差更敏感。逐层、长上下文和代表性输入质量验证因此必要，不能由 FP8 载荷减半推断任务质量不变。

### Prefix Cache 与可变 per-block scale 怎样协调？

Per-token/head scale 随对应位置保存，读取历史时找到各位置的 scale 即可；per-block scale 若随新增值扩大范围，旧编码也需重算。封闭的共享块需要保持数据与 scale 不变，不能在其他请求仍引用时原地修改。可采用固定尺度、只对新/私有块更新或 COW 等设计，具体选择影响精度和写入成本，必须和缓存 allocator 共同实现。

## 5. 通信重叠必须有独立工作 {#overlap-dependencies}

异步提交通信后，仅推进不依赖其结果的计算，在消费点用事件/完成协议等待。通信 kernel 也可能消耗 SM 和显存带宽，NIC/互联传输也可能与数据搬运竞争。

例如通信原需 4 ms、独立计算需 6 ms，理想重叠窗口可接近 6 ms，但仍有启动/收尾与其他依赖。若并发后计算变为 9 ms，总时间可能只省很少甚至回退；不能从两条重叠 bar 推断隐藏了 4 ms。

检查关键路径、未覆盖等待、rank 到达差异和正常计时。TBO 是提供独立工作的一种组织方式，见 [DP Attention 与 Two Batch Overlap](16-DPAttention与TBO.md)。

资料：[CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)、[vLLM Quantized KV Cache](https://docs.vllm.ai/en/latest/features/quantization/quantized_kvcache/)。具体平台/backend 的支持以部署版本为准。
