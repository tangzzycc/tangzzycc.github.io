# 投机推理：候选、验证、状态修正和收益

<div class="study-notes study-analysis" markdown="1">

来源：提供的「百度昆仑芯一面」记录；对应推理优化[第 45～47 题](../index.md#q78)。模型的 MTP 与半自回归结构见 [MTP 与候选依赖](../../models/analysis/04-MTP与半自回归.md)。

## 1. 为什么验证可以并行多个位置？ {#draft-verify}

普通 Decode 的下一 token 未知，要先采样才能继续。Drafter 先给出候选后，候选 token 已知，目标模型可像一小段 Prefill 一样，按因果 mask 一次计算各验证位置；这并不消除同一位置的因果条件。

1. <strong class="study-key">Draft。</strong> 从已提交前缀提出 γ 个候选，准备相应候选状态。
2. **Verify。** 目标模型计算正确对齐的条件分布，接受候选前缀，在首次拒绝处纠正；全部通过时标准方案还能采样一个额外 token。
3. **Commit。** 提交本轮允许输出的 token，处理 EOS、停止规则和输出预算。
4. **State。** 保留已接受状态，截断/恢复被拒绝后缀，使下次条件与已提交历史一致。

已输出 token 不一定已完成自身 KV 前向，验证输入和 logits 偏移需明确；不能把“候选条数”“已计算 token 数”和“已提交 token 数”混用。

已提交前缀末尾为 t₀，drafter 提出 t₁、t₂。标准验证可把 `[t₀,t₁,t₂]` 作为因果输入：位置 t₀ 的 logits 验证 t₁，位置 t₁ 的 logits 在 t₁ 已接受的条件下验证 t₂，最后位置可采样额外 token。若 t₁ 被拒绝，t₂ 的条件历史不再成立，即使目标模型计算过其位置，也不能提交。

**并行验证利用的是候选输入已知；可输出结果仍是按正确条件通过的连续前缀。**
{.study-core}

验证前缀已有多少真实 KV、第一输入是否已缓存，会改变具体输入组织，但 logits 与候选必须保持一位偏移对应。EOS 或输出预算提前终止时，即使后续候选数学上可接受，也不能继续越界输出。

## 2. 精确采样不能只用命中阈值 {#exact-sampling}

对于标准串行草稿的单位置，设 drafter 的条件分布为 q、目标分布为 p，候选 x 从 q 采样：

$$
P(\mathrm{accept}\mid x)=\min(1,p(x)/q(x)).
$$

拒绝时从归一化的 `max(p−q,0)` 分布采样纠正；全部接受后再从相应目标条件采样额外 token。在适用前提及正确实现下保持目标输出分布，而非保证同一随机种子产生完全相同 token 序列。

Greedy 路径可逐位置比较目标 argmax，接受一致前缀；它与随机采样纠正不是同一个规则。Top-k、top-p、temperature 等需进入正确的条件分布与验证契约。树或并行 proposal 的结构不同，不能不检查前提就照搬串行 q 的公式。

两 token 的简例：目标 p=(0.6,0.4)，草稿 q=(0.8,0.2)。候选 a 的接受率为 0.75，b 为 1；接受 a 的概率为 0.8×0.75=0.6，接受 b 为 0.2，剩余 0.2 来自拒绝 a。纠正分布 `max(p−q,0)` 只在 b 上有质量，所以最终 b 的概率为 0.4，恢复目标 p。

若拒绝后重新从原 p 采样，最终 a 会成为 `0.6+0.2×0.6=0.72`，已经改变分布。这个闭合例子说明纠正规则为什么必要；多位置时需逐位置使用对应条件分布，树 proposal 的规则也要按实际方法推导。

### 拒绝采样为什么精确恢复目标分布？

对单位置离散分布，候选 x∼q，经 `min(1,p(x)/q(x))` 接受，输出 x 的接受质量为 `min(p(x),q(x))`。总拒绝概率为 `R=1−Σ_x min(p(x),q(x))`，也等于 `Σ_x max(p(x)−q(x),0)`。拒绝后按 `max(p−q,0)/R` 采样，则每个 x 的最终质量为 `min(p,q)+max(p−q,0)=p(x)`。

这是标准串行草稿 proposal 的数学证明。R=0 时不会进入拒绝分支；q(x)=0 的位置不会作为 q 的候选，但仍可能出现在纠正分布。多 token 验证必须逐位置使用“已接受前缀”对应的条件 p/q，不能把后缀在错误前缀下的分布拿来提交。

Logits processor 还可能依赖历史，例如重复惩罚；验证第 i 个候选时，应使用前 i−1 个已接受候选形成的历史，不能对整段验证都沿用最初历史。处理后的概率需要符合对应采样算法的 p/q 契约。

## 3. 方案差异沿三个维度判断 {#proposal-types}

| 维度 | 常见选择 | 主要成本 |
| --- | --- | --- |
| 候选来源 | 独立小模型、EAGLE 等隐藏状态 drafter、原生 MTP、n-gram/后缀匹配 | 权重、训练、状态、候选生成时间 |
| 候选结构 | 串行链、并行块、树 | 条件信息、连续接受概率、验证 token 数与 mask |
| 自适应控制 | 固定或动态 draft/verify 长度 | 决策成本、负载变化、浪费的候选与缓存 |

轻量查找在重复代码等场景可能有效，无命中时收益小；模型 drafter 泛化更强，也有额外资源。没有一种方法仅凭名字就对所有 batch、长度和采样策略最佳。

### 为什么 n-gram、MTP、隐藏状态 drafter 的边界不同？

N-gram/后缀匹配从已有重复 token 查找候选，几乎不需要额外模型计算，却依赖文本重复；MTP 使用目标模型训练出的附加预测模块，需权重/表示接口支持；隐藏状态 drafter 基于目标表示提议后续 token，额外模型规模与所用层状态也不同。

候选是串行链还是树，决定 verify 输入、mask、条件分布与 cache 修正。不能把标准串行 p/q 接受式不加前提套给任意并行头或树。比较方法应固定目标模型、采样规则、负载与显存，用连续接受前缀和每最终提交 token 的总成本评价，见[精确验证](17-投机推理与验证.md#exact-sampling)。

## 4. 状态修正是正确性的组成部分 {#state-rollback}

- **目标 KV。** 验证可能写入被拒绝候选的状态，必须修正有效长度、页映射和下次位置，确保不会当作真实历史读取。
- **Draft 状态。** 草稿模型需与提交/纠正后的 token 对齐，不能继续使用过时条件。
- **混合模型。** 递归状态可能被原地更新，不能仅截断 KV 长度解决；需 checkpoint、恢复或重算等支持。
- **系统。** Scheduler 的 token 预算、Graph shape、取消、EOS 与 P/D 状态都要纳入同一生命周期。

标准 KV 可以通过有效长度/页表截断拒绝后缀，但有效长度之外的物理数据并不一定要立刻清零，只要后续绝不会误读并在复用前满足写入协议。递归状态却可能被每个候选原地覆盖，只有最终状态无法自动恢复到较早已接受位置；需要保存中间 checkpoint、恢复后重放或其他支持。

对于同时有 KV、短卷积历史和递归状态的混合模型，回滚必须让所有层看到同一个已提交前缀。只修正 Scheduler 的 token 长度而不恢复算子内部状态，会在下一轮产生不可见的错误历史。
{.study-caution}

### 已接受 token、已提交 token 与已计算 KV 怎样对齐？

候选全部通过时，标准算法还能从目标末位置采样额外 token；它已提交，但自身 KV 通常需要下一轮作为输入才写入。拒绝时纠正 token 同样可能尚未被前向。因此每轮结束要分别记录接受前缀长度、最终输出数、有效目标 KV 长度和 drafter 条件历史，不能把四者都设为一个 A。

EOS 和取消优先限制允许提交的边界，后续算过的候选不因此成为真实历史。有效目标 KV 比最终输出少一个 token 的正常情况，也要与“已拒绝但物理空间仍有残留数据”区分。

## 5. 接受率与总收益不同 {#committed-cost}

若每轮耗时为 draft Td、verify Tv、状态/调度 To，平均最终提交 A 个 token，简单服务成本为 `(Td+Tv+To)/A`。普通 Decode 对照用相同请求负载与边界；有跨轮重叠时需按实际关键路径测量，不机械相加。

例如 Td=1 ms、Tv=5 ms、To=0.5 ms、A=3.5，平均约 1.86 ms/token；若普通 Decode 为 3 ms/token，则这个简化条件下约快 1.62 倍。若实际 A 只有 1.5，则约 4.33 ms/token，反而更慢。

γ 个候选的各位置平均命中率不等于连续接受长度。前面拒绝会让后面的候选无法提交；应报告每轮接受前缀长度、包含纠正/额外 token 的提交数，以及 draft、verify、KV 与端到端时间。

较低 batch、访存受限的目标模型常有验证并行机会；计算已繁忙的高负载也可能回退。最终检查质量、延迟、吞吐/goodput 和显存，不能只追求接受率。
