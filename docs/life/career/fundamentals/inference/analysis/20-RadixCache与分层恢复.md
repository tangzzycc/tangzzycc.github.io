# Radix Cache 与分层恢复：前缀匹配、HiCache 和关键路径

<div class="study-notes study-analysis" markdown="1">

来源：提供的「小米基模组一面」「阿里平头哥一面」记录；对应推理优化[第 30～31、34～35 题](../index.md#q87)，并复用[第 29、36、77～80 题](../index.md#q55)。TerarkKVCache 的仓库和版本未提供，仅提取多级缓存知识，不据名称推断其实现。

## 1. Radix Tree 索引的是连续前缀状态 {#radix-prefix}

普通 trie 可用一个 token 标记一条边；radix tree 将没有分叉的一段 token 压成边标签，节点/边关联实际缓存位置。树通常位于 Host，KV 数据在设备页/槽或其他层，不是把 KV 数值作为树搜索键。

连续例子：

1. 已计算序列 `[10,20,30,40]`，索引中保留其 KV。
2. 新请求 `[10,20,30,50]` 与旧边前三个 token 相同；可将旧边拆成 `[10,20,30]` 的公共段与 `[40]` 后缀，另接 `[50]` 分支。
3. 第三个请求 `[10,20,99]` 最长匹配为 2 个 token，不能跳过 99 后再寻找匹配段。

LCP 是 longest common prefix，不是最长公共子串。标准因果模型中某位置的 KV 依赖前面的完整上下文，相同文本片段处在不同前缀后并不保证 KV 相同。

匹配还需模型版本、adapter、位置、mask 与多模态输入等状态兼容；不能只检查 token ID。存储和复用粒度可能按完整 block 对齐：逻辑 LCP 为 18 token、block 为 16 时，实现可能只复用已完整可共享的 16 token。未完成写入的前缀、部分块和引用锁需按实际策略处理；logits 边界、模型结构和 backend 也可能限制可跳过长度，所以“匹配长度”不总等于“本轮少算 token 数”。

## 2. 插入、引用和驱逐保持数据有效 {#reference-eviction}

执行前固定所使用的前缀节点及实际数据引用。部分匹配可拆节点，插入新结果时更新树和数据映射；完成请求后释放活动引用，允许保留缓存供其他请求复用。

SGLang 论文中的 RadixAttention 使用叶节点 LRU 驱逐，并用引用计数保护活动请求。现代实现可有不同页粒度和驱逐策略，应按部署版本说明，不把论文例子当全部实现约束。

异步加载、写回和跨实例传输也持有引用。逻辑索引命中不代表 GPU 数据就绪，释放源页前必须确认所有在途访问结束；若恢复失败，可使用可用的连续前缀后缀重算或回退完整 Prefill。

### 为什么叶节点驱逐能避免保留一个不可用的长前缀？

Radix 树的子段依赖从根到它的完整前缀。先驱逐叶子可缩短最深冷后缀，同时保留公共前缀供更多请求复用；若任意删中间段却留下后缀，索引可能表示一个无法连续恢复的状态。不同现代实现可按页或成本驱逐，但必须保持可复用连续前缀和数据位置一致。

一个请求使用末节点时，需要保护路径对应数据；节点拆分不应重复分配或丢失原物理页引用。GPU/Host/存储层可分别保留同一逻辑前缀，GPU 层驱逐不代表删除全部目录；加载、传输和正在执行也都是引用来源。索引命中、引用保护与数据就绪应分别检查。

## 3. HiCache 的层级与 GPU Cache 不同 {#hicache-tiers}

| 文档中的软件层级 | 存储位置 | 作用 |
| --- | --- | --- |
| L1 | GPU KV pool | 为执行提供当前可读缓存 |
| L2 | Host 内存 | 保留较大前缀集合并恢复到 GPU |
| L3 | 可选外部存储 backend | 更大容量或跨实例共享，具体介质依 backend |

这里的 L1/L2 是软件 KV 层级，不能与 SM L1 或硬件共享 L2 混淆。Radix 索引识别哪些状态可复用，HiCache 管理不同位置的数据迁移、就绪和容量。

HiCache 文档包含本地匹配、外部存储预取、写回及多 rank 同步。外部 backend、量化和并行支持会随版本变化；不会因为开启分层机制就自动获得任意跨实例共享。

## 4. 比较的是恢复与重算的增量关键路径 {#load-vs-recompute}

设同一新请求可复用前缀 P，后缀 U；在相同入场与服务口径下，比较：

- 重算路径：重新计算 P 及 U 的最终耗时。
- 恢复路径：定位/读取 P 的 KV、准备设备布局，再计算 U 的最终耗时。

恢复成本可包含 L3 读取、Host 暂存、H2D、页映射、同步和队列；层间预取与后续计算能重叠时，计入未覆盖的关键路径，不能重复相加。因 batch、Attention shape 和历史长度变化，节省的 Prefill 不必严格等于孤立运行 P 的耗时。

例如同一口径下恢复增量为 6 ms、重算可省 20 ms，可能有净收益；若争用使恢复变成 25 ms，就不应只为命中而等待。写回若需 12 ms、每次命中净省 14 ms，至少约一次未来命中才可能摊薄该写回成本；预测概率、驱逐和对其他请求的干扰仍需另算。数字是教学成本，不是 HiCache 的实测性能。

设一个可复用前缀为 512 MiB KV，主机到设备的有效吞吐为 25 GB/s，纯搬运下界约 21.5 ms。若恢复前排队 12 ms、元数据准备 2 ms，则串行估计为 35.5 ms；若同边界的重新 Prefill 需要 30 ms，容量命中也可能不值得恢复。若重算需 100 ms，恢复则更有机会节省时间。

!!! note "Load-vs-Recompute 比较增量关键路径"
    缓存载荷除以带宽只是搬运下界。队列、层级读取、H2D、目标空间、重排、以及和其他请求的带宽竞争都会改变恢复成本；比较对象应是同一前缀在当前负载下的重算时间。重叠路径按实际依赖取关键路径，不能总是把所有阶段直接相加。

恢复取消后，已经提交的 IO/拷贝可能仍在进行，目标 block 不能提前分给新请求。缓存淘汰也必须避开正在引用或恢复的源数据；否则节省的重算会变成错误状态或重复工作。

## 5. 预取、写回和驱逐相互制约 {#cache-io}

- <strong class="study-key">预取。</strong> 在有足够命中与收益时提前搬运，控制 bytes、容量和并发。文档列出 best-effort、等待完成和超时等等待策略，各有延迟/命中取舍，默认阈值不作为通用规律。
- **写回。** 提前保存提高未来可恢复性，驱逐时保存减少部分无用写；热点、大小、保存成本与预计复用共同决定策略。
- **驱逐。** 优先考虑无活动引用且可安全回收的数据；快层可释放但慢层仍保留，必须一致更新目录。
- **多 rank。** 各 rank 的分片共同组成逻辑前缀，可复用长度与加载进度需一致。一个 rank 多命中并不代表整组可以跳过更多。
- **服务预算。** 回写和预取不能无限占据活动 Decode 的带宽或可用 KV；高命中率仍可能导致低 goodput。

### 多级缓存的预取为什么需要 admission 和取消协议？

发现远端前缀不代表应该立即搬运。先估计恢复关键路径是否小于重算、目标有无可预留空间、请求何时需要数据，以及现有 IO/H2D 是否拥塞；否则低价值预取会占据更重要请求的链路和 KV。加载状态至少要区分已发现、已预留、读取中、H2D 中、可执行和待回收。

取消只停止后续需求，不保证已提交 IO/拷贝能立刻中止。目标页要等在途写入安全结束再复用；写回也需保护源页，不能边拷边覆盖。对 TP 分片，整组能跳过的前缀要满足各 rank 一致的可用边界，一个 rank 提前命中不足以让整组推进。

### Cache key 为什么要含模型状态，不能仅 hash 文本？

Tokenization、模板、adapter、位置、attention mask 和多模态 embedding 都可能改变同一文本的逐层状态。模型版本或特殊状态语义不同，KV/递归 checkpoint 不可互换。Block hash 可串联前块身份与当前 token 及必要额外字段，radix 则在兼容命名空间内索引 IDs；具体键结构可以不同，兼容语义不能省略。
