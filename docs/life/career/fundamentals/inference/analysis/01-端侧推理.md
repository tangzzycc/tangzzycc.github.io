# 端侧推理：部署约束与性能瓶颈

<div class="study-notes study-analysis" markdown="1">

## 1. 为什么做端侧推理？ {#edge-purpose}

- <strong class="study-key">延迟与可用性。</strong> 本地执行减少网络往返，弱网或离线时也能运行；模型本身的计算时间仍需优化。
- **数据与成本。** 可减少原始数据上传和持续云端调用成本，同时增加设备算力、内存和模型维护需求。
- **决策条件。** 结合任务质量、响应时间、模型容量与设备成本选模型；需要时采用端云协同。

## 2. 端侧与云端部署的区别 {#edge-cloud}

- **资源预算。** 端侧通常受单设备内存、功耗和散热约束；云端通常有更强资源与扩展能力，也受成本和利用率约束。
- **指标。** 端侧关注交互延迟、持续生成速度、内存峰值与每次任务能耗；云端还要关注并发、吞吐及满足延迟目标的有效吞吐。
- **执行方式。** 本地交互常是小 batch；云端可把多用户请求合批，提高权重复用。两种场景都应按实际负载测量。

同一个模型在端侧也可能有两个完全不同的限制：单次交互 batch=1 时，权重读取难以摊薄；长时间持续运行时，功耗/散热导致频率下降。云端则可能通过合批摊薄权重读取，但要承担请求等待和多租户竞争。性能目标应使用实际到达方式、持续时长和功耗预算，而不是只比峰值 TOPS。

统一内存不等于“所有跨设备数据访问免费”。CPU/GPU 的可访问性、缓存一致性、同步协议和访问速度是不同问题；NPU/DLA 还可能要求专用张量布局、连续缓冲区或显式导入。拷贝是否消除要看整个数据路径。

## 3. 怎样定位端侧瓶颈？ {#edge-bottlenecks}

- **先拆阶段。** 区分预处理、Prefill、Decode 和后处理；看 CPU、GPU 计算、搬运与等待分别占多少时间。
- **再查资源。** 小 batch Decode 优先分析权重与 KV 流量；Prefill 分析矩阵形状与计算效率；短 kernel 检查提交空隙。
- **共享内存。** Jetson 等平台的 CPU/GPU 可共享系统 DRAM，省去部分独立显存间搬运，但仍有带宽竞争、缓存和同步成本。
- **持续运行。** 记录功耗模式、频率和温度，区分冷启动短测与长时间负载；容量不足也可能迫使模型卸载或数据搬运。

以一次图像问答为例，先拆为图像解码/预处理、视觉编码、文本 Prefill、持续 Decode 与流式返回。若 GPU 时间线在视觉编码后空闲，CPU 数据处理或跨设备等待可能主导；若 Decode kernel 连续运行但带宽很高，优先看权重与 KV；若每个 kernel 很短且间隙明显，图执行、融合或异步准备才更对症。

持续压测需固定功耗模式并记录频率/温度曲线。初始数秒的性能与达到温度稳态后的性能可以不同，端侧体验更依赖后者。测量还应覆盖进程启动、模型加载与首次编译，和稳定服务分开报告。

### NPU 支持模型，为什么实际端侧延迟仍可能很差？

支持某算子不代表支持模型全部 shape、dtype、layout 和动态状态。若大部分网络在 NPU，少数算子回退 CPU/GPU，每次边界可能需要同步、格式转换或数据搬运；这些成本能抵消加速器计算收益。应沿实际计算图标出 backend 分段和边界数据量，再定位总关键路径。

量化还可能改变图分段：后端有 W8A8 Linear 不证明支持 GPTQ W4A16 的 packed 布局或 group scale，也不证明分页 KV Attention 可原生执行。必要时重写等价算子或保留回退，分别验证模型语义、质量和实际执行路径。

零拷贝只消除某次显式复制，仍可能存在共享 DRAM 带宽竞争、cache maintenance、DMA 导入和 fence。异构调度要同时看任务依赖与缓冲所有权，见[跨帧缓冲竞争](19-异构调度与跨帧缓冲.md#buffer-race)。
