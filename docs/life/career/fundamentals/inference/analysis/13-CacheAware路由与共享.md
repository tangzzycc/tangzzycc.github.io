# Cache-aware 路由：缓存收益、热点负载与跨实例共享

<div class="study-notes study-analysis" markdown="1">

来源：提供的「腾讯 AI Infra 部门二面」「英特尔校招面经」「小鹏汽车三面」「小米基模组一面」「阿里平头哥一面」；对应推理优化[第 36、77～80、83 题](../index.md#q60)，补充[第 76 题](../index.md#q24)的多副本路由。个人仿真项目与“和自己项目的差异”不作为基础题。

## 1. 省 Prefill 不等于请求更快 {#cache-hotspot}

热门前缀集中到某实例，可提高复用，同时积累排队、活动 Decode 和 KV 占用。路由的目标应是在容量和延迟目标下获得更好的服务能力；缓存只是减少工作的一项信号。

Prefix reuse 直接减少 Prefill，可能改善 TTFT；缓存命中不直接缩短同一请求每步 Decode 计算。TPOT/ITL 的改善可能来自更均衡的生成负载或减少 Prefill 干扰，需用时间线验证。原面经写作“TTFT/TBOT”，TBOT 的定义未给出，本文沿用已有 TTFT/TPOT/ITL 口径，不将 TBOT 自动解释为 TPOT。

假设 A 本地命中更多，当前排队 50 ms，剩余 Prefill 需 10 ms；B 命中少，排队 5 ms，剩余 Prefill 需 30 ms。在忽略其他成本的例子中，A 首次执行前后约 60 ms，B 约 35 ms，B 更合适。数字是相同测量边界下的简化成本，真实还需预处理、采样、传输和返回。

## 2. 评分需要方向、尺度和准入条件 {#score-units}

设缓存收益 C 越大越好，负载成本 L 越大越差，均已归一化，可使用 `score=C−λL`，选高分；这是教学评分，不是所有框架的固定公式。

- <strong class="study-key">Cache Score。</strong> 匹配前缀 token 数、预计省下的 Prefill 时间、缓存层级与恢复成本都可能参与；不能把远端命中与本地命中同价。
- **Load Score。** 已分配和本次新增的工作、活动 Decode batch、KV 长度、队列与设备能力；两个同请求数实例可能成本不同。
- **硬约束。** 先过滤无法容纳请求、模型不兼容或已过载的目标，再比较分数；高命中不能覆盖容量不足。
- **统一时间。** 更可解释的方案是估计排队时间、未命中 Prefill、恢复和执行开销，选预计完成代价较低者；模型估计仍需测量校准。

用原始“命中 token 数”减“请求数”时，λ 必须承载换算关系；任意归一化方法也会改变最优 λ。指标单位未固定时，数值大小没有可迁移意义。

用统一时间单位可以避免任意分数相减。对候选 worker j，粗估首次响应成本为 `T_queue,j+T_restore,j+T_prefill,j+T_other,j`；已有可复用前缀会减少 T_prefill，但增加的恢复成本进入 T_restore。还要预测本请求入场后对 D 侧活动 KV/迭代时间的影响，并先过滤容量不足的目标。

假设 A 预计省下 80 ms Prefill，却新增 100 ms 排队；B 只能省 20 ms，但新增排队 10 ms。相对于相同未命中基线，A 的净代价增加 20 ms，B 减少 10 ms。缓存收益只有放回总关键路径，才能决定哪个目标合适。

### 缓存分和负载分怎样变成可解释的预测？

先估计相同 worker 上“完整执行”与“复用前缀后执行”的增量差，把 cache benefit 转为预计节省的时间；load 估计排队与活动迭代成本，远端命中再加恢复时间。长度不能简单线性换算时间，因为 Attention 与 chunk/batch 会改变成本；同样命中 4K token，在 4K 与 32K prompt 上可能省下不同工作。

若分数用 `C−λL`，C/L 的单位和归一化方法一变，λ 的含义就变。用毫秒估计可更易解释，但模型误差、反馈滞后与多请求同时入场仍存在；目标容量、健康、模型兼容必须先作为硬筛选条件。

### 多个 Router 同时选“最空闲”实例会怎样？

两台 Router 读取同一旧负载，都把一批请求送到 worker A，下一轮才发现 A 已热点；短时决策在反馈之间相互放大。可在分配时立即记账在途负载、使用容量预留与释放协议、随机化近似等价候选，并控制反馈延迟。仅缩短监控周期不能完全解决并发入场的状态竞争。

## 3. λ 与反馈怎样验证？ {#lambda-feedback}

1. 用代表性 workload 标定单实例耗时与负载代理，统一 score 单位和计量边界。
2. 扫描 λ，比较仅缓存、仅负载与混合策略，在 TTFT/TPOT 目标下衡量 goodput。
3. 覆盖前缀热度变化、冷启动、低命中、长短输入输出、突发和异构设备。
4. 检查实例负载偏斜、拒绝/抢占、缓存淘汰与传输，避免平均指标掩盖热点。

在线更新参数或负载时，需计入刚分配但还没上报的请求，控制反馈延迟。多个 Router 独立选最低分目标可能造成集中入场；可用分配记账、容量预留和适当随机化等缓解，但不能只靠随机化掩盖过载。

### 调 λ 如何避免只适配一个数据集？

以相同硬件和服务目标扫描缓存权重、负载权重，并对照 cache-only、load-only、混合与基础策略。标定集估计时间模型，独立 workload 验证；覆盖冷缓存、热门 system prompt 突变、低重复、不同长度与到达率。参数应按在线 goodput 与长尾表现选择，而不是只最大化命中率。

实际 TTL/淘汰和路由形成反馈：总选某一实例会让缓存更集中，随后命中继续吸引请求；负载惩罚过强又可能失去局部性、造成重复预填充。参数自适应需设稳定窗口与变更速度，避免追逐瞬时波动；不同设备执行成本也不宜只用相同队列长度比较。

## 4. 共享索引与共享数据不同 {#directory-vs-data}

| 层次 | 解决什么 | 仍需完成什么 |
| --- | --- | --- |
| 共享缓存目录/索引 | 找到前缀在哪个实例或存储层 | 目录更新、淘汰与失效处理 |
| KV 数据传输/共享层恢复 | 把实际数据准备给目标执行者 | 传输、布局兼容、目标空间、就绪通知 |
| 请求/状态交接 | 继续原请求或使用正确前缀 | 有效长度、模型版本、adapter、位置与其他模型状态 |

本地 block ID 不具备跨实例含义。源数据需保留到传输安全结束，目标数据就绪后才能执行；如果索引滞后或源失败，需回退到其他缓存或重算。TP、层分组和量化布局不一致时还可能重排，混合 Attention 模型可能有标准 KV 以外的状态。

“少重算”与“少传输”可能冲突：远端命中很多，但恢复很慢时，本地重算反而更优。共享缓存能增加可用复用范围，却不会消除路由与带宽瓶颈。

## 5. 为什么不能只优化命中率？ {#hit-vs-latency}

- **请求命中。** 至少命中某部分的请求比例，与完整前缀命中不同。
- **Token 命中。** 总复用 token 数占可缓存 prompt token 的比例，计量要明确实际可跳过边界。
- **计算收益。** 同样 token 数的 Prefill 时间会随长度、batch 和实现变化，不应直接用命中比例当加速比。
- **服务结果。** 同时报告排队、TTFT/TPOT/ITL、goodput、负载偏斜与传输成本；低命中策略也可能更符合延迟目标。

### Token 命中率怎么会提高，却减少了 goodput？

命中长前缀省下 Prefill，但目标 worker 可能因此聚集活动 Decode、KV 占用与排队；远端命中还需恢复，写回/预取可争用带宽。命中率是工作减少的代理，最终延迟还包含等待与新增数据路径。

可以把高命中请求分成“直接可用 GPU 命中”“Host/远端待恢复”“部分匹配仍需后缀前向”，分别统计实际跳过行数、恢复耗时、queue、TTFT/ITL 和达标率。若提高命中后抢占/超时增多，应约束入场、负载与 IO，而不是继续单独最大化命中。

## 6. 与 Dynamo 已有策略如何比较？ {#dynamo-comparison}

查阅的 **Dynamo v1.5.1 Routing Concepts** 已同时考虑可复用缓存与预计活动负载；公开模型包含未命中及活动 Prefill 工作、活动 Decode KV 工作，并支持按配置加入活动请求成本。不同存储层命中有 credit，缓存丰富但活动 Prefill 过重时还可衰减相应 credit。

因此“cache score 加 load score”本身不是与 Dynamo 的区别。比较应固定版本与部署方式，明确：

- 缓存和负载信号来自事件还是预测，是否计入刚分配请求。
- Prefill/Decode、活动请求与硬件能力怎样建模，参数如何标定。
- 本地/主机/磁盘/共享命中怎样折算，是否计入传输路径与容量。
- 是否有过载过滤、随机化、扩缩容及多 Router 协调。
- 相同资源、模型和 workload 下的消融与 goodput 证据。

仅凭面试记录无法判断个人方案的实际差异，不能从两个评分名字推断创新。

## 7. Router、Worker 与 Planner 的控制粒度 {#control-granularity}

| 角色 | 主要决策/职责 | 输入与输出 |
| --- | --- | --- |
| Router | 请求选择哪个兼容执行组 | 缓存、活动/在途负载→目标与路由记账 |
| Worker 与内部 Scheduler | 当前迭代怎样执行 | 队列、预算、KV→batch/forward、完成与资源状态 |
| Planner | 如何规划容量或扩缩容 | 流量观测、性能模型和目标→副本建议或部署动作 |

Dynamo v1.5.1 Planner 文档说明它使用引擎性能与流量信息，为 TTFT/ITL 目标调整 P/D 副本；支持不同优化目标、短期负载和较长期容量策略。这里保留职责划分，不将默认周期或可选能力当成所有部署的固定行为。

缓存目录和 forward/负载事件把执行反馈给控制决策，但观测可能滞后，规划也有启动成本。Planner 不逐 kernel 分配 warp，Router 也不取代 Worker 内的 Continuous Batching。仿真替代执行的边界见 [性能模型与 Mock](21-推理仿真与性能模型.md)。

## 8. 未命中后重算、恢复还是换目标？ {#miss-decision}

「B站 AI Infra 二面」图片描述的系统在本地未命中时重算，并不从其他节点迁移。这是原实现边界，不是所有推理引擎的行为；对应推理优化[第 32 题](../index.md#q102)。

只管理本地缓存时，可复用已有连续前缀并计算剩余后缀；有 Host/外部缓存或跨实例组件时，可比较恢复 KV 与本地重算，也可在执行前重新路由。Least-load 应估计执行组的活动/在途工作与新增请求成本，而不是只按请求数。

尚未执行的新请求选择有缓存目标，与迁移已生成的活动请求不同。后者还需 KV、位置、采样/停止进度及其他模型状态，不能只换 worker ID。共享目录能发现远端命中，但不保证数据已准备好；兼容性、容量和恢复关键路径都要满足。
