# 推理仿真与性能模型：虚拟时钟、数据来源和误差验证

<div class="study-notes study-analysis" markdown="1">

来源：提供的「小鹏汽车三面」「小米基模组一面」「阿里平头哥一面」记录；对应推理优化[第 24、66、94～97 题](../index.md#q93)。保留可迁移的系统建模方法，不收录个人项目实现、客户用途或未经证据支持的误差数字。

## 1. 单进程也能模拟多执行组 {#virtual-clock}

离散事件仿真维护虚拟时间 t 和按事件时间排序的队列。事件可包括请求到达、Host 调度完成、模型迭代完成、KV 传输完成和资源释放。每次取出最早事件推进 t，处理状态与资源，再安排下一批事件；不需要真实 `sleep`，不要求每个 Worker 启一个真实进程。

| 请求状态 | 推进条件与更新 |
| --- | --- |
| Waiting Prefill | 已入场，等待 P 组、token 预算和容量 |
| Prefill | 推进当前 chunk/批次，更新已计算长度、KV 和输出边界 |
| KV Transit | 目标已预留，源就绪，传输占用实际路径并等待完成 |
| Waiting Decode | 已有可用状态，但等待 D 侧组批/资源 |
| Decode | 每轮按 batch 和历史长度查/算 forward 成本，更新 token 与停止状态 |
| Finished/Cancelled | 输出结束或取消，按真实在途依赖释放资源 |

首 token 可以由 P 侧输出或按交接方式在 D 侧处理，事件时间需遵循实现，不能固定 TTFT 必含或必不含传输。相同时间事件要有明确 tie-break 规则，避免到达和释放先后偶然改变结果。

每个 Replica 是独立执行组，有自己的队列、模型布局、KV pool 和完成事件；TP ranks 协作一轮，PP stages 有各自依赖和资源。共享 EP 组、链路或 Host 队列会耦合多个入口，不能把副本当成完全独立服务器后直接乘峰值能力。

假设时刻 0 有 P₀、P₁ 两组同时开始任务，性能表给出 5 ms、8 ms。事件队列记录 `(5,P₀完成)` 与 `(8,P₁完成)`；仿真先把虚拟时钟推进到 5，更新 P₀ 的队列和 KV transit，再推进下一事件。宿主进程只顺序处理事件，但仿真资源在 0～5 ms 内可以同时处于忙碌状态。

每项工作需要按依赖和资源计算开始时间，例如 `max(到达,依赖完成,资源可用)`。若两条 KV 传输共享上行链路，不能都独占峰值带宽；同一时间的完成、取消和新入场也需确定事件处理规则。把每个 forward 延迟机械相加会把所有执行组串行化，丢失本来要研究的并行效果。

## 2. 状态会反过来决定下一次延迟 {#state-feedback}

Forward 延迟不是单个常量，它依赖本轮 token 数、各请求历史长度、head/hidden、dtype、并行、chunk、Graph 桶和执行路径。Decode 输出增加后，历史 KV 读取和容量随之变化；cache hit 和迁移也改变 Prefill 工作。

可用 request trace 规定输入、输出长度、到达和前缀。若用受控 logits/EOS 模拟完成，需明确是否仍经过真实 sampling/CPU 流程；某个输出改变长度、专家分布或候选接受，会改变系统工作。不能将所有请求的 forward 延迟提前固定后声称已准确模拟动态组批。

通信/计算重叠需表示并行资源、依赖与争用，不应把两项成本始终相加或始终取 max。KV 容量、入场限制、在途预留与驱逐都可能改变排队，相关策略见 [P/D 与容量交接](05-PD分离.md)。

### 单进程虚拟时钟如何模拟资源竞争而不是串行求和？

每个执行组/链路维护可用状态，事件记录完成时间与要更新的资源。任务开始取决于到达、前置完成、容量及执行资源；事件触发后更新 batch、KV 长度、队列与下一项工作，再查询对应 shape 的延迟。Decode 的下一轮不能在上一轮采样尚未完成时启动，两个独立执行组则可以同时忙碌。

共享链路或 HBM 的服务速度可能随并发变化：若模型给每条并行传输都独占峰值带宽，会系统性低估 transit。可用实测并发曲线、资源份额模型或更细事件近似，明确使用哪一种。数据缓存命中、抢占、取消和 P/D 绑定改变未来工作，不能只预先为每请求算一个固定总时间。

## 3. 性能数据必须带来源与适用边界 {#latency-provenance}

| 来源 | 可用于什么 | 主要局限 |
| --- | --- | --- |
| Silicon 实测 | 标定真实算子、forward 和搬运曲线 | 受驱动、kernel、shape、频率和测试边界影响 |
| SOL 理论估计 | 判断理想资源瓶颈与耗时下界 | 不包含所有低效、提交、竞争和排队 |
| 拟合模型 | 压缩数据并预测未测 shape | 需要独立验证，可能遗漏 regime 切换 |
| 插值 | 测量邻域内估计 | 不能跨不同 kernel/策略随意插值 |
| Pre-silicon 周期级仿真 | 为未上市硬件提供周期、访存与执行估计 | 周期转时间、系统外设及 workload 的假设需说明 |

性能表 key 至少包含设备/软件版本、算子或模型、dtype/量化、实际 shape、并行和执行策略；通信还需路径、方向、消息大小与并发。记录测的是设备 kernel、模型 forward，还是包含 Host/通信的端到端时间，防止重复计入或漏算。

<strong class="study-key">SOL（Speed of Light）与 SLO（Service Level Objective）不同。</strong> SOL 表示理想资源性能上界；在指定资源模型下，可初估 `t≥max(FLOPs/P_eff,bytes/BW_eff)`，多层 Roofline、实际低精度指令与稀疏条件需一致。SLO 是 TTFT、TPOT 等服务目标，本身不提供算子耗时。

若记录写“按 SLO 拟合”，只能理解为在目标约束下标定能力，不能据此把 SLO 当作设备实测延迟。峰值、持续性能和经验效率也要明确区分。

在同 regime 内插值，例如测得同 kernel 下 token 行数 128、256 的耗时 4、7 ms，线性估算 192 为 5.5 ms；这是待验证预测。若中间换了 kernel、Graph 桶或 tile，曲线可能不连续。超出测量边界属于外推，应标明风险与不确定性。

### 性能表的键应该包含哪些 shape 与执行条件？

GEMM 至少需要 M/N/K、dtype、量化/稀疏布局和 backend；Attention 需要 Query 行数、历史长度分布、Q/KV heads、head width、mask 和缓存表示；collective 需要组规模、拓扑、消息 bytes 与并发。仅以“模型名+batch”查一条时间，会把本地 TP shape 与长短历史差异吞掉。

实测记录应带芯片/软件版本、warmup、时钟/功耗、计量边界与样本分布。SOL 是相应计算/带宽理想下界，可帮助缺失区域推导，不含全部真实启动、依赖和资源竞争；SLO 则是服务目标，二者不能混用。插值跨过算法分发、tile 或容量阈值时可能失真，外推更需明确不确定性。

## 4. MAPE 的口径和反例 {#mape}

对于 N 个正的实测耗时 tᵢ 和预测 t̂ᵢ：

$$
\mathrm{MAPE}=\frac{100\%}{N}\sum_{i=1}^{N}\frac{|\hat t_i-t_i|}{t_i}.
$$

例如真实 `[10,100]` ms、预测 `[11,90]` ms，MAPE=10%；平均绝对误差为 5.5 ms。若真实 0.01 ms、误差 0.01 ms，则单点相对误差 100%，即使绝对误差很小。实测为 0 时公式无定义，需说明排除、计时下限或其他度量，不能静默改分母而继续报标准 MAPE。

验证应留出未参与拟合/插值标定的数据，可按 shape/配置/workload 分组，避免重复样本泄漏；同时报告分桶 MAPE、绝对误差、偏差方向、最差区间和样本覆盖。

面经的 `<10%` 不是本笔记验证结果，也不是通用准确度门槛。算子预测误差较小仍可能使高利用率队列出现很大的 P99 偏差，需要再校准端到端 TTFT、TPOT、吞吐与容量边界。

### 平均 MAPE 很小，为什么长尾预测仍可能不可靠？

MAPE 平均各样本的相对误差，短 kernel 的分母小可能占比很大；多数普通样本预测准确也能掩盖少数极长请求、容量阈值与高并发区域。应按阶段、shape、长度、负载分桶，并结合绝对误差、偏差和高分位误差。

校准表的留出验证检查 kernel/collective 延迟，端到端验证再检查排队、缓存、transit 和状态反馈。模块误差可能在临界负载下放大：预计服务能力略高于真实值，就可能错误预测队列稳定。低于某个 MAPE 门槛只说明该数据和口径下的拟合表现，不证明所有配置搜索结果可靠。

## 5. 传输估计需要真实路径 {#transport-path}

512 MiB KV 在独立有效 50 GB/s 路径上的主载荷约为 10.7 ms。这未包含启动、拆块、布局转换、暂存、映射和完成通知；并发下有效带宽也可能降低。

跨 NUMA 的 GPU、NIC 和 Host memory 可能经过不同 PCIe root complex、CPU 互联或远端内存。应记录 endpoint 与 NUMA 放置、P2P/GPUDirect 是否实际可用、方向、size 和并发，测量延迟曲线后建模。KV 数据量由实际布局计算，TP 重分片或重复 KV 不能直接用逻辑总量代替物理传输。

同一路径两份流量共享带宽时，应建资源服务模型或使用并发曲线，不让每条流都独享满带宽。队列、传输尾部和请求可见延迟分别统计；分层/按层传输可能与计算重叠，最终看关键路径。

### 用 KV bytes/BW 估计传输，遗漏了哪些依赖？

源需要先完成数据写入，目标需分配并建立兼容落点，发送还需打包/注册或 descriptor，路径可能包含 Host 暂存、NUMA 和网络。链路启动对小消息明显，并发流共享带宽；按层流水时总时间又由依赖关键路径决定，而不总是逐层时间直接相加。

为仿真标定曲线时至少固定源/目标对、实际 bytes、并发、方向、内存位置和完成边界。跨 NUMA 的 H2D、GPU P2P 与 GPUDirect RDMA 不应共享同一条“标称带宽”常数。估计还要包含状态转换和容量等待，不能把纯拷贝完成当作目标已入场。

## 6. Mock 与真实执行的验证边界 {#mock-boundary}

Mock forward 可以接收实际调度产出的 batch/metadata，分配逻辑 KV，查表得到完成时间并产生受控输出；这样能评估策略和生命周期，而不运行真实 GPU 算术。

Logits hook 可能仅在真实 forward 后修改输出，用于控制 token 或停止行为；如果未替换 forward，真实设备耗时仍存在。若从算子成本合成 forward，还需验证融合、通信和 overlap，不能单纯相加全部算子时间。

建议从三层对照校准：基础 kernel/传输→完整 forward→固定 trace 的完整服务。Mock 无法独立证明模型质量、真实硬件竞争或国产 backend 正确性。用仿真扫描配置得到候选及帕累托前沿后，再对关键候选实测确认，见 [部署配比与帕累托前沿](12-缓存层级与部署配置.md)。

### Mock logits 可以替代真实模型到什么程度？

查性能表替代 GPU forward，适合研究明确给定的 shape/延迟与状态规则下的排队、组批和资源配比；它无法凭空预测采样输出、投机接受、动态 MoE 路由或语义 prefix hit。若这些影响后续负载，需要真实 trace、统计模型或受控条件，而不能随意固定成常数。

验证应分别对照单算子延迟、事件/状态转换和端到端 workload。Mock 的提交/事件开销也不能混入虚拟 GPU 时间重复计算。不同 fidelity 回答不同问题：性能表模拟软件资源，周期级模拟可研究更细硬件机制，但参数来源、假设和误差范围必须明确。
