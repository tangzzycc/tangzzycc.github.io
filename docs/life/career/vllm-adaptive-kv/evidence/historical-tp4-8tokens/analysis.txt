# 最终 Adaptive KV Offload 测试记录

## 测试目标

验证在四卡 TP=4、GPU KV cache 较小且二级缓存为本地文件系统时，Adaptive KV Offload 是否会在磁盘读取拥塞时选择重算，从而保护短请求的 TTFT。

## 测试环境与场景

- 模型：`Qwen3.6-35B-A3B-FP8`
- 并行度：TP=4
- GPU KV cache：4 GiB
- CPU KV cache：10 GiB
- 二级存储：本地文件系统，读线程数 1，写线程数 1
- FlashInfer autotune：关闭
- 请求波次：先提交 4 个 16,384-token bulk 请求，50 ms 后提交 4 个 4,096-token latency 请求
- 输出长度：8 tokens
- Adaptive：`async_with_fallback`，最多 4 个并发 fallback，单请求最多重算 8,192 tokens

seed 阶段使用已生成的 16K 文件系统 KV cache。此前尝试生成 30K seed 时触发账户磁盘配额（`Errno 122`），该失败目录已移入 `archive/failed_final_seed_20260830`，没有作为结果使用。

## 结果

| 指标 | baseline | adaptive | 变化 |
| --- | ---: | ---: | ---: |
| 全部请求 TTFT P50 | 2,561 ms | 2,914 ms | +13.8% |
| 全部请求 TTFT P99 | 2,614 ms | 3,490 ms | +33.6% |
| 全部请求 TPOT P50 | 12.5 ms | 78.0 ms | +522.6% |
| 输出吞吐 | 23.41 tok/s | 17.96 tok/s | -23.3% |
| 短请求 TTFT P50 | 2,561 ms | 1,447 ms | **-43.5%** |
| 短请求 TTFT P99 | 2,562 ms | 2,378 ms | **-7.2%** |
| bulk 请求 TTFT P50 | 2,140 ms | 3,457 ms | +61.5% |

baseline 的 8 个请求全部磁盘命中、0 个重算。adaptive 的 4 个 latency 请求全部选择重算，4 个 bulk 请求仍从磁盘加载。日志中的决策为“load 470--591 ms vs recompute 377 ms”，与策略的成本模型一致。

## 分析结论

该场景证明了自适应策略的目标行为：当文件系统读取排队导致预计 load 成本高于 GPU prefill 重算成本时，策略会放弃慢速磁盘读取，优先完成短请求；短请求 TTFT P50 下降 43.5%，P99 下降 7.2%。

由于 fallback 请求仍占用 prefill 资源，混合批次中的 bulk 请求被推迟，导致整体 TTFT 和吞吐下降。因此这不是“所有指标都提升”的场景，而是一个明确的 SLO trade-off：以牺牲低优先级 bulk 吞吐换取短请求延迟保护。生产配置应结合请求优先级、并发 fallback 上限和 prefill 余量设置，而不能只追求最大 fallback 并发度。

## 规模化场景推演与面试表述边界

当前目录中只有一组小规模端到端实测，不能把未运行的大规模结果写成实测收益。特别是 TPOT 会受到 fallback 重算、prefill 资源竞争和统计口径影响，不能依据当前样本线性外推“整体 TPOT 提升”。

可以将下面的配置作为下一阶段的可复现实验设计和合理目标区间：

- TP=4；
- 64 个请求，分 4 个波次进入；
- 每波 12 个 16K bulk 请求和 4 个 4K latency 请求；
- bulk 输出 256 tokens，latency 输出 32 tokens；
- GPU KV cache 4 GiB，CPU KV cache 10 GiB；
- 磁盘读线程数为 1，用于制造存储排队；
- adaptive fallback 上限为 4 个请求、8192 tokens；
- 第 1 波只做 warmup，后续 3 波采集数据；
- baseline 和 adaptive 在同一个长生命周期服务中运行，避免每次启动的 CUDA Graph/JIT 冷启动污染；
- 至少重复 3 轮，报告 P50/P95/P99 和置信区间。

该场景的目标区间只能作为待验证假设：

| 指标 | 待验证目标区间 |
| --- | ---: |
| latency TTFT P95 | 降低 25%--45% |
| latency TPOT | 降低 5%--20% |
| overall TTFT P95 | 增加不超过 0%--10% |
| overall TPOT | -5%--+5% |
| bulk TTFT | 增加不超过 15%--25% |

要使这个目标更可能成立，实验或后续实现需要：

1. 为 latency 请求预留独立的 prefill token budget；
2. 只允许 fallback 使用预留预算，避免形成新的 prefill 洪峰；
3. 给 latency 请求更高的调度优先级；
4. 分别统计 latency 和 bulk 的 TPOT，而不是只看混合批次平均值；
5. 明确 TPOT 统计口径，排除请求进入调度前的等待时间；
6. 使用同一进程多波次测试，单独报告并剔除冷启动阶段。

面试中应将结论表述为：

> 当前实测已经验证策略在存储拥塞时可以把短请求从慢速 KV load 切换为 GPU recompute，短请求 TTFT P50 降低 43.5%。大规模场景的设计目标是通过预留 prefill 资源和请求优先级控制，进一步降低短请求尾延迟，并把整体 TTFT/TPOT 退化控制在可接受范围内；整体收益仍需在资源隔离后的多波次压测中验证。

不应把“64 请求下 TPOT 提升 15%”等目标区间写成已完成结果，除非产生对应的 JSON、服务日志和重复实验数据。
